## Context

詳細画面のコメントは `commentBlock`（`internal/ui/preview.go:50`）が 1 件ずつ行に直す。AI のコメントだけが
引数 `expanded` を見て、false なら見出し 1 行（`▌AI  HH:MM  <要約>  (+<n> 行)`）に畳まれる。
呼び出し側は 2 つある。キュー画面のプレビューは常に `true` を渡し（同 `:43`）、詳細画面は
`detailState.expanded` をそのまま渡す（`internal/ui/detail.go:375`）。`detailState` は `openDetail` が
ゼロ値で作る（同 `:75`）ので、詳細を開いた直後の `expanded` は false になる。動機は proposal.md の「Why」を見る。

制約は 2 つある。第 1 に `card-detail` の 5 つの Requirement が、既定・`x` の向き・書式の参照先の名前・
フッタのヒントを文面で固定している。第 2 に `detailState` はテストが 3 か所でゼロ値のまま組み立てており
（`internal/ui/view_test.go:542`、`internal/ui/detail_test.go:505`, `:1032`）、既定をゼロ値から外すと
テストの見る画面が実物とずれる。

## Goals / Non-Goals

**Goals:**

- カード詳細画面と PR 詳細画面を開いた直後に、routine コメントの全文が出るようにする
- 見出しだけの一覧に戻す手立て（`x`）を残す
- キュー画面のプレビュー・review thread・ヘルプ画面の見え方を変えない

**Non-Goals:**

- コメントごとの折りたたみ（1 コメントだけ畳む）を持つこと。フラグは画面に 1 つのままとする
- 折りたたみの書式（要約と `(+<n> 行)`）を変えること
- 長いコメントを別の方法で短くすること（先頭 n 行だけ出す、検索で飛ぶ、など）
- 人のコメントの扱いを変えること。元から全文である

## Decisions

### D1. フラグを `collapsed` に変えて、ゼロ値を既定にする

`detailState.expanded bool` を `collapsed bool` に変える。`openDetail` は今までどおりゼロ値で
`detailState` を作り、ゼロ値の `collapsed == false` がそのまま「展開」になる。描画は
`commentBlock(..., !m.detail.collapsed)` で渡し、`case "x"` は `m.detail.collapsed = !m.detail.collapsed` に
なる。`commentBlock` の引数名 `expanded` は変えない（プレビューが常に `true` を渡す側の言葉なので、
呼び出し側の状態の名前とは別で良い）。

`expanded: true` を `openDetail` に書き足す案は採らない。`detailState` をゼロ値で作るテストが 3 か所あり、
そこだけ折りたたみの画面を見ることになる。**既定が変わるときは、ゼロ値が既定を指すように名前を選ぶ**方が、
初期化の書き忘れで既定が崩れる経路を消せる。

### D2. 開き直しは `detailState` の作り直しで既定に戻る

「キュー画面から `Enter` で開くたびに既定へ戻る」は `openDetail` が `detailState` を作り直すことで
満たされており（`internal/ui/detail.go:75`）、この change でそのコードは変わらない。D1 でゼロ値の意味が
変わるので、戻り先だけが折りたたみから展開に変わる。カード詳細と PR 詳細を `g` / `Enter` / `Esc` で
行き来するときは `detailState` を作り直さないので、`x` で畳んだ状態はそのまま持ち越す。今の挙動
（展開したまま持ち越す）と同じ構造で、向きだけが逆になる。

### D3. フッタのヒントは `x 畳む` にする

`x 展開` と `x 畳む` はどちらも表示幅 6 列なので、フッタのヒント全体の列数（カード詳細 144 列、
PR 詳細 109 列、`PRs` が空のカード詳細 96 列）と、「幅 143 以下の端末で末尾から切れる」という記述が
そのまま通る。`x 折りたたみ` は 12 列で、カード詳細のヒントが 150 列になり、`TestDetailFooters` が
使う幅 150 の端末でヒントがちょうど端まで届く（ステータスが出ているときはヒント側が丸ごと消える。
`internal/ui/view.go:316-317`）。語としても `internal/ui/preview.go:49` の「見出し 1 行に畳む」と揃う。

ヘルプ画面の行（`internal/ui/help.go:29`「routine コメントの展開 / 折りたたみ（詳細）」）は、向きを
書いていないので変えない。`help-screen` の Requirement はキーの行を 1 字単位で固定しているため、
変えなければ MODIFIED が 1 本減る。

### D4. 表示状態は `example` fixture を通したテストで再現する

この TUI は `gh` の出力を読むだけで、開発用の DB や seed を持たない。表示状態は
`internal/gh/testdata/fixtures/example/` が持つ 2 つの fixture で再現できる。issue 108 は AI コメント
1 件と人のコメント 1 件を持ち、PR 131 は AI コメント 1 件と review thread 1 本を持つ。
テストは `internal/ui/detail_test.go` が担い、`View` の
文字列をそのまま検証している。したがって seed を足さず、既存 fixture を使う Scenario で
「開いた直後に全文が出る」ことを見る。

## Risks / Trade-offs

- **画面に最初から見えている範囲が狭くなる。** AI コメントが数行〜数十行に増えるので、その下にある
  `── review thread ` や checks を見るのにスクロールが要る場面が増える。`G` / `End`（s37）で末尾へ
  飛べるので、手立て自体は既にある。
- **行の増え方はコメントの長さに比例する。** grill の質問が並ぶ PR では 1 コメントが 20 行を超える。
  畳みたい人は `x` を 1 回押す（Q1 で選択肢 B を採ると、この逃げ道が無くなる）。
- **既存のテストが 6 本壊れる。** どれも「畳まれていること」を期待しているので、期待値を入れ替える。
  壊れること自体が既定を変えた証拠になるので、テストを消さずに書き換える。

## 未決事項

- **畳んだ状態を設定ファイルに持つか。** 「起動時は畳む」を `config` の項目にする案は採らない。
  設定項目が増えるだけで、`x` を 1 回押すのと結果が変わらない。既定を変えたい要望が出たら、その時点で
  issue を立てて決める。
- **コメントごとに畳めるようにするか。** フラグは画面に 1 つのままとする（`card-detail` の Requirement が
  「1 つのフラグで画面内の全 AI コメントを同時に切り替え、コメントごとには持たない」と決めている）。
- **本文領域をコメントの先頭へ送るキーを足すか。** 開いた直後に見えるのは本文の先頭で、コメントは
  その下にある。`G` / `End` は末尾へ飛ぶだけで、コメントの先頭に止まるキーは無い。必要になったら
  別 issue で決める。
