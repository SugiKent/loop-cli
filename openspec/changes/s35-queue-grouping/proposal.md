issue: #42

## Why

進行中タブは、**全行がまったく同じ見た目で並ぶ**。このタブに入るのは `SituationInProgress` だけ
（`internal/model/model.go:96-105`）なので、種別の列は常に `進行中`、優先度は常に 7
（同 `:84-85`）、行の色は `kindStyle` に `進行中` の項目が無いので無色
（`internal/ui/view.go:28-35`）。並びは優先度が同じなので経過の新しい順になり、
リポジトリが交互に現れる（`internal/ui/rows.go:84-96`）。

その結果、進行中タブは「無色の行が更新時刻順に混ざった一覧」になる。分類はこのタブの中を
8 通りに分けている（`#n は AI が作業中` / `#n は回答済み。sweep 待ち` /
`#n は question のみ。dispatcher の回収待ち` / `#n は段階ラベルの書き直し中。sweep 待ち` /
`#n は進行中` / `PR #n は回答済み。worker が受け取り中` / `PR #n は auto-fix が受け取り中` /
`PR #n は AI 評価待ち`。`internal/classify/classify.go`）のに、**その違いは画面のどこにも出ていない**。
`Result.Summary` を読んでいるのは `loop-cli-dev classify` だけで、キュー画面の表もプレビューも出さない
（`internal/ui/view.go:216-262`、`internal/ui/preview.go:18-36`）。

どの段階で AI が回っているか（propose を書いている / 実装している / archive 待ち）も、
PR のタイトルが `[propose] #35 …` の形をしているおかげで**主体が PR の行だけ**偶然読める。
主体が issue の行では段階がどこにも出ない。

## What Changes

- 進行中タブの表を**リポジトリごとに区切る**。グループの先頭に、リポジトリ名と件数を載せた見出し行を
  1 行置く（`── <owner/name> ── <n> 件 ────…`）。行があるリポジトリが 1 つだけのときは見出しを出さない
- 進行中タブの**並びをリポジトリ優先に変える**。リポジトリ昇順 → 段階順（`todo` → `propose` →
  `apply` → `archive` → 段階なし。`label` 方式は `To Do` → `In Progress` → `Done`）→
  経過の新しい順 → 番号昇順。優先度は進行中タブでは全行同じなので、第 1 キーから外れても並びは崩れない
- 進行中タブの**種別の列に段階ラベル名を出す**。今は全行 `進行中` で情報が無い列を、その行の主体の
  段階ラベル（`stage:` の接頭辞を落としたもの。無ければ `-`）に差し替える。列幅は変えない
- 段階ラベル名に**色を付ける**。付け方は「未確定の判断」の Q2 で決める
- 今やる / バックログ / 異常のタブは変えない（対象は「未確定の判断」の Q1 で決める）
- 表の高さの配分・スクロールの有無・キー操作・プレビュー・ヘッダ・フッタは変えない。
  見出し行のぶん表に出るカードが減ることは受け入れる（Q3）

## 確定した判断

- **進行中タブの行は 1 つも色が付いていない。** `kindStyle`（`internal/ui/view.go:28-35`）は
  質問 / 方針 / merge / todo 候補 / 異常の 5 種別にしか項目が無く、`進行中` と `その他` は
  mvp.md に色の指定が無いので無色のままにしてある（`openspec/specs/queue-screen/spec.md` の
  「行全体の色は `Kind()` で固定する」）。issue #42 の「色もつけて」という依頼は、このタブでは
  **色が 1 つも無いところへ色を足す作業**を指す
- **進行中タブでは優先度が第 1 キーとして働いていない。** このタブに入る局面は
  `SituationInProgress` だけで `Priority()` は常に 7。だから `buildRows` の第 1 キーを
  リポジトリに差し替えても、このタブの中では並びの意味が変わらない。**他のタブでは変わる**
  （今やるタブは優先度順が製品の中心にある。README 冒頭「優先度順に並べる」）ので、
  Q1 の答えが「全タブ」ならその影響を design で詰め直す
- **段階ラベルは新しい判定を作らずに引ける。** `model.IssueStages(mode, labels)` /
  `model.PRStages(mode, labels)`（`internal/model/model.go:212-226`）が段階順に返し、
  方式は `Model.modes`（`queue-screen`「運用方式は取得のたびに判定した結果を持つ」）に既にある。
  `internal/classify` と `internal/model` に手を入れる必要は無い
- **段階ラベルの色は GitHub 側の実値が分かっている。** `routines-setup` が作るラベルの色は
  `stage:todo` / `wip` = `fbca04`、`stage:propose` / `propose` = `0e8a16`、
  `stage:apply` / `apply` = `1d76db`、`stage:archive` / `archive` = `5319e7`
  （`internal/gh/testdata/fixtures/example/labels.json`）。mvp.md も
  「GitHub 側のラベル色と揃える」と書いている
- **その 4 色を文字色にすると、暗い端末で `archive` の紫が読みにくい。** 黒（`#000000`）に対する
  コントラスト比は `fbca04` 10.4、`0e8a16` 4.7、`1d76db` 4.7 に対して `5319e7` は **2.6** で、
  WCAG AA（4.5）を割る。背景色に回して輝度から黒白の文字色を選べば全色で 4.5 以上になるが、
  その規則は PR #37（`s33-colorful-labels`）が定めている。どちらを採るかは Q2
- **列幅は変えない。** 種別の列は 10 列で、`colTitleStart`（43 列目）と `colFixed`（48 列）が
  spec の Scenario とテストの期待値に埋まっている（`queue-screen`「表の行は…」）。
  段階ラベル名のうち `propose`（7）/ `apply`（5）/ `archive`（7）/ `todo`（4）は収まり、
  `label` 方式の `In Progress`（11）だけが既存の `pad` に `…` で切られる（`internal/ui/view.go:297-303`）。
  幅を動かすと色と区切りに関係の無い Scenario を横断して書き換えることになる
- **見出し行は選択できない。** カーソル（`Model.cursor`）は `m.rows[m.tab]` の添字で、
  `tableLines` が描く行数とは既に一致していない（タイトルの折り返しで 1 枚が複数行になる）。
  見出し行は描画側で挟むだけなので、`j` / `k` の移動もプレビューの対象も変わらない
- **表はスクロールを持たない。** `cut`（`internal/ui/view.go:306-314`）が表の高さで切り捨て、
  mvp.md のキーバインド表に表のスクロールのキーが無い。見出し行は表の高さを消費する
- **この change の delta は、open な 4 件の propose PR のどの delta とも衝突しない。** 4 件のうち
  `queue-screen` に触るのは `s33-colorful-labels`（PR #37）だけで、それは ADDED
  Requirement 3 本（ラベル名の色・`Model` のラベル色の表・状態語の色）で、この change が
  MODIFIED する 2 本の Requirement を触らない。`s33-pr-status-sections`（PR #40）は
  `card-detail`、`s33-now-subcommand`（PR #39）は `now-command` と `tui-entrypoint`、
  `s34-answer-template-quote`（PR #41）は `card-model` / `answer-action` / `answer-question`
- **`s33-colorful-labels` は「キューの表にラベル列を足さない」を延期した判断として書いている。**
  理由は、表の行が種別の色で行全体を包んでいるため、その内側に色を置くと内側のリセットが
  外側の背景を落とすこと（同 change の design D6）。**進行中タブの行は無色なので外側の包みが無く、
  この理由は当たらない**。ただし「表に段階の色を置く」ことが 2 つの change の境目に乗るので Q2 で問う

## 未確定の判断

### Q1. 区切りと色を入れるのは進行中タブだけか、4 タブ全部か

issue の題は「進行中一覧」だが、本文は「すべてのリポジトリ、すべてのステータスが雑多に」と書いている。
進行中タブの中では種別が 1 つしか無いので、「すべてのステータス」が指すのが
**進行中の内訳（段階ラベル）**なのか、**4 タブを合わせた全体**なのかで対象が変わる。

- 選択肢 A（推奨）: **進行中タブだけを区切り、今やるタブは優先度順の 1 本のキューのまま残す。**
  今やるタブをリポジトリで区切ると、「どのリポジトリの用事でも、先頭から捌けば優先度の高い順になる」という
  README 冒頭の約束が崩れる（`!!` の質問が 2 番目のリポジトリの見出しの下に沈む）。進行中タブは
  優先度が全行同じなので、区切っても失うものが無い
- 選択肢 B: **4 タブ全部を区切る。** どのタブもリポジトリで区切られて見た目が揃う。代わりに、
  今やるタブの「優先度順に上から捌く」が成り立たなくなる（リポジトリを跨いだ優先度の比較を
  見出しが分断する）
- 選択肢 C: **バックログ / 進行中 / 異常 の 3 タブを区切り、今やるタブだけ今のまま残す。**
  今やるタブの優先度順を守りつつ、「承認する issue を選ぶ」「壊れた状態を直す」場面ではリポジトリで区切る。
  異常タブは行全体が黄の背景なので、その内側に色を置けない制約（「確定した判断」の最後）がそのまま当たる
- 依存: なし

### Q2. 段階ラベル名の色をどう出すか

進行中タブの行は今どこも無色なので、色の規則をこの change で決めることになる。

- 選択肢 A（推奨）: **段階ラベル名を、GitHub のラベル色を背景に、輝度から選んだ黒か白を文字色にして描く。**
  この規則は PR #37（`s33-colorful-labels`）が `queue-screen` の ADDED Requirement として既に定めているので、
  この change はその規則を引くだけにして自前の規則を書かない。どんなラベル色でもコントラスト比 4.5 以上を
  保証でき、色の規則をリポジトリに 1 つだけ置ける。代償として、この change の実装は
  PR #37 が merge され、実装され、archive されるまで待つ
- 選択肢 B: **固定の 4 色を文字色として段階ラベル名に付ける**（`todo` `#FBCA04` / `propose` `#0E8A16` /
  `apply` `#1D76DB` / `archive` `#5319E7`）。PR #37 を待たずに出せる。代わりに、暗い端末では
  `archive` の紫がコントラスト比 2.6 になり、明るい端末では `fbca04` が 1.6 になる。
  端末の地の色によって、どれかの段階が読みにくいまま残る
- 選択肢 C: **段階ラベル名には色を付けず、グループの見出し行にだけ色を付ける。** PR #37 も端末の背景も
  気にせずに済むが、issue #42 の「ラベルの状態等がわかるように」という依頼に対して色で答えないことになる
- 依存: なし（A を採ると実装順序が PR #37 の後になる。proposal / spec は先に確定できる）

### Q3. 見出し行のぶん表からカードが溢れることを許すか

表はスクロールを持たず、高さは端末の残りの約半分（高さ 24 の端末では 11 行）しかない。
リポジトリが 3 つあれば見出し 3 行を使い、カードが 3 枚ぶん表から落ちる。

- 選択肢 A（推奨）: **許す**。見出しは区切りが要る数だけ出し、スクロールも高さの再配分も足さない。
  mvp.md のキーバインド表に表のスクロールのキーが無く、`cut` が切り捨てる今の振る舞いを変えない。
  リポジトリが 1 つだけのときは見出しを出さないので、単一リポジトリの利用者には 1 行も減らない
- 選択肢 B: **進行中タブの表にスクロールを足す**（`j` / `k` で選択行が表の外に出たら表示をずらす。
  `url-picker` とラベル一覧が既に持っている規則）。溢れなくなるが、キュー画面の表に初めて
  スクロール位置の状態が入り、mvp.md に無い振る舞いを 1 つ足すことになる
- 選択肢 C: **表とプレビューの高さの配分を変える**（進行中タブでは表を厚くする）。
  `queue-screen`「キュー画面は端末サイズによらず表とプレビューを 2 ペインで出す」の按分の規則を
  タブごとに分けることになる
- 依存: なし
