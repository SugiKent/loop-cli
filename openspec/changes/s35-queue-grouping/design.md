## Context

動機は `proposal.md` の Why にある。設計の前提になる現状は次の 6 点。

- **進行中タブに入る Card の分類結果は 1 種類しかない。** `result()` は `Priority` / `Tab` / `Kind` を
  すべて `Situation` から導く（`internal/classify/classify.go:18-20`、`internal/model/model.go:69-128`）。
  `model.Result{...}` のリテラルを書いているのは `classify` の 2 か所だけなので、製品コードの
  進行中タブの行は `Priority` が 7、`Kind()` が `進行中` に固定される
- **`buildRows` はタブを問わず同じ 4 キーで並べている。** 第 1 キーが `Priority` なので、
  進行中タブでは第 1 キーが並びを決めず、実質「経過の新しい順 → リポジトリ → 番号」で並ぶ
  （`internal/ui/rows.go:71-98`）。`Tab` が空の Card はここで黙って捨てられる（同 `:77-79`）
- **表の描画は行の集合を平らに連ねている。** `tableLines` が `m.rows[m.tab]` を回して `tableRow` の
  返す行を連結し、`cut` が表の高さで切る（`internal/ui/view.go:182-214`、`:296-304`）。行と行の間に
  何かを挟む仕組みは無い
- **カーソルは Card の並びの添字で、描画行の数と既に一致していない。** タイトルの折り返しで 1 枚の
  Card が複数行になるため、`m.cursor` が指すのは「何枚目の Card か」である
  （`internal/ui/view.go:211-262`）。`▶` は 1 枚の 1 行目にだけ付く
- **段階ラベルと運用方式はどちらも手元にある。** `model.IssueStages` / `model.PRStages` が段階順に返し
  （`internal/model/model.go:212-226`）、方式は `Model.modes` が持つ（`queue-screen`「運用方式は
  取得のたびに判定した結果を持つ」）。`row` は主体の `labels` を既に持っている（`internal/ui/rows.go:22`）
- **`buildRows` の呼び出しは 2 か所で、どちらも方式を素直には持っていない。** `New` の
  スナップショット経路（`internal/ui/model.go:135`）には方式が無く、`Options` も方式を受け取らない。
  `fetchedMsg` の中では `m.rows = buildRows(m.cards)`（同 `:202`）が `m.modes = msg.res.Modes`
  （同 `:204`）より前にある

## Goals / Non-Goals

**Goals:**

- 進行中タブの行を、リポジトリと段階で目で追える形にする
- 「どの段階で AI が回っているか」を、主体が issue の行でも読めるようにする
- 列幅・高さの配分・キー操作・カーソルの意味を 1 つも変えない
- 他の 3 タブの見た目を 1 文字も変えない

**Non-Goals:**

- 表にスクロールを足すこと（`proposal.md`「明示的に延期した判断と残るリスク」）
- 今やるタブの並びを変えること。優先度順の 1 本のキューは製品の中心にある
- 色の規則を新しく定義すること。ラベル名の色は `s33-colorful-labels` の規則を引く（D5）
- 分類の結果に値を足すこと。列に出す 1 語は段階ラベルに決まったので、`internal/classify` は読むだけにする
- mvp.md がキーバインド表に置いた `v`（カンバンへのビュー切替）を実装すること。これは
  別の画面を足す話で、この change は今の表の中を区切るだけにする

## Decisions

列に出す 1 語は段階ラベル、対象は進行中タブだけ、区切りはリポジトリの 1 段に決まっている
（`proposal.md`「回答で確定した判断」）。以下はその設計である。

### D1. 区切りは「リポジトリの見出し行 1 段」にし、段階は列で示す

issue #42 は「リポジトリごと、またステータスやラベルごとに分解して」と書いており、素直に読むと
リポジトリ → 段階の 2 段のグループになる。**表の高さがそれを許さない。** 表の高さは端末の残りの
約半分で、高さ 24 の端末では 11 行（`internal/ui/view.go:70-71`）。3 リポジトリ × 3 段階なら
見出しだけで 12 行を使い、カードが 1 枚も見えなくなる。

そこで区切りは 1 段（リポジトリ）にし、段階は**既に情報の無い列**に出す。進行中タブの種別の列は
全行 `進行中` なので、そこを段階ラベル名に差し替えると新しい幅を要求せずに済む。並びの第 2 キーを
段階にすることで、同じ段階の行はリポジトリの中で隣り合って並び、見出し行が無くても段階のまとまりが
読める。

### D2. 並びの第 1 キーをリポジトリにするのは進行中タブだけにする

`buildRows` の 4 キーをタブごとに分け、進行中タブだけ `Repo` → 段階 → `UpdatedAt` 降順 → 番号昇順に
する。進行中タブでは `Priority` が全行 7 なので、第 1 キーから外しても並びの意味が変わらない。

手で組み立てた Card では不変条件が破れる。`internal/ui/todo_test.go:39` は `Situation` E /
`Priority` 4 の Card を `Tab: TabInProgress` で作っており、タブで分岐する実装ではこの Card も
新しい経路を通る。分岐の条件にはタブを使う。`tableLines` と `buildRows` はどちらもタブを手元に
持っており、`Situation` を見に行くと Card 1 枚ごとの判定が増える。
この Card は段階ラベルを持たないので列は `-` になり、並びも 1 枚なので観測できる差は出ない。

他の 3 タブは 4 キーをそのまま残す。`rows_test.go` の既存の期待値（優先度順）は今やるタブで
書かれているので、進行中タブだけ分けるかぎり通る。

### D3. `buildRows` は方式を引数で受け取り、取得完了では `msg` から直接渡す

並び（第 2 キー）と列の値が運用方式に依存するので、`buildRows` が方式の表を受け取る形にする。
`fetchedMsg` の中で `buildRows(m.cards, m.modes)` と素直に書くと、`m.modes` の更新が後ろにあるため
**1 回前の取得の方式で並べる**（`internal/ui/model.go:202` と `:204`）。`m.modes` の代入を
`buildRows` の呼び出しより前に動かし、`buildRows(m.cards, m.modes)` を読める形にする。

スナップショットだけで起動した直後（`internal/ui/model.go:135`）は方式が存在しない。
`queue-screen`「運用方式は取得のたびに判定した結果を持つ」が定める「分からない」の扱いに揃え、
ゼロ値の `sdd` として描く。`label` 方式のリポジトリでは `In Progress` が `sdd` の段階順に無いので
列が `-` になり、初回の取得が終わった時点で段階付きに入れ替わる。ラベル色の表も同じく
スナップショットには無いので色も後から付く（`s33-colorful-labels`「Model はリポジトリごとの
ラベル色を持つ」が同じ扱いを定めている）。表が 2 回組み替わることは受け入れる。

### D4. 段階が 2 つある主体は段階順で先のものを出す

進行中の規則 4（`internal/classify/classify.go:43-46`）と規則 5（同 `:47-50`）は段階ラベルの件数を
見ずに `in-progress` を返し、段階が 2 つ以上のときの局面 F の判定（同 `:64`）はその後ろにある。
PR も規則 2 / 3（同 `:99-110`）が先で F（同 `:133`）が後。だから `stage:propose` + `stage:apply` +
`question` の issue は進行中タブに 2 段階のまま入る。`IssueStages` は段階順の `[]string` を返すので、
その先頭を採る。`-` に倒す案は採らない。2 段階の issue は壊れた状態であり、どちらの段階にいるかが
読めた方が直しやすい。

### D5. 色の規則は `s33-colorful-labels` から引き、この change では定義しない

段階ラベルの色として使える値は GitHub 側のラベル色で、`routines-setup` が作る実値は
`stage:todo` `fbca04` / `stage:propose` `0e8a16` / `stage:apply` `1d76db` / `stage:archive` `5319e7`
（`internal/gh/testdata/fixtures/example/labels.json`）。この 4 色を文字色に使う案は PR #37 の
design D3 が計算で否決済みで、実測でも `5319e7` は黒に対して 2.6、`fbca04` は白に対して 1.6 になる。
背景色に回して輝度から黒白の文字色を選べばどの色でも 4.5 以上になり、その規則は PR #37
（`s33-colorful-labels`）が `queue-screen` の Requirement「ラベル名は GitHub のラベル色を背景に、
輝度で選んだ黒か白を文字にして描く」として定めている。

同じ規則をこの change でもう 1 本書くと、リポジトリの中に色の規則が 2 つ並ぶ（CLAUDE.md
「パターン競合は平均化しない」）。だから引く側に回り、**実装は `s33-colorful-labels` の archive を
前提にする**。`tasks.md` の 1 本目がその確認になる。PR #37 は既に `未確定の判断: 0 件` で
`ai-assess:requested` が付いており、この change より先に進んでいる。

`s33-colorful-labels` の delta には、この change と噛み合わない文面が 2 か所ある。

- ADDED「ラベル名は GitHub のラベル色を背景に…」の「色を付けない範囲」に挙げた「行全体に色を付ける
  描画（キューの表の種別の色）の中」は、**進行中タブには当たらない**。進行中の行は `kindStyle` に
  項目が無く行全体の色を持たないので、外側のスタイルが無く、内側のリセットで背景が落ちる問題
  （同 change の design D6）が起きない
- ADDED「プレビューの 1 行目のラベル名に色を付ける」の本文にある「表にラベル列は無い」と、
  同 proposal の「キューの表にラベル列は足さない（列を足す提案が来たときにそこで止まる）」は、
  この change が進行中タブに段階の列を足すことで成り立たなくなる。この change の Requirement
  「進行中タブの段階ラベル名に色を付ける」がその前提を上書きすると spec に明記した

色を引く鍵は**接頭辞を落とす前のラベル名**にする。列に出すのは `archive` でも、issue に付いているのは
`stage:archive` であり、ラベル色の表はリポジトリのラベル一覧から作られるので `stage:archive` で
引かないと色が見つからない。

### D6. 列幅を動かさず、`label` 方式の `In Progress` は既存の切り詰めに任せる

種別の列は 10 列で、`colFixed`（48）と `colTitleStart`（43）が `queue-screen` の Scenario と
`internal/ui/view_test.go` の期待値に埋まっている。段階ラベル名のうち `propose`（7）/ `archive`（7）/
`apply`（5）/ `todo`（4）は収まり、`label` 方式の `In Progress`（11）だけが 1 列はみ出す。
`pad` が `ansi.Truncate(s, 10, "…")` で切るので `In Progr…` になる（`internal/ui/view.go:287-293`）。

`In Progress` のために列を 11 に広げると、タイトル列の開始位置が 43 → 44 に動き、折り返しの継続行の
字下げを見る Scenario とテストが全部ずれる。色と区切りの change でそこまで波及させる価値は無い。
`label` 方式は issue-label-driven のリポジトリ向けで、`In Progr…` でも段階は読める。

一覧では `stage:` を落とし、カード詳細は `段階: stage:propose` を出したままにする
（`internal/ui/detail.go:186-188`）。一覧は列幅 10 に収める必要があり、詳細は幅に余裕がある。
段階ラベルであることは、一覧では列の位置が示す。

### D7. 見出し行は描画のときに挟み、`row` の列には入れない。リポジトリが 1 つでも出す

見出し行を `m.rows[m.tab]` の要素にすると、カーソルの添字と選択の意味が壊れる（見出しを選べてしまう、
`j` 2 回で 2 枚目に届かない、プレビューの対象が無くなる）。`tableLines` が `m.rows[m.tab]` を回す間に
「1 つ前の行と `repo` が違えば見出し行を先に足す」だけにすれば、カーソル・プレビュー・
`a` / `t` / `m` / `c` / `o` / `u` の対象決定はどれも触らずに済む。

「行があるリポジトリが 2 つ以上のときだけ出す」とデータで分岐させる案は採らない。自動更新（既定
120 秒）ごとに `rows` を作り直すので（`internal/ui/model.go:202`）、2 つ目のリポジトリの行が 1 枚
増減するたびに見出しが出入りし、表の全行が 1 行ずれる。選択行の添字は変わらないので、利用者が
何もしていないのに選択行が画面上を動き、末尾の行が落ちる。単一リポジトリの利用者が表の高さを
1 行失うより、表示が揺れないことを採る。件数を毎回見せられる副作用もある。

### D8. 見出し行の書式は `── <名前> ── <n> 件 ` + `─` の埋めにする

無地の `─` だけにすると、表とプレビューの間の区切り線（`internal/ui/view.go:73`）と見た目が同じに
なり、表の中の区切りなのかペインの境目なのか読めなくなる。名前を線の中に置けば、リポジトリ名が
そのまま見出しとして読める。件数を入れるのは、表の高さで切られてカードが見えないときでも
「このリポジトリに何枚あるか」が分かるようにするためである。

幅に収まらないときに `…` を付けないのは、切った跡が線の一部に見えるようにするため。`strings.Repeat`
に負の数を渡すと panic するので、埋める本数は `max(幅 − 見出しの表示幅, 0)` で求める。表の他の行と
同じく、見出し行の表示幅も端末の幅ちょうどにする（`pad` と `emptyHintLines` が同じ扱い）。

## Risks / Trade-offs

- **[段階ラベルは「詰まっているか」を区別できない]** → 規則 1（`wip` あり = AI が健全に作業中）・
  規則 4（人が回答済みで sweep 待ち）・規則 5（question だけの残骸）・規則 6（ラベル書き直し中）は
  どれも `stage:propose` の issue に当たり得るので、列は同じ `propose` になる。issue #42 の
  「状況がわかるように」という依頼に段階ラベルが答えられるのはこの範囲にとどまる。
  分類の状態の語を出す案がこの限界を解くが、`s30-other-grace` との順番待ちを理由に見送った
  （`proposal.md`「回答で確定した判断」）
- **[`s30-other-grace` が段階ラベルの無い行を増やす]** → 同 change は「PR を作った直後でラベルが
  無い / checks が pending / grill 中」の `other` を猶予（既定 30 分）の間だけ進行中に置く。
  そのような PR に段階ラベルは付いていないので、猶予中の行は全部 `-` になる。その行について列は
  何も語らない。どちらの change が先に archive されても spec は衝突しないが、**この change の
  価値は `s30-other-grace` の後で目減りする**
- **[見出し行のぶんカードが表から溢れる]** → 表はスクロールを持たず `cut` が切り捨てる。
  3 リポジトリなら高さ 24 の端末で 11 行のうち 3 行を見出しが使う。選択行が表の外にあるまま `t` を
  押すとラベルを確認画面なしで書き込むので（`internal/ui/todo.go`。`m` / `c` は確認画面が対象を
  見せる）、既存の弱点が悪化する。追従（スクロール）の手立ては URL 一覧
  （`internal/ui/urls.go:157`）とラベル一覧（`internal/ui/labels.go:253`）にあり、どちらも
  スクロール位置の状態を持たずに `start := max(cursor-h+1, 0)` で窓を取っている。キューの表は
  1 枚の Card が複数行になるので窓の起点を描画行の添字で取り直すことになり、この change の範囲を
  超える（`proposal.md`「明示的に延期した判断と残るリスク」）
- **[起動直後に表が 2 回組み替わる]** → D3 のとおり、スナップショットだけの起動では方式と
  ラベル色が無く、初回の取得で段階と色が入る。`label` 方式のリポジトリでは並びも変わる
- **[`s33-colorful-labels` が却下・大幅変更されると、色の規則の引き先が消える]** → 固定 4 色を
  文字色にする案は D5 のとおり成立しないので、そのときは色の規則をこの change で定義し直すか、
  色を見出し行だけに置くかを選び直すことになる。spec で色を付ける対象（種別の列の段階ラベル名）と
  付けない対象（`-`・列の余白）は規則の出どころと独立に書いてあるので、書き換えるのは 1 文になる
- **[`loop-cli-dev classify` の「種別」列と意味がずれる]** → dev CLI の列は `Situation.Kind()` の
  ままなので、この change の後は TUI の進行中タブと dev CLI で同名の列が別の意味になる。
  dev CLI は分類の検証用（V-1）で人が一覧を捌く道具ではないので、揃えない
- **[異常タブに同じ扱いを広げると色が置けない]** → 異常タブの行は黄の背景で行全体を包んでいるので、
  その内側に段階の色を置くと行末まで背景が消える（`s33-colorful-labels` の design D6）。
  対象を進行中タブだけに絞ったのでこの change では起きないが、後から異常タブへ広げる提案が来たら
  そこで列の色を付けない扱いが要る

## 未決事項

`docs/mvp` と `docs/domain` が沈黙している点と、実装者が採る既定値。`proposal.md` の
人に問うた 3 件は PR #48 のコメントで決着したので（`proposal.md`「回答で確定した判断」）、
ここに残るのは実装者が選ぶ既定値だけである。

- **見出し行の書式**: 既定値は `── <owner/name> ── <n> 件 ` の後を端末の幅まで `─` で埋める。
  mvp.md の画面構成に表の中の区切りの例が無い
- **件数の単位**: 既定値は Card の枚数（折り返しで増えた行数ではない）。行数にすると同じカードでも
  端末の幅で件数が変わる
- **見出し行の色**: 既定値は色を付けない。罫線は画面の構造を示す記号で、色は段階ラベル名が担う
- **リポジトリの並び順**: 既定値は `Repo` の昇順。設定ファイルの `repos` の順に合わせる案もあるが、
  `internal/ui` に `repos` を渡すプラミングが増える（`Options` は今リポジトリの列を受け取っていない）
- **表の最終行が見出し行になる場合**: 既定値はそのまま出す（`cut` に任せる）。グループの行が 1 行も
  残らない見出しを落とす規則を足すほどの害が無い
- **`docs` ラベルの PR**: 既定値は `-`。`docs` は `model.PRStages` の段階順に入っておらず
  （`internal/model/model.go:198`）、段階ラベルではない
- **`stage:todo` の行**: 既定値は `todo` を出す。進行中の規則 4 / 5 は段階を問わないので
  `stage:todo` + `question` の issue が進行中タブに入り得る
