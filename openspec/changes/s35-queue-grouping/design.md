## Context

動機は `proposal.md` の Why にある。設計の前提になる現状は次の 5 点。

- **進行中タブに入る Card の分類結果は 1 種類しかない。** `result()` は `Priority` / `Tab` / `Kind` を
  すべて `Situation` から導く（`internal/classify/classify.go:18-20`、`internal/model/model.go:69-128`）。
  `Tab` が `進行中` になるのは `SituationInProgress` だけなので、このタブの行は `Priority` が 7、
  `Kind()` が `進行中` で固定される
- **`buildRows` はタブを問わず同じ 4 キーで並べている。** 第 1 キーが `Priority` なので、
  進行中タブでは第 1 キーが並びを決めず、実質「経過の新しい順 → リポジトリ → 番号」で並ぶ
  （`internal/ui/rows.go:84-96`）
- **表の描画は行の集合を平らに連ねている。** `tableLines` が `m.rows[m.tab]` を回して `tableRow` の
  返す行を連結し、`cut` が表の高さで切る（`internal/ui/view.go:203-214`）。行と行の間に何かを
  挟む仕組みは無い
- **カーソルは Card の並びの添字で、描画行の数と既に一致していない。** タイトルの折り返しで 1 枚の
  Card が複数行になるため、`m.cursor` が指すのは「何枚目の Card か」である
  （`internal/ui/view.go:216-262`）。`▶` は 1 枚の 1 行目にだけ付く
- **段階ラベルと運用方式はどちらも手元にある。** `model.IssueStages` / `model.PRStages` が段階順に返し
  （`internal/model/model.go:212-226`）、方式は `Model.modes` が持つ（`queue-screen`「運用方式は
  取得のたびに判定した結果を持つ」）。`row` は主体の `labels` を既に持っている（`internal/ui/rows.go:22`）

## Goals / Non-Goals

**Goals:**

- 進行中タブの行を、リポジトリと段階で目で追える形にする
- 「どの段階で AI が回っているか」を、主体が issue の行でも読めるようにする
- 列幅・高さの配分・キー操作・カーソルの意味を 1 つも変えない
- 他の 3 タブの見た目を 1 文字も変えない

**Non-Goals:**

- 表にスクロールを足すこと（`proposal.md` Q3 の選択肢 B）
- 今やるタブの並びを変えること（同 Q1）。優先度順の 1 本のキューは製品の中心にある
- 色の規則を新しく定義すること。ラベル名の色は `s33-colorful-labels` の規則を引く（D4）
- `Result.Summary`（「なぜ進行中か」の 8 通り）を表に出すこと（「未決事項」に既定値を書く）
- mvp.md がキーバインド表に置いた `v`（カンバンへのビュー切替）を実装すること。これは
  別の画面を足す話で、この change は今の表の中を区切るだけにする

## Decisions

### D1. 区切りは「リポジトリの見出し行 1 段」にし、段階は列で示す

issue #42 は「リポジトリごと、またステータスやラベルごとに分解して」と書いている。素直に読むと
リポジトリ → 段階の 2 段のグループになるが、**表の高さがそれを許さない**。表の高さは端末の残りの
約半分で、高さ 24 の端末では 11 行（`queue-screen`「キュー画面は端末サイズによらず表とプレビューを
2 ペインで出す」の按分）。3 リポジトリ × 3 段階なら見出しだけで 9 行を使い、カードがほぼ 1 枚も
見えなくなる。

そこで区切りは 1 段（リポジトリ）にし、段階は**既に情報の無い列**に出す。進行中タブの種別の列は
全行 `進行中` なので、そこを段階ラベル名に差し替えると新しい幅を要求せずに済む。並びの第 2 キーを
段階にすることで、同じ段階の行はリポジトリの中で隣り合って並ぶ。見出し行が無くても段階のまとまりは
読める。

### D2. 並びの第 1 キーをリポジトリにするのは進行中タブだけにする

`buildRows` の 4 キーをタブごとに分け、進行中タブだけ `Repo` → 段階 → `UpdatedAt` 降順 → 番号昇順に
する。進行中タブでは `Priority` が全行 7 なので、第 1 キーから外しても並びの意味が変わらない
（`proposal.md`「確定した判断」）。

手で組み立てた Card や将来の分類の変更で、進行中タブに `Priority` が 7 以外の Card が入る可能性は
残る。そのときこの並びは優先度を無視する。無視してよいと判断したのは、優先度が同じ局面から導かれる
値であり（`Situation.Priority()`）、タブと優先度が食い違う Card は `classify` が作らないためである。
この前提が崩れたら、進行中タブの第 1 キーを `Repo`、第 2 キーを `Priority` に直せば足りる。

他の 3 タブは 4 キーをそのまま残す。`rows_test.go` の既存の期待値（優先度順）は今やるタブで書かれて
いるので、進行中タブだけ分けるかぎり通る。

### D3. 見出し行は描画のときに挟み、`row` の列には入れない

見出し行を `m.rows[m.tab]` の要素にすると、カーソルの添字と選択の意味が壊れる（見出しを選べてしまう、
`j` 2 回で 2 枚目に届かない、プレビューの対象が無くなる）。`tableLines` が `m.rows[m.tab]` を回す間に
「1 つ前の行と `repo` が違えば見出し行を先に足す」だけにすれば、カーソル・プレビュー・
`a` / `t` / `m` / `c` / `o` / `u` の対象決定はどれも触らずに済む。

見出しを出すかどうかの判定（行があるリポジトリが 2 つ以上か）は、そのタブの行を 1 度なめて
`repo` の種類数を数えれば決まる。並びの第 1 キーが `Repo` なので、種類数は「前の行と違う `repo` の
出現回数」で求まる。

### D4. 色の規則は `s33-colorful-labels` から引き、この change では定義しない

段階ラベルの色として使える値は GitHub 側のラベル色で、`routines-setup` が作る実値は
`stage:todo` `fbca04` / `stage:propose` `0e8a16` / `stage:apply` `1d76db` / `stage:archive` `5319e7`
（`internal/gh/testdata/fixtures/example/labels.json`）。**この 4 色を文字色に使うと、暗い端末で
`archive` の紫がコントラスト比 2.6 になり WCAG AA（4.5）を割る**（黒に対する相対輝度 0.082 から計算）。
`fbca04` は逆に明るい端末で 1.6 になる。背景色に回して輝度から黒白の文字色を選べばどの色でも
4.5 以上になり、その規則は PR #37（`s33-colorful-labels`）が `queue-screen` の Requirement
「ラベル名は GitHub のラベル色を背景に、輝度で選んだ黒か白を文字にして描く」として既に定めている。

同じ規則をこの change でもう 1 本書くと、リポジトリの中に色の規則が 2 つ並ぶ（CLAUDE.md
「パターン競合は平均化しない」）。だから引く側に回り、**実装は `s33-colorful-labels` の archive を
前提にする**。`tasks.md` の 1 本目がその確認になる。PR #37 は既に `未確定の判断: 0 件` で
`ai-assess:requested` が付いており、この change より先に進んでいる。

`s33-colorful-labels` は自分の delta に「キューの表にラベル列は無い」「行全体に色を付ける描画の中には
色を置かない」と書いている。前者はこの change が進行中タブに段階の列を足すことで成り立たなくなるので、
この change の Requirement「進行中タブの段階ラベル名に色を付ける」がその前提を上書きすると spec に
明記した。後者は当たらない。進行中の行は `kindStyle` に項目が無く行全体の色を持たないので、外側の
スタイルが無く、内側のリセットで背景が落ちる問題（同 change の design D6）が起きない。

色を引く鍵は**接頭辞を落とす前のラベル名**にする。列に出すのは `archive` でも、issue に付いているのは
`stage:archive` であり、ラベル色の表はリポジトリのラベル一覧から作られるので `stage:archive` で
引かないと色が見つからない。

### D5. 列幅を動かさず、`label` 方式の `In Progress` は既存の切り詰めに任せる

種別の列は 10 列で、`colFixed`（48）と `colTitleStart`（43）が `queue-screen` の Scenario と
`internal/ui/view_test.go` の期待値に埋まっている。段階ラベル名のうち `propose`（7）/ `archive`（7）/
`apply`（5）/ `todo`（4）は収まり、`label` 方式の `In Progress`（11）だけが 1 列はみ出す。
`pad` が `ansi.Truncate(s, 10, "…")` で切るので `In Progr…` になる（`internal/ui/view.go:297-303`）。

`In Progress` のために列を 11 に広げると、タイトル列の開始位置が 43 → 44 に動き、折り返しの継続行の
字下げを見る Scenario とテストが全部ずれる。色と区切りの change でそこまで波及させる価値は無い。
`label` 方式は issue-label-driven のリポジトリ向けで、`In Progr…` でも段階は読める。

### D6. 見出し行の書式は `── <名前> ── <n> 件 ` + `─` の埋めにする

無地の `─` だけにすると、表とプレビューの間の区切り線（`internal/ui/view.go:72`）と見た目が同じに
なり、表の中の区切りなのかペインの境目なのか読めなくなる。名前を線の中に置けば、リポジトリ名が
そのまま見出しとして読める。件数を入れるのは、表の高さで切られてカードが見えないときでも
「このリポジトリに何枚あるか」が分かるようにするためである。

幅に収まらないときに `…` を付けないのは、切った跡が線の一部に見えるようにするため。`strings.Repeat`
に負の数を渡すと panic するので、埋める本数は `max(幅 − 見出しの表示幅, 0)` で求める。

## Risks / Trade-offs

- **[見出し行のぶんカードが表から溢れる]** → 表はスクロールを持たず `cut` が切り捨てる。リポジトリが
  1 つだけなら見出しを出さないので単一リポジトリの利用者は 1 行も失わないが、3 リポジトリなら
  高さ 24 の端末で 11 行のうち 3 行を見出しが使う。`proposal.md` Q3 で人に問い、許す方を推奨している
- **[選択行が表の外に出ていても追従しない現状が悪化する]** → 今も折り返しで増えた行に押し出されて
  選択行が見えなくなることがあり（`queue-screen`「1 枚の Card の途中の行までしか表示されないことが
  ある」）、見出し行はその確率を上げる。選択行への追従（スクロール）を足すのは Q3 の選択肢 B で、
  推奨していない
- **[進行中タブの並びが優先度を無視する]** → D2 のとおり、このタブでは優先度が全行同じなので今は
  影響が無い。将来 `Situation.Priority()` が進行中を複数の値に分けたら、第 2 キーに優先度を戻す
- **[`s33-colorful-labels` が却下・大幅変更されると、色の規則の引き先が消える]** → `proposal.md` Q2 の
  選択肢 B（固定 4 色を文字色）に切り替えられる。spec で色を付ける対象（種別の列の段階ラベル名）と
  付けない対象（`-`・列の余白）は規則の出どころと独立に書いてあるので、書き換えるのは 1 文になる
- **[段階ラベル名が「なぜ進行中か」を完全には表さない]** → `stage:apply` + `wip` の issue と、
  同じ issue の `apply` PR が `auto-fix が受け取り中` の状態は、どちらも列に `apply` と出る。
  分類が持つ 8 通りの区別（`Result.Summary`）はこの列では復元できない。「未決事項」に既定値を書く
- **[異常タブに同じ扱いを広げると色が置けない]** → 異常タブの行は黄の背景で行全体を包んでいるので、
  その内側に段階の色を置くと行末まで背景が消える（`s33-colorful-labels` の design D6）。Q1 の
  選択肢 C を採る場合、異常タブでは段階の色を付けない扱いが要る

## 未決事項

`docs/mvp` と `docs/domain` が沈黙している点と、実装者が採る既定値。`proposal.md` の
「未確定の判断」に残した 3 件は人の判断を待つもので、ここには含めない。

- **見出し行の書式**: 既定値は `── <owner/name> ── <n> 件 ` の後を端末の幅まで `─` で埋める。
  mvp.md の画面構成に表の中の区切りの例が無い
- **件数の単位**: 既定値は Card の枚数（折り返しで増えた行数ではない）。行数にすると同じカードでも
  端末の幅で件数が変わる
- **見出し行の色**: 既定値は色を付けない。罫線は画面の構造を示す記号で、色は段階ラベル名が担う
- **見出し行を出す下限**: 既定値は「行があるリポジトリが 2 つ以上」。1 つのときに出すと、区切る相手が
  無いまま表の高さを 1 行使う
- **リポジトリの並び順**: 既定値は `Repo` の昇順。設定ファイルの `repos` の順に合わせる案もあるが、
  `internal/ui` に `repos` を渡すプラミングが増える（`Options` は今リポジトリの列を受け取っていない）
- **`Result.Summary` を表に出すか**: 既定値は出さない。表の幅に余りが無く、タイトルの列を削ると
  「タイトルを全文出す」（`queue-screen`）と衝突する。プレビューに出す案は、プレビューが選択行しか
  見せないので一覧の読みやすさには効かない
- **段階ラベルが 2 つ以上ある主体の列**: 既定値は段階順で最初の 1 つ。段階が 2 つ以上なら局面 F で
  異常タブに入るので、進行中タブでは起きない
- **`docs` ラベルの PR**: 既定値は `-`。`docs` は `model.PRStages` の段階順に入っておらず
  （`internal/model/model.go:196`）、段階ラベルではない
