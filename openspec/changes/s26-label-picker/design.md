## Context

`internal/ui` の `Model` は画面の状態を 6 つ（キュー / カード詳細 / PR 詳細 / 確認 / ヘルプ / URL 一覧）持ち、`Update` が状態ごとにキーを振り分け、`View` が状態ごとに全画面を描く（`internal/ui/detail.go:22-30`、`view.go:48-60`）。重ね合わせのオーバーレイは 1 つも無い。

ラベルを書く経路は `t` だけで、`internal/action/todo.go` の `ToggleTodo` が `ViewIssue` で現在のラベルを読み直してから `AddLabel` / `RemoveLabel` を 1 ラベルずつ呼ぶ。書き込みの直前に読み直すのは、画面の Card のラベルが最終取得時点のもので、続けて 2 回押した 2 回目が「もう一度付ける」になるのを防ぐためである。

`GHClient`（`internal/gh/gh.go:12-31`）は 17 メソッドで、`Client` が `gh` サブプロセス、`Fake` が fixture ディレクトリを読む。後続 change がメソッドを足すときは interface・`Client`・`Fake` を同時に拡張する（`gh-client` spec「`GHClient` interface が読み取りと書き込みのメソッドを定義する」）。

ラベルという語がこのプロジェクトで持つ重みは大きい。`docs/domain/issue-driven-sdd/human-turn-signals.md` の不変条件 2 は TUI が書けるラベルを 2 つに限っており、この change はそれを広げる提案である。何をどこまで広げるかは proposal.md の未確定の判断 Q1 で人に問うている。

## Goals / Non-Goals

**Goals:**

- 画面を離れずに、対象（issue でも PR でも）のラベルを 1 つトグルできる
- ラベルの種類が増えてもキーは 1 つのまま
- 何が付いていて何を付けられるかが一覧で分かる
- 誤って routine の状態機械を回さない（Q1 の結論に従う）

**Non-Goals:**

- ラベルの新規作成・削除・色や説明の編集（`gh label create` / `edit` / `delete` の経路は持たない）
- 利用者が複数のラベルを一度にトグルする操作（不変条件 1「1 操作 1 ラベル」に反する）
- ラベルで一覧を絞り込む機能（`/` の絞り込みは s19 の担当）
- 書き込み後の対象 1 件だけの再取得（P2 の別項目。反映は `R` / 自動更新に任せる）

## Decisions

### D-1: ラベル一覧は 7 つ目の画面の状態として全画面で描く

`Model` の画面の状態にラベル一覧を足し、`View` は端末の幅と高さ全体を使って描く。依頼の言葉は「モーダル（画面）」だが、s22 が URL 一覧で同じ判断（design.md D-1）をしており、確認画面もヘルプ画面も全画面である。重ね合わせを入れると背面の描画結果に対する切り出しと合成の規則を新しく決めることになり、`View` の分岐が 1 つ増えるだけの全画面より複雑になる。

一覧の見た目は URL 一覧に合わせる。見出し `ラベルを付け外し` / 空行 / ラベルの行 / 残りは空行 / フッタ。1 行は `<選択の印><付いている印> <名前>  <説明>`。スクロール位置は持たず、選択位置から表示開始位置を決める（`renderURLs` と同じ）。

`gh label list` は色（`color`）も返すが、一覧では使わない。ラベル名に色を付けると、`kindStyle`（種別の色。`view.go:27-33`）と意味の違う色が同じ画面に並ぶ。色の利用は明示的に見送る。

### D-2: 一覧の分岐は `a` / `t` / `m` / `o` / `?` より前に置く

`Update` のキー振り分けで、ラベル一覧画面の分岐を URL 一覧の直後（`a` / `t` / `m` / `o` / `?` の判定より前）に置き、`l` のハンドラをその後ろに置く。後ろに置くと、一覧を出している間の `t` が「画面はキュー」と見なして裏の対象へ書き込む。`l` のハンドラを一覧の分岐より前に置くと、一覧を出したまま `l` を押したときに戻り先が一覧自身に上書きされて `Esc` が効かなくなる（s22 design.md D-2 と同じ）。

一覧画面で扱うキーは `j` / `k` / `↑` / `↓`（選択）、`Enter`（トグル）、`Esc`（戻る）、`q` / `Ctrl+C`（終了）だけ。戻り先がカード詳細 / PR 詳細のときは、戻るときに本文領域を作り直す（一覧を出している間の端末サイズ変更が詳細に反映されないため。s12 / s22 と同じ）。

### D-3: ラベル一覧の取得は `l` を押したときに 1 リポジトリ 1 回だけ行う

`GHClient` に `ListLabels(ctx, repo) ([]Label, error)` を足す。`Client` は `gh label list --repo <repo> --json name,description,color --limit 100` を実行する。

`Model` は `map[string][]gh.Label` をリポジトリ名で持つ。`l` を押したとき、対象のリポジトリの一覧を持っていればコマンドを返さずその場で画面を開く。持っていなければ取得のコマンドを返し、フッタに `<repo> のラベル一覧を取得中` を出し、結果が届いた時点で画面を開く。取得に失敗したら画面を変えず、フッタに赤で `<repo> のラベル一覧を取得できません: <エラー>` を出す。

**なぜ起動時に先読みしないか。** 起動時の取得はリポジトリの数だけ `gh` を増やし、`l` を一度も押さない利用者にも払わせる。D-001 が定めた 1 更新あたりの呼び出し回数（`2 + N + 3M`）を変えないためにも、`l` を押したときの遅延取得にする。

**なぜ捨てないか。** ラベルの集合はセッション中にまず変わらない。`R` でも自動更新でも捨てず、プロセスが終わるまで保持する。ラベルを新しく作った直後に `l` を押しても出ないが、そのときは loop-cli を起動し直せばよい。この割り切りは s23 の「更新の確認は起動につき 1 度だけ。版はセッション中にまず変わらない」と同じ考え方である。

### D-4: 取得中とトグル中はどちらも「書き込み中」として扱う

`m.writing` を立てる場面を、ラベル一覧の取得中とトグル中の両方に広げる。s14 が「`m` が押されてから merge の判断材料を取り直している間（まだ書き込んでいない）」を書き込み中に含めたのと同じで、手続きを重ねて始めさせないためである。一覧を開いている間（取得が終わり、まだ `Enter` を押していない間）は書き込み中ではない。

### D-5: トグルは書き込み直前に対象を読み直して決める

`internal/action` に、対象 1 件のラベル 1 つをトグルする関数を足す。対象が issue なら `ViewIssue`、PR なら `ViewPR` で現在のラベルを読み直し、付いていれば `RemoveLabel`、無ければ `AddLabel` を呼ぶ。戻り値は `ToggleTodo` と同じく「付けたか（`added`）」とエラー。

`AddLabel` / `RemoveLabel` は `gh issue edit` を実行するが、PR 番号でも動く。`gh` の `issue edit` は `issueOrPullRequest(number:)` で対象を解決し、`UpdateIssue` に `issue.IsPullRequest()` を渡している（cli/cli `pkg/cmd/issue/shared/lookup.go` の `FindIssueOrPR`、`pkg/cmd/issue/edit/edit.go:360,494`）。PR 用のメソッドを新設しない。

**`ToggleTodo` と 1 本にまとめない。** `ToggleTodo` は `stage:todo` 固有の拒否（`ErrOtherStage` / `ErrMultipleStages` / `ErrBlocked`）を持ち、対象が issue に限られる。汎用のトグルにこの判定を持ち込むと、`stage:todo` 以外のラベルにも段階ラベルの検査が走る。2 つの関数を隣に置き、`t` は `ToggleTodo` を、`l` は新しい関数を呼ぶ。

### D-6: 一覧の「付いている」印は画面の Card のラベルで出す

対象に今付いているラベルは、`Card.Issue.Labels` / `PR.Labels`（最終取得時点）から取る。`l` を押した時点で GitHub に問い合わせると、依頼が避けたがっている「`l` の反応が鈍い」に戻る。印が古くなり得るのは受け入れる。実際に付けるか外すかは D-5 の読み直しで決まるので、印が古くても操作の結果は正しい。

### D-7: 対象の決め方は `a` / `u` と同じにする

キュー画面は選択行の主体（`subjectOf`）、カード詳細は `Card.Issue`、PR 詳細は選択中の PR。`t` の「対象は常に Issue」は `stage:todo` が issue のラベルだからで、`l` は PR にも付けたいので `a` / `u` の規則を採る。選択行が無ければ何もしない。確認画面・merge 確認画面・ヘルプ画面・URL 一覧では `l` は届かない（それぞれの分岐が先に処理する）。

## Risks / Trade-offs

- **routine の状態機械を人が回してしまう危険。** これがこの change の最大のリスクで、proposal.md の Q1 で人に問うている。選択肢 C（全部トグルできる）を採ると、`stage:apply` を誤って付けたときに worker が 1 本起動し、段階ラベルが 2 つある issue（局面 F）を人が手で直すことになる。TUI 側で取り消せない副作用である
- **`gh label list` の 100 件の上限。** `--limit 100` を超えるラベルを持つリポジトリでは一覧が途切れる。ページングは実装しない（このプロジェクトが対象とする issue-driven-sdd のリポジトリのラベルは十数件）。上限に当たっているかを画面に出す仕組みも持たない
- **キャッシュが古くなる。** D-3 のとおりセッション中は捨てないので、他の経路でラベルを新しく作っても `l` には出ない。起動し直しでしか直らない
- **印の古さ。** D-6 のとおり、最終取得の後に他の経路でラベルが変わっていると、印と実際がずれる。`Enter` を押した結果（付けた / 外した）はフッタに出るので、ずれていたことはその場で分かる
- **`h` を落とすかどうか（Q2 の選択肢 A）。** カンバンの列移動から `h` / `l` を落とすと、vim 風の移動に慣れた利用者が s17 の実装後に戸惑う可能性がある。`j` / `k` は行移動として既に動いているので、`h` / `l` だけが無いのは一貫していない
