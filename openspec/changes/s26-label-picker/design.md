## Context

`internal/ui` の `Model` は画面の状態を 7 つ（キュー / カード詳細 / PR 詳細 / 確認 / ヘルプ / URL 一覧 / merge 確認）持ち（`internal/ui/detail.go:22-30`）、`Update` が状態ごとにキーを振り分け、`View` が状態ごとに全画面を描く（`view.go:48-60`）。重ね合わせのオーバーレイは 1 つも無い。

ラベルを書く経路は `t` だけで、`internal/action/todo.go` の `ToggleTodo` が `ViewIssue` で現在のラベルを読み直してから `AddLabel` / `RemoveLabel` を 1 ラベルずつ呼ぶ。書き込みの直前に読み直すのは、画面の Card のラベルが最終取得時点のもので、続けて 2 回押した 2 回目が「もう一度付ける」になるのを防ぐためである。書き先の表現は `action.Target{Repo, Number, IsPR}`（`action.go:29-33`）で、`Comment` はこれ 1 つで issue / PR を書き分けている。

`GHClient`（`internal/gh/gh.go:12-31`）は 17 メソッドで、`Client` が `gh` サブプロセス、`Fake` が fixture ディレクトリを読む。後続 change がメソッドを足すときは interface・`Client`・`Fake` を同時に拡張する（`gh-client` spec「`GHClient` interface が読み取りと書き込みのメソッドを定義する」）。`Fake` は「ディレクトリ 1 つ = リポジトリ 1 件」で `repo` 引数をファイル探索に使わない（`fake.go:50-51`）。

ラベルという語がこのプロジェクトで持つ重みは大きい。`docs/domain/issue-driven-sdd/human-turn-signals.md` は不変条件 2 と冒頭の `ai-assess:requested` の一文で TUI が書けるラベルを絞っており、この change はそれを広げる提案である。何をどこまで広げるかは proposal.md の未確定の判断 Q1 で人に問うている。

## Goals / Non-Goals

**Goals:**

- 画面を離れずに、対象（issue でも PR でも）のラベルを 1 つトグルできる
- ラベルの種類が増えてもキーは 1 つのまま
- 何が付いていて何を触れるかが一覧で分かる
- 誤って routine の状態機械を回さない、loop-cli 自身の merge ガードを外側から無効化しない（Q1 の結論に従う）

**Non-Goals:**

- ラベルの新規作成・削除・色や説明の編集（`gh label create` / `edit` / `delete` の経路は持たない）
- 利用者が複数のラベルを一度にトグルする操作（不変条件 1「1 操作 1 ラベル」に反する）
- ラベルで一覧を絞り込む機能（`/` の絞り込みは s19 の担当）
- 書き込み後の対象 1 件だけの再取得（P2 の別項目。反映は `R` / 自動更新に任せる）
- 100 件を超えるラベルのページング

## Decisions

### D-1: ラベル一覧は 8 つ目の画面の状態として全画面で描く

`Model` の画面の状態にラベル一覧を足し、`View` は端末の幅と高さ全体を使って描く。s22 が URL 一覧で同じ判断（design.md D-1）をしており、確認画面も merge 確認画面もヘルプ画面も全画面である。重ね合わせを入れると背面の描画結果に対する切り出しと合成の規則を新しく決めることになり、`View` の分岐が 1 つ増えるだけの全画面より複雑になる。

一覧の見た目は URL 一覧に合わせる。見出し `ラベルを付け外し` / 空行 / ラベルの行 / 残りは空行 / フッタ。1 行は `<選択の印><状態の印> <名前>  <説明>` で、状態の印は「付いている」「付いていない」「触れない」の 3 種。スクロール位置は持たず、選択位置から表示開始位置を決める（`renderURLs` と同じ）。

`gh label list` は色（`color`）も返すが、一覧では使わない。ラベル名に色を付けると、`kindStyle`（種別の色。`view.go:27-33`）と意味の違う色が同じ画面に並ぶ。色の利用は明示的に見送る。

並び順は `gh` 任せにしない。`gh label list` の既定は作成順（cli/cli `pkg/cmd/label/http.go` の `defaultSort = "created"`）で、リポジトリごとに並びが変わり fixture も画面も非決定になる。`--sort name --order asc` を渡して名前の昇順に固定する。

### D-2: 一覧の分岐は `a` / `t` / `m` / `o` / `?` より前に置く

`Update` のキー振り分けで、ラベル一覧画面の分岐を URL 一覧の直後（`a` / `t` / `m` / `o` / `?` の判定より前）に置き、`l` のハンドラをその後ろに置く。後ろに置くと、一覧を出している間の `t` が「画面はキュー」と見なして裏の対象へ書き込む。`l` のハンドラを一覧の分岐より前に置くと、一覧を出したまま `l` を押したときに戻り先が一覧自身に上書きされて `Esc` が効かなくなる（s22 design.md D-2 と同じ）。

一覧画面で扱うキーは `j` / `k` / `↑` / `↓`（選択）、`Enter`（トグル）、`Esc`（戻る）、`q` / `Ctrl+C`（終了）だけ。戻り先がカード詳細 / PR 詳細のときは、戻るときに本文領域を作り直す（一覧を出している間の端末サイズ変更が詳細に反映されないため。s12 / s22 と同じ）。

### D-3: 対象は `l` を押した時点で `action.Target` に写し取る

`l` を押した時点で対象の `{Repo, Number, IsPR}` と戻り先の画面を状態に写し取り、`Enter` のときはその写しを使う。`Cards` から引き直さない。

理由は自動更新である。`refresh.go:20-25` の自動更新は `fetching || writing` だけを見て画面を見ないので、一覧を出している間（`writing` は立っていない。D-5）にも走る。`fetchedMsg` は `m.cards` / `m.rows` を差し替えて `clampCursor()` する（`model.go:164-189`）ので、`Enter` の時点で `m.rows[m.tab][m.cursor]` を読むと、選択行が別の issue に入れ替わっていてもそれに気づかずラベルを書く。s14 の `mergeState` が同じ理由で押した時点の repo / number をコピーしている（`merge.go:22-31`）。

### D-4: ラベル一覧の取得は `l` を押したときに 1 リポジトリ 1 回だけ行う

`GHClient` に `ListLabels(ctx, repo) ([]Label, error)` を足す。`Client` は `gh label list -R <repo> --json name,description,color --sort name --order asc --limit 100` を実行する。

`Model` は `map[string][]gh.Label` をリポジトリ名（`action.Target.Repo`。D-3 で写し取ったもの）で持つ。経路は 2 つに分かれ、仕様とテストもこの 2 つに分ける。

- **キャッシュに有る**: コマンドを返さず、その場で一覧画面に移る。`writing` は立たない
- **キャッシュに無い**: 取得のコマンドを返し、`writing` を立て、フッタに `<repo> のラベル一覧を取得中` を出す。結果が届いたら `writing` を下ろし、D-6 の判定を通してから一覧画面に移る。取得に失敗したら画面を変えず、フッタに赤で `<repo> のラベル一覧を取得できません: <エラー>` を出す

**なぜ起動時に先読みしないか。** 起動時の取得はリポジトリの数だけ `gh` を増やし、`l` を一度も押さない利用者にも払わせる。D-001 が定めた 1 更新あたりの呼び出し回数（`2 + N + 3M`）を変えないためにも、`l` を押したときの遅延取得にする。

**なぜ捨てないか。** ラベルの集合はセッション中にまず変わらない。`R` でも自動更新でも捨てず、プロセスが終わるまで保持する。ラベルを新しく作った直後に `l` を押しても出ないが、そのときは loop-cli を起動し直せばよい。この割り切りは s23 の「更新の確認は起動につき 1 度だけ。版はセッション中にまず変わらない」と同じ考え方である。同じ理由で、`--limit 100` を超えるリポジトリでは一覧が 100 件で切れることも画面には出さない（切れているかを知るには 101 件目を取りに行くしかなく、`l` の反応を鈍らせる）。上限と「新しいラベルは起動し直すまで出ない」ことは `label-picker` の spec に明記する。

**`Fake` での検証。** `Fake` は `repo` 引数を無視するので「リポジトリごとに別の集合を持つ」は fixture では確かめられない。代わりに `Fake.ListLabels` の呼び出しを `Calls` に記録し、「同じリポジトリで `l` を 2 回押しても `Calls` の `ListLabels` は 1 件」で 2 回目に `gh` を呼ばないことを検証する。記録しないと D-4 の主要な主張がテスト不能なまま残る。

### D-5: 取得中とトグル中は「書き込み中」、一覧を出している間は違う

`m.writing` を立てる場面を、ラベル一覧の取得中とトグル中の両方に広げる。s14 が「`m` が押されてから merge の判断材料を取り直している間（まだ書き込んでいない）」を書き込み中に含めたのと同じで、手続きを重ねて始めさせないためである。一覧を開いている間（取得が終わり、まだ `Enter` を押していない間）は書き込み中ではない。したがって一覧を出している間も自動更新は走り、D-3 の写し取りが必要になる。

### D-6: 取得の間に画面が変わっていたら一覧を開かない

取得のコマンドを返した時点の画面を保持し、結果が届いたときの画面がそれと違えば、一覧画面に移らずフッタに `<repo> のラベル一覧の表示を中止しました（画面が変わりました）` を出す。

`m.writing` は書き込み系のキーだけを止め、`o` / `?` / `u` / `Esc` / `Enter` などの画面移動は通す（`openspec/specs/merge-pr/spec.md:106`）。この規則が無いと、取得中に `?` を押して開いたヘルプ画面や `u` で開いた URL 一覧を、あとから届いたラベル一覧が踏み潰す。s14 が merge の取り直しに対して同じ規則を持っており（同 spec:38、`merge.go:124-131`）、そこに揃える。

### D-7: トグルは `action.Target` を受け取り、書き込み直前に読み直して決める

`internal/action` に、`Target` とラベル名 1 つを受け取ってトグルする関数を足す。`Target.IsPR` で読み直しの経路（`ViewPR` / `ViewIssue`）と書き込みの経路（`AddLabelPR` / `RemoveLabelPR` と `AddLabel` / `RemoveLabel`）を選ぶ。戻り値は `ToggleTodo` と同じく「付けたか（`added`）」とエラー。触れないラベル（Q1 の結論）を渡されたら、`gh` を呼ばずにエラーを返す。

`Target` を使うのは、`internal/action` に 2 つ目の「対象の表し方」を作らないためである（`Comment` が既に `Target` で書き分けている。`action.go:52-56`）。

**`ToggleTodo` と 1 本にまとめない。** `ToggleTodo` は `stage:todo` 固有の拒否（`ErrOtherStage` / `ErrMultipleStages` / `ErrBlocked`）を持ち、対象が issue に限られる。汎用のトグルにこの判定を持ち込むと、`stage:todo` 以外のラベルにも段階ラベルの検査が走る。2 つの関数を隣に置き、`t` は `ToggleTodo` を、`l` は新しい関数を呼ぶ。

**PR へのラベル書き込みは `gh pr edit`。** proposal.md の確定した判断のとおり、`gh issue edit` が PR を受ける文書化されていない挙動には依存しない。`Client.AddLabelPR` / `RemoveLabelPR` は `gh pr edit <n> -R <repo> --add-label <l>` / `--remove-label <l>` を実行する。

### D-8: 一覧の印は画面の Card のラベルから作り、トグルの結果で上書きする

対象に今付いているラベルは、`Card.Issue.Labels` / `PR.Labels`（最終取得時点）から取る。`l` を押した時点で GitHub に問い合わせると、依頼が避けたがっている「`l` の反応が鈍い」に戻る。

ただし「印は古くなり得る」を全面的な割り切りにはしない。トグルに成功したら、その 1 件の印だけを結果（`added`）で書き換える。`Cards` は書き換えないので（`t` と同じ）、印だけがその場で正しくなる。これをしないと、Q4 で「一覧を残す」を選んだとき、付けたのに印が変わらないのを見た利用者がもう一度 `Enter` を押して外してしまう。

### D-9: 対象の決め方は `a` / `u` と同じにする

キュー画面は選択行の主体（`subjectOf`。`rows.go:25-37`）、カード詳細は `Card.Issue`、PR 詳細は選択中の PR。`t` の「対象は常に Issue」は `stage:todo` が issue のラベルだからで、`l` は PR にも付けたいので `a` / `u` の規則を採る。選択行が無ければ何もしない。確認画面・merge 確認画面・ヘルプ画面・URL 一覧では `l` は届かない（それぞれの分岐が先に処理する）。

リポジトリ名は `subjectOf` が返した `Issue.Repo` / `PR.Repo` を正とする（`row.repo` は表示用に `Subject` が同じ値から作っているので一致する）。

## Risks / Trade-offs

- **routine の状態機械と merge ガードを人が崩す危険。** これがこの change の最大のリスクで、proposal.md の Q1 で人に問うている。選択肢 C（全部トグルできる）を採ると、`stage:apply` を誤って付けたときに worker が 1 本起動し、`question` を外すと AI 評価前の PR を merge できる。どちらも TUI 側では取り消せない
- **`gh label list` の 100 件の上限。** `--limit 100` を超えるラベルを持つリポジトリでは一覧が途切れ、しかも切れていることを画面に出さない（D-4）。このプロジェクトが対象とする issue-driven-sdd のリポジトリのラベルは十数件なので当面は当たらない
- **キャッシュが古くなる。** D-4 のとおりセッション中は捨てないので、他の経路でラベルを新しく作っても `l` には出ない。起動し直しでしか直らない
- **取得中の `R` がステータスを消す。** `R` は `m.fetching` だけを見るので取得中でも押せ、`startFetch` が `writeStatus` を消す（`model.go:140`）。`<repo> のラベル一覧を取得中` が黙って消える。`t` / `m` のステータスも同じ扱いなので、この change で変えない
- **印の古さ。** D-8 で自分がトグルしたラベルは直るが、最終取得の後に他の経路で変わったラベルの印はずれたままである。とくに詳細の取得に失敗した PR の `Labels` は search 時点のもの（`model.go:230`）で、ずれが大きい
- **`h` を落とすかどうか（Q3）。** カンバンの列移動から `l` を落とすと、vim 風の左右移動が片側だけ残る。`h` も落とすと不揃いは消えるが、`h` を落とす理由は `l` の衝突と無関係である
- **fixture のラベルの説明文。** s04 の伏せ字は全ファイル一括のテキスト置換で、login 表はコメントの `"login"` 値と `@mention` から作る。ラベルの `description` に表に無い人名や組織名が書かれていれば残り得る。これは既存の issue / PR 本文と同じ性質の残余リスクで、`labels.json` を足したことで新しく生まれるものではない
