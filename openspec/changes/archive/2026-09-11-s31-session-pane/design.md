## Context

動機は proposal.md の「Why」を見る。設計を縛る現状は 4 つある。

- `internal/ui` の `Model` は `Update` でキーを画面の状態ごとに振り分け、外部プロセスの実行は必ずコマンド（別ゴルーチン）で行う（`internal/ui/model.go:241`）。`R` は今キュー画面の分岐にしか無く、詳細画面のキーを扱う `updateDetailKey` は `tea.Cmd` を返せない形（`internal/ui/model.go:313`）
- 詳細画面は本文領域を viewport の幅に端末幅そのものを渡している（`internal/ui/detail.go:134`）。`renderDetail` は ヘッダ / 区切り線 / 本文 / フッタ を縦に連ねるだけで、横の分割を持たない（`internal/ui/view.go:79`）
- 外部コマンドの起動は `internal/gh/client.go:40` の 1 つの形（`exec.CommandContext` + `Stdout` / `Stderr` のバッファ + `ctx` を先に見るエラー分け + テスト用に差し替えられる `run` フィールド）で書かれている。`internal/claude` もこの形に合わせる
- 取得 1 回がプロファイルの利用枠を使う。回数を抑えることが設計の目的の 1 つで、キャッシュと同時実行の抑制はどちらも利用枠の節約のために置く

## Goals / Non-Goals

**Goals:**

- 詳細画面を開いている人が、`claude.ai` を開かずにセッションの生死と直近の動きを読める
- `claude` を起動する場所がコードの 1 か所に限られ、起動の回数が画面の操作から予測できる
- `claude` が無い・プロファイルが違う・利用上限に達した、のどれが起きても左ペインと他のキーが動き続ける

**Non-Goals:**

- セッションへの書き込み（返信・承認・中断）はしない。読むだけにする
- キュー画面にセッションの状態を出さない（`[3]進行中` タブの行も変えない）
- 右ペインのスクロールと選択を作らない。読むのは最新の十数行だけである
- 取得結果を `snapshot-cache` に混ぜない。プロセスを終えたら捨てる

## Decisions

### D1. `internal/claude` は `get_run_log` だけを実装する

issue #18 は `list` / `list_runs` / `get_run_log` の 3 つのプロンプトを記録しているが、右ペインに出すものはログの最新行から作れる（`session-pane`「右ペインは紐づくセッションの稼働状況を出す」）。誰も呼ばないコードを置かない（CLAUDE.md「投機的な機能・将来の拡張に備えたコードは書かない」）。

代案として `list` → `list_runs` → `get_run_log` の 3 回を呼ぶ形を検討した。`list_runs` の `worker_status` があれば `requires_action`（入力待ち）を出せるが、1 回の取得が 約 15 秒 / $0.045 になる。人はこの代案を退け、1 回だけ起動する形を選んだ（PR #31 のレビューコメント 2026-09-11T06:47:10Z）。`requires_action` と `archived` を区別できないことは受け入れる。

### D2. 取得は詳細を開いたときとその画面の `R` だけで起きる

`Update` の `R` の分岐を、キュー画面の前に「画面がカード詳細 / PR 詳細なら `o` / `?` と同じ位置でセッション取得のコマンドを返す」形で足す（`updateDetailKey` は `tea.Cmd` を返せないので、そこには置かない）。開いたときの取得は `openDetail` と、詳細から詳細へ移る `updateDetailKey` の `enter` / `g` の枝から、画面の状態が決まった後に判定する。

同じセッションを 2 回取得しないために、取得結果を `map[セッション ID]結果` で持つ。`Esc` や `g` での行き来、ヘルプ / URL 一覧 / ラベル一覧から戻ったときは、この表に当たるので `claude` を起動しない。人はこの「持っていなければ取る」を選び、毎回取得と時間での期限切れを退けた（PR #31 のレビューコメント 2026-09-11T06:47:10Z）。

### D3. 右ペインは幅 40 固定、境目は端末幅 120

右ペインを 40 列にすると、`tool_use` の行が `12:03 tool_use Bash: git pu…` まで読める。左ペインには 79 列が残り、既存の Scenario が使う幅 100 の 1 ペインより広い。比率（例: 3 割）で割ると、幅 120 で右が 36 列、幅 200 で 60 列になり、右ペインに出す内容が増えないのに幅だけ増える。

境目を 120 にしたのは、既存の Scenario が使う幅（40 / 60 / 100 / 130 / 150）のうち 100 以下を 1 ペインのまま保ち、130 と 150 を 2 ペインにするためである。フッタは 2 ペインでも 1 行のまま端末幅の全体を使う（ヒントとステータスは画面に 1 組しか無い）。

### D4. `R` のヒントをフッタに足さない

カード詳細のフッタのヒントは既に 144 列で、幅 80 の端末では末尾が切れている（`card-detail`）。`R 取得` を足すと切れる位置が前に動くだけなので、案内はヘルプ画面の `R` の行に置く（`help-screen` の MODIFIED）。

### D5. セッション URL は `u` の一覧に足す

issue #18 は「`o` で開けるようにする」と書いているが、`o` は画面の対象をブラウザで開くキーとして `browse-open` が定めている。`u` の一覧に出典 `session` の 1 件を先頭に置けば、既存のキーの意味を変えず、キーも増えない（`url-picker` の MODIFIED）。人はこの形を選び、`o` の意味を変える案と専用のキーを足す案を退けた（PR #31 のレビューコメント 2026-09-11T06:47:10Z）。

### D6. 利用上限はプロセスが動いている間ブロックする

`claude` が返す `resets Sep 14 at 2am (Asia/Tokyo)` は年を持たない表示用の書式で、時刻として解釈すると年をまたぐときに壊れる。文字列のまま右ペインに出し、そのプロファイルの取得はプロセスが動いている間止める。週の上限は日をまたいで解けるので、人はその間に loop-cli を再起動する。

### D7. fixture は手書きし、`fixture capture` の経路は作らない

`cmd/loop-cli-dev fixture capture` は `gh` の標準出力を採って伏せ字にする仕組みで、`--alias` でリポジトリ名を伏せる（`cmd/loop-cli-dev/fixture.go:87`）。`claude -p` の出力は採取のたびに利用枠を使い、伏せる対象も違う（セッション ID・リポジトリ名・ログ本文）。`internal/gh/testdata/fixtures/example` と同じ手書きの fixture を `internal/claude/testdata` に置き、issue #18 に記録された形式を写す。

## Risks / Trade-offs

- **手書きの fixture が実際の stream-json とずれていれば、パースが外れる** → ずれは右ペインの「取得の状態」に出るので画面が壊れることはない。`tool_result` を探す条件と `HTTP <status>` の判定は形式の変化に鈍い形で書き（`type` と `content[].type` だけを見る）、ログの行は形式外の行を捨てる
- **`SugiKent/loop-cli` の Routine のプロファイルが未検証（proposal.md の「確定した判断」）** → プロファイルが違えば右ペインに `HTTP 404 プロファイルが違う可能性があります` が出る。設定を直す手掛かりは画面にある
- **`claude` の起動オプションとプロンプトは Claude Code 2.1.267 で確認したもので、将来の版で変わりうる** → 変わったときは `tool_result` が見つからず「起動の失敗」として標準出力の先頭が右ペインに出る。エラーを握り潰さない形にしておく
- **モデルにプロンプトを投げる以上、応答が `RemoteTrigger` を呼ばずに終わる可能性が残る** → その場合も `tool_result` が無いので起動の失敗として扱う。`--max-budget-usd 0.05` が暴走を止める
- **右ペインぶん左ペインが狭くなる** → 幅 120 未満では右ペインを出さないので、既定幅 80 の端末では今までと同じ表示になる

## 未決事項

issue #18 と既存の spec が沈黙している点を列挙する。括弧内が実装者が採る既定値で、spec はこの値で書いてある。`docs/mvp` はこれ以降更新しないので（CLAUDE.md）、ここで決めた既定値は `openspec/specs/` だけに残る。

1. 右ペインの幅と境目（右ペインは表示幅 40 列固定、境目は端末幅 120。D3）
2. 「直近の動き」に出すログの行数（最も新しい 12 行。幅 40・高さ 40 の右ペインに、見出しと状態の行を出したうえで収まる行数）
3. 状態の語（`実行中` / `起動中` / `終了` / `不明`。ログの行の種類から決める。D1）
4. ペインの縦の区切り（1 列の縦線。横の区切り線が左ペインの幅で 1 本引かれているのと同じ文字の系統にそろえる）
5. 右ペインの「最終更新」の経過の基準（取得時刻。キュー画面の経過が最後の取得完了時刻を基準にするのと同じ考え方）
6. `claude_config_dir` のグローバル既定値（持たない。書き忘れたリポジトリで意図しないプロファイルの利用枠を使わないため。`config-loading` の ADDED）
7. 取得の打ち切り（30 秒。issue #18 が定めた値で、実測の約 6 倍）

## Migration Plan

設定ファイルの互換は保たれる。`claude_config_dir` は省略でき、省略したリポジトリでは右ペインに `claude_config_dir が未設定です` が出るだけで、今までの表示と操作は変わらない。`claude` が入っていない環境でも `claude が見つかりません` が出るだけで起動できる。前の版に戻す場合も設定ファイルを直す必要は無い（未知のキーとして起動に失敗するので、`claude_config_dir` の行を消す必要がある点だけを README に書く）。
