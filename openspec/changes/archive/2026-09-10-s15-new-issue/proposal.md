issue: #6

## Why

人が TUI から起こせる書き込みは、回答（`a`）・`stage:todo`（`t`）・merge（`m`）の 3 つで、**新しい issue を起こす手立てが無い**。
キューを見ていて「これは別 issue だ」と気づいた瞬間に、ブラウザへ出て repo を選び直すしかなく、キューに戻るまでの往復がそのまま人の出番の取りこぼしになる。
`gh` 側の `CreateIssue`（`gh issue create -R <repo> --title <title> --body-file -`。URL を返す）は s03 が実装済みで、キー `n` は各 spec が「s15 の担当」として予約している。

## What Changes

- キュー画面（選択行）・カード詳細画面・PR 詳細画面で `n` を押すと、**その画面が見せている対象の repo** に新しい issue を作る手続きを始める。repo は選ばせない
- `$EDITOR`（`a` と同じ `Editor`）で下書きを書かせる。**1 行目をタイトル、2 行目以降を本文**として扱う
- 編集後に必ず確認画面を出し、`y` で作成、`e` で編集に戻る、`Esc` で中止する（`a` の確認画面と同じ操作、別の画面状態）
- タイトルが空、または本文が空なら作成しない。`<!-- routine -->` を含む下書きは確認画面に出すが作成の選択肢を出さない（不変条件 7）
- ラベルは 1 つも付けない（不変条件 6「Issue 作成は承認ではない」）。assignee も指定しない
- 作成に成功したらフッタのステータスに作成された issue の URL を出す。`Cards` は書き換えず、反映は `R` / 自動更新に任せる
- 書き込み中（投稿 / ラベル切り替え / merge / 作成）は `n` を受け付けず、作成中は `a` / `t` / `m` も受け付けない
- `?` ヘルプのキー一覧と、カード詳細 / PR 詳細のフッタのキーヒントに `n` を足す。キュー画面のフッタのキーヒントは 80 列のまま据え置く

範囲外: mvp.md キーバインド表の `s`（即着手）。同じ s15 の枠で予約されているが、この issue は `n` だけを求めており、`s` は後続 change が担当する。

## Capabilities

### New Capabilities
- `new-issue-action`: `internal/action` の issue 作成。下書きをタイトルと本文に分ける規則、空とマーカーの検査、`gh.GHClient.CreateIssue` の呼び出しと URL の返却。ラベル・コメントは書かない
- `new-issue`: `internal/ui` の `n`。作成先の repo を画面から決め、`Editor` で下書きを開き、作成の確認画面（`y` / `e` / `Esc`）を出し、結果（URL）をステータスに出す

### Modified Capabilities
- `queue-screen`: キュー画面の `n` が「何もしないキー」から「選択行の主体の repo に issue を作る」に変わる。フッタの右側に作成のステータスが加わり、キーヒント（80 列）は据え置く
- `card-detail`: 画面の状態が 7 つから 8 つ（作成の確認画面を追加）になる。カード詳細・PR 詳細で `n` が効き、フッタのキーヒントに `n 新規` が入る
- `answer-question`: 編集完了のメッセージの扱いが「`a` で始めた編集のとき」に限定される（`n` の編集完了は `new-issue` が扱う）。一時ファイルの名前が `loop-cli-answer-*.md` から `loop-cli-draft-*.md` に変わる（`Editor` を 2 つの用途で共有するため）
- `help-screen`: 実装済みキーの一覧に `n` が入る
- `todo-toggle`: 「書き込み中は `t` / `a` / `m` を受け付けない」に `n` が加わり、issue 作成中も `t` / `a` / `m` / `n` を受け付けない

## Impact

- コードは 2 か所を触る。`internal/action` に issue 作成のファイルを足し、`internal/ui` に `n` のキー処理・確認画面・状態・フッタとヘルプの行を足す。`cmd/loop-cli` の配線は変わらない
- `gh` は `y` の後に `CreateIssue` を 1 回呼ぶだけで、押下時の読み取りは無い（`m` と違い、判断材料を GitHub から取り直す必要が無い）。`GHClient` インターフェースは変えない
- docs 逸脱: mvp.md キーバインド表の `n` は「フォーム: リポジトリ・タイトル・本文」と書いている。この change は repo を画面の対象から決め、下書きは `$EDITOR` で書かせる。issue #6 が明示的にそう決めている。mvp.md の当該行はこの change で書き換える（tasks 5.1）
- 書き込み後の対象 1 件再取得（D-002）は s18 の担当で、この change では行わない。作った issue は次の `R` か自動更新で現れる
- 作成した issue に段階ラベルは付かないので、キューには「バックログ」として現れる。着手させるなら人が続けて `t` を押す（不変条件 6）

## 確定した判断

- **repo は画面の対象から決める**。キュー画面は選択行の主体（`internal/ui/rows.go` の `row.repo`）、カード詳細は `Card.Issue.Repo`、PR 詳細はその PR の `Repo`。`a` の `answerTarget`（`internal/ui/answer.go:60`）と同じ決め方で、`Card.Issue` が nil のカードはカード詳細を開かず PR 詳細に直行する（`openspec/specs/card-detail/spec.md` の Requirement「Enter でカード詳細を開き…」）ので、カード詳細で `Issue` が nil になる経路は無い
- **`$EDITOR` 方式を採り、`huh` のフォームは使わない**。`internal/ui` の書き込み系の下書きはすべて `Editor`（`internal/ui/editor.go`）を通っており、`huh` は onboarding（`cmd/loop-cli`）だけが使う。CLAUDE.md「パターン競合は平均化しない」に従い、`internal/ui` の主流である `Editor` に乗せる
- **確認画面は `a` の確認画面と別の状態にする**。`a` の確認画面は「投稿するか」を聞くもので `e` が下書きの再編集を意味する。`n` は下書きの意味（タイトル / 本文）も、成功時の結果（URL）も違う。s14 が merge の確認画面を別に持った判断（`openspec/changes/archive/2026-09-06-s14-merge-pr/design.md`）と同じ理由で状態を 1 つ増やす
- **ラベルを付けない**。`gh.Client.CreateIssue`（`internal/gh/client.go:299`）は `--label` を渡さない実装で、不変条件 6 と一致している。この change でも足さない
- **`Cards` を書き換えない**。s10 / s11 / s14 と同じく、書き込み後の再取得は s18 の担当
- **mvp.md キーバインド表の `n` の行を、この change で書き換える**（人の回答 Q1: A）。「フォーム: リポジトリ・タイトル・本文」を「選択中の対象の repo に `$EDITOR` で作成」に直し、内部処理の欄を `gh issue create -R <選択中の repo>` にして、変更履歴に 1 行足す。実装 PR の diff に `docs/mvp/mvp.md` が入る（tasks 5.1）。正本と実装が一致するので、次に mvp.md を読む人が古い前提で判断しない
- **キュー画面のフッタのキーヒントは 80 列のまま据え置く**（人の回答 Q2: B）。`n 新規` を足すと 88 列になり、ステータスが無いときでも幅 80 の端末で末尾の `q 終了` が常に切れる。s14 が移動系のキーを落として 80 列に収めた budget を保ち、`n` の入口は `?` のヘルプと詳細画面のフッタが見せる
- **作成先の repo は確認画面だけで明示する**（人の回答 Q3: A）。`n` を押すとすぐ `$EDITOR` が開き、確認画面の 1 行目 `新規 issue の確認: <repo>` で `y` を押す前に必ず目に入る。エディタを開く前に作成先だけの画面を挟む案は採らない（issue 1 本ごとに `y` が 2 回になる）

## 延期した判断と残るリスク

- **`s`（即着手）は範囲外**。mvp.md キーバインド表で `n` と同じ s15 の枠に予約されているが、issue #6 は `n` だけを求めている。`s` は `stage:propose` を書く強制操作（不変条件 2・3）で、`n` と共通する部分が無い。後続 change が担当する
- **作成した issue が画面に出るまで待ちがある**。`Cards` を書き換えないので、作った issue は次の `R` か自動更新（既定 120 秒）でキューに現れる。それまでの手掛かりはフッタに出る URL だけである。書き込み後の対象 1 件再取得は s18 の担当で、s10 / s11 / s14 と同じ穴を引き継ぐ
- **作成先を取り違えると下書きを 1 本失う**。気づけるのは書き終わった後の確認画面で、`Esc` で捨てて行を選び直すことになる（Q3: A の結果として受け入れる）
- **マーカーを引用した issue は TUI から起こせない**。不変条件 7 の 1 文目「TUI は `<!-- routine -->` を書かない」を本文とタイトルにも及ぼすため、`<!-- routine -->` を含む下書きには作成の選択肢を出さない。loop-cli 自身の開発でこれが要るときはブラウザで起票する
- **キュー画面を見ているだけでは `n` に気づけない**（Q2: B の結果）。`?` のヘルプと詳細画面のフッタが入口を見せる
