## Context

今の TUI で外部を開く経路は `o` だけで、`internal/gh` の `Browse` が `gh browse <n> -R <repo>` を実行する。`gh browse` はリポジトリと番号（またはリポジトリ内のパス）を受け取る作りなので、この経路に任意の URL を渡せない。

画面の状態は `internal/ui` の `Model` が 5 つ（キュー / カード詳細 / PR 詳細 / 確認 / ヘルプ）持ち、`Update` が状態ごとにキーを振り分け、`View` が状態ごとに全画面を描く。確認画面（s10）とヘルプ画面（s12）はどちらも全画面で、重ね合わせのオーバーレイは使っていない。`a` / `t` / `o` / `?` は画面の状態より前に振り分けられ、対象は「画面が見せているもの」で決まる。

URL の材料になる本文は、`Fetch` が Card に入れた値の中にある。`Issue.Body` / `Issue.Comments` / `PR.Body` / `PR.Comments` / `PR.ReviewThreads` で、詳細を開いても `gh` は呼ばない（s09）。s20 が全件先取りにしたので、`Comments` / `ReviewThreads` が `nil` なのは詳細の取得に失敗したときだけである。

本文の解析は `internal/model/parse.go` に `ParseUndecided` / `ParseQuestions` があり、`internal/ui/detail.go` に `dependsOn` がある。純粋な本文パースの主流は `internal/model` である。

## Goals / Non-Goals

**Goals:**

- PR / issue の説明文に貼られた URL に、GitHub を経由せずキーボードだけで到達できる
- キーを 1 つ（`u`）増やすだけで、URL の件数に依存せず選べる
- 開けなかったときに、何が起きたかがフッタに出る

**Non-Goals:**

- URL の中身を TUI 内で表示すること（プレビュー・タイトル取得・HTTP アクセスは行わない）
- URL 以外の参照（`#123`、`org/repo#123`、`@user`）へのジャンプ
- checks の詳細 URL を開く導線（`m` merge と合わせて別 change で扱う）
- 複数の URL をまとめて開く操作

## Decisions

### D-1: URL 一覧は 6 つ目の画面の状態として全画面で描く

`Model` の画面の状態に URL 一覧を足し、`View` はキュー / 詳細と同じく端末の幅と高さ全体を使って描く。

**なぜオーバーレイ（モーダル）ではないか。** 依頼の言葉は「モーダルのようなもの」だが、このコードベースに重ね合わせの前例は無く、確認画面もヘルプ画面も全画面で作られている。重ね合わせを入れると、背面の描画結果に対する切り出しと合成の規則を新しく決めることになり、`View` の分岐が 1 つ増えるだけの全画面より複雑になる。利用者から見た振る舞い（`u` で一覧が出て、選んで開いて、`Esc` で元に戻る）は同じである。

### D-2: `u` と一覧のキーは `a` / `t` / `o` / `?` より前に振り分ける

`Update` のキー振り分けで、URL 一覧画面の分岐を確認画面・ヘルプ画面と同じ位置（`a` / `t` / `o` / `?` の判定より前）に置く。

一覧を出している間の `o` を後ろに置くと、`o` の対象を決める処理が「画面はキュー」と見なして選択行を開いてしまう。`a` / `t` も同じ理由で、一覧の裏にある対象へ書き込みが起きる。確認画面が既に同じ位置で分岐しているので、そこに並べる。振り分けの中では一覧画面の分岐を先に置き、`u` のハンドラをその後ろに置く（逆にすると、一覧を出したまま `u` を押したときに裏のキュー行から対象を取り直し、戻り先が一覧自身に上書きされて `Esc` が効かなくなる）。

一覧画面で扱うキーは `j` / `k` / `↑` / `↓`（選択）、`Enter`（開く）、`Esc`（戻る）、`q` / `Ctrl+C`（終了）だけで、他のキーは何もしない。ヘルプ画面の `?` と同じく、戻り先の画面を保持して `Esc` でそこへ戻す。戻り先がカード詳細 / PR 詳細のときは、ヘルプ画面と同じ理由（一覧を出している間の端末サイズ変更が詳細に反映されない）で、戻るときに本文領域を作り直す。

### D-3: URL の抽出は `internal/model` の純粋な関数にする

本文 1 つを受け取り、出現順の URL とリンクテキストの並びを返す関数を `internal/model/parse.go` に足す。`internal/ui` は対象から本文を集めてこの関数を呼び、出典を付けて並べる。

拾うのは 2 つの書き方に限る。

1. Markdown のリンク `[テキスト](URL)` — テキストを一覧に出す
2. 裸の `https://` / `http://` で始まる文字列 — テキストは空

裸の URL は、空白・改行・閉じ括弧（`)` `>` `]` `）` `］` `〉` `」`）のいずれかの直前までを 1 件とし、末尾に句読点（`.` `,` `:` `;` `。` `、`）が付いていたら削る。Markdown リンクとして取った範囲は裸の URL の走査から外す（同じ URL を 2 回返さないため）。Markdown の `<https://…>` は `>` で切れるので同じ結果になる。この規則で `Closes #108` のような参照記法は拾わない。

**なぜ `internal/ui` に置かないか。** `dependsOn` が `ui` にあるが、これは詳細のヘッダにしか使われない表示専用の判定である。URL の抽出は 5 か所（issue 本文・issue コメント・PR 本文・PR コメント・review thread コメント）から呼ばれ、テストも本文の書き方ごとに書きたい。`model` の既存の 2 つのパース関数と同じ場所に置く。

### D-4: 収集元は本文 → コメント → review thread の順、重複は初出だけ

対象と収集元は次のとおり。

| 画面 | 対象 | 収集元 |
| --- | --- | --- |
| キュー | 選択行の主体（s08 `Subject`） | 主体が PR なら PR の 3 か所、issue なら issue の 2 か所 |
| カード詳細 | `Card.Issue` | Issue 本文 → Issue コメント |
| PR 詳細 | 選択中の PR | PR 本文 → PR コメント → review thread のコメント |

並びは表の順で、コメントの中は `Fetch` が入れた並び（時系列）のまま。同じ URL が複数回出てきたら初出の 1 件だけを残し、後の出現は捨てる（リンクテキストも初出のものを使う）。

出典は行の先頭に `[本文]` / `[コメント]` / `[thread]` として出す。`Comments` や `ReviewThreads` が `nil`（取得に失敗した）ときは、その収集元を飛ばすだけで、一覧には何も出さない。

### D-5: 任意の URL を開く経路は `GHClient` に足す

`GHClient` interface に `OpenURL(ctx, url)` を足し、`Client` は `runtime.GOOS` が `darwin` なら `open <url>`、それ以外なら `xdg-open <url>` を実行する。`Client` の既存の差し替え口は `gh <引数>` を実行する関数なので、ブラウザ起動コマンドはそれとは別の差し替え可能な関数として持ち、テストはそちらを差し替えて引数を記録する。`Fake` は呼び出しを `Calls` に記録し、外部プロセスを起動しない。記録のために `Call` に URL の欄を足す。

**なぜ `internal/gh` に置くか。** 外部を開く操作は今 `Browse` だけで、`Model` はそれをコマンド（別ゴルーチン）として実行し、`Fake.Calls` で検証している。`u` の経路も同じ形にすれば、タイムアウト（30 秒）・エラーのフッタ表示・テストの書き方を `o` と共有できる。`internal/open` のような小さなパッケージを新しく作って `Editor` と同じく `cmd/sugi-loop` から注入する案もあるが、外部を開く経路が 2 つに分かれ、`Model` が持つ依存が 1 つ増える。`internal/gh` は「外部プロセスを呼ぶ層」として既にその役割を持っている。

mvp.md のキーバインド表は `o` の内部処理を `gh browse` / `open <url>` と書いており、`open <url>` を使うこと自体は正本に沿っている。

### D-6: URL が 0 件なら画面を変えずステータスに出す

`u` を押したときに 1 件も集まらなければ、画面の状態を変えず、フッタのステータスに `URL がありません` を出す（赤にしない。失敗ではない）。このステータスは `o` / `a` / `t` と同じ場所を共有し、次の取得の開始や次の `a` / `t` で消える。

空の一覧画面に入ると、`Esc` を押すためだけの画面が出る。押すキーが増えて手数が減らない。

### D-7: 一覧の描画は見出し・行・フッタの 3 部で、選択行に追従して窓をずらす

`View` は、見出しの `URL を開く`、空行、URL の行、残りを埋める空行、フッタを、上からこの順で描く。フッタの左は `j/k 選択  Enter 開く  Esc 戻る  q 終了`、右は他の画面と同じステータスとする。

1 行は `<印><出典> <リンクテキスト>  <URL>` で、印は選択行が `▶ `、他が空白 2 列。リンクテキストが空なら出典と URL の間は空白 2 列にする。行が端末幅を超えるときは他の画面と同じく末尾を切り詰める。

URL の件数が表示できる行数を超えるときは、選択行が必ず見えるように表示の開始位置をずらす（選択が上端より上に出たら開始位置を選択に合わせ、下端より下に出たら開始位置を「選択 − 表示行数 + 1」にする）。スクロール用の部品は持ち込まず、一覧は選択位置だけを状態に持つ。

### D-8: ヒントの `u URL` は `? ヘルプ` の直後に置く

キュー・カード詳細・PR 詳細のフッタのヒントで、`u URL` を `? ヘルプ` の直後に入れる。

キュー画面のヒントは 64 列から 71 列になる。取得中のステータス `⠋ 取得中`（8 列）と並べると 71 + 間隔 1 + 8 = 80 で、既定幅 80 にちょうど収まる（`footer` はヒント幅 + 1 + ステータス幅が端末幅を超えるとヒントを捨ててステータスだけを出すため、この 1 列の余りが s08 の Scenario「既定幅 80 で取得中でもヒントとスピナーが両方出る」を満たす境目になる）。これ以上ヒントを伸ばす後続 change は、この Scenario が壊れることを前提に幅を配分する。

s12 はカード詳細のヒントについて「`? ヘルプ` を `a 回答` の前に置くのは、末尾に置くと幅 80 で切れてヘルプの入口が見えないため」と決めている。同じ理由で、`u URL` も幅 80 で見える位置に要る。`? ヘルプ` の直後なら、キュー（64 → 71 列）と PR 詳細（66 → 73 列）は幅 80 に収まり、カード詳細（101 → 108 列）でも `u URL` は 72 列目で終わるので、ステータスが出ていない幅 80 の端末では見える。

ヘルプ画面のキー一覧には `u  URL を開く` の行を `o` の直後（mvp.md キーバインド表に合わせた並び）に足す。キーの行は 14 行から 15 行になり、見出しと空行を含めた 17 行は既定の高さ 24 に収まる（s21 で `p` の行が消えた分を反映する）。

## Risks / Trade-offs

- **[裸の URL の切れ目を誤る]** → 括弧や句読点を含む URL は途中で切れることがある。括弧の対応を数える解析は行わないので、Markdown リンク `[テキスト](URL)` の中に `)` を含む URL も最初の `)` で切れる。開く前に一覧で URL 全体が見えるため、切れた URL はその場で分かる
- **[`xdg-open` が無い環境で必ず失敗する]** → 失敗はフッタに赤で出る（`o` と同じ扱い）。開発と運用の対象は macOS で、Linux は `xdg-open` を既定とする。ブラウザ起動コマンドを設定で変える仕組みは、要望が出たときに別 change で足す
- **[コメントが多い PR で一覧が長くなる]** → 重複を除いた上で、出典で本文が先頭に来るので、説明文の URL は常に上に出る。件数の上限は設けない
- **[取得に失敗した範囲の URL が出ない]** → 詳細取得が失敗した対象は `Comments` / `ReviewThreads` が `nil` で、そこからは URL が集まらない。失敗自体は s08 のフッタに出るので、一覧の中で改めて説明せず、単に出さない
- **[先行する `s21-always-two-pane` と同じ Requirement を書き換える]** → `queue-screen` のキー・`card-detail` の 2 つ・`help-screen` のキー一覧は、この change の MODIFIED を s21 の delta を土台に写している。s21 より先にこの change を archive すると、`p` の削除が巻き戻る。実装と archive は s21 → s22 の順で行う
- **[`Call` に欄を足すと `gh-fake` の spec が変わる]** → `Call` は `Method` ごとに使う欄が違う構造で、欄の追加は既存の検証を壊さない。`gh-fake` の Requirement を MODIFIED で写して 1 行足す

## 未決事項

docs が沈黙している点と、実装者が採る既定値。

1. **キー `u`** — mvp.md のキーバインド表に `u` は無い（2026-09-05-1805 の上流同期で別の意味の `u` が削られている）。既定値: `u` を「URL 一覧を開く」として使い、mvp.md の表に行を足して正本と実装を揃える
2. **見出しとフッタの文言** — 既定値: 見出しは `URL を開く`、フッタは `j/k 選択  Enter 開く  Esc 戻る  q 終了`
3. **出典ラベルの語** — 既定値: `[本文]` / `[コメント]` / `[thread]`。`thread` は PR 詳細の表示（`thread 未 resolve`）で既に使っている語に合わせる
4. **0 件のときの文言** — 既定値: `URL がありません`。赤にしない
5. **確認画面（s10）での `u`** — 既定値: 何もしない（`?` と同じ扱い。回答の途中で画面を移さない）
6. **一覧画面での `o` / `a` / `t` / `R`** — 既定値: 何もしない
7. **`Enter` で開いた後の選択位置** — 既定値: 変えない（一覧に留まり、同じ行が選択されたまま）
8. **同じ URL がリンクテキスト違いで複数回出るとき** — 既定値: 初出のリンクテキストを使う
9. **HTML エスケープされた本文** — `internal/model/parse.go` は `&lt;!-- routine --&gt;` の形で届く本文を扱う実績がある。エスケープされた本文では `&lt;https://x&gt;` の終端が `&` になり、`&amp;` を含むクエリも壊れる。既定値: 走査の前にエスケープを戻さず、届いた文字列のまま走査する（誤って切れた URL は一覧で見えるので、開く前に分かる）
10. **コードブロック内の URL** — 既定値: 本文の他の部分と区別せず拾う（抽出は Markdown の構造を解釈しない）
11. **`OpenURL` に渡す ctx のタイムアウトの長さ** — 既定値: `Model` は 30 秒のタイムアウトを付けた ctx を渡す（s10 / s11 / s12 と同じ値）
