## Context

人の役割 3 つのうち merge だけが TUI に無い。`gh` 側の `MergePR(ctx, repo, number, method)` は s03 が実装済みで、キー `m` は各 spec が「s14 の担当」として予約している。
merge の判断材料（`question` ラベル・本文 1 行目の `未確定の判断: N 件`・checks・`isDraft`・`mergeable`）のうち、画面が持っているのは取得時点の値である。s09 は「詳細を開いても `gh` を呼ばない」と決めたため、human-turn-signals.md「merge 可否は表示時に取り直す」を満たしていない。
merge は取り消せない書き込みであり、docs は局面 C に「確認ダイアログ必須」と書いている。

## Goals / Non-Goals

**Goals:**
- キュー・カード詳細・PR 詳細の 3 画面から、対象の PR を選んで merge できる
- merge の直前に GitHub の現在の状態を読み直し、その値で判断材料を確認画面に出す
- draft の PR と、すでに merged / closed の PR を merge させない
- `question` / 未確定 N > 0 / checks 非緑 を確認画面の警告として見せ、merge するかどうかは人が決める

**Non-Goals:**
- merge 後の対象 1 件の再取得（D-002。s18 の担当）
- `--delete-branch` / `--auto` / `--admin`（s03 が付けないと決めている）
- 画面上での merge 方式の切り替え（設定ファイルの値をそのまま使う）
- 局面 G（`docs` ラベルの PR）と局面 C の区別（どちらも同じ `m` で merge する）
- review の承認、conflict の解消

## Decisions

### ガードは draft と open でない PR だけが止める。他は警告にする
human-turn-signals.md 不変条件 5 は `question` / 未確定 N > 0 / checks 失敗 / `isDraft` の 4 つで merge を拒否すると定めるが、この change は draft 以外を警告に緩める。
理由は、この TUI を使う人が「未確定の判断が残っていても、内容を読んだ上で merge する」判断をできる立場にあり、TUI 側で禁止すると `o` でブラウザに逃げる動線しか残らないためである。禁止は動線を消すだけで、誤 merge の抑止にはつながらない。
警告は確認画面に全部並べ、`y` を押す前に必ず目に入る。draft は「まだ人に見せる状態ですらない」という作者自身の宣言なので、これだけは `y` を出さない。
docs 逸脱の申し送りをここに残す。この決定は human-turn-signals.md 不変条件 5 の文面と食い違う。上流の規約が変わったわけではないので、docs を書き換えず、この design.md を根拠として残す。運用してみて誤 merge が起きるようなら、拒否に戻す判断は妥当である。

代替案: 4 条件すべてで拒否する（docs 準拠）。人の判断を奪うので採らない。警告も出さず draft だけ見る案は、判断材料を隠すことになるので採らない。

### `m` の押下で ViewPR と ViewPRMergeState を呼び直す
画面が持つ `MergeState` は取得時点の値で、checks が後から緑になったり赤になったりする。merge の判断はその瞬間の値でしなければならない。
`ToggleTodo` が `ViewIssue` で読み直してから書く前例に揃え、`m` は `ViewPR`（`Labels` / `Body` / `IsDraft`）と `ViewPRMergeState`（checks / `mergeable`）を呼び、その結果で確認画面を組み立てる。s09 の逸脱を、merge の判断に使う値については回収する。
どちらか一方でも失敗したら確認画面を出さず、フッタに赤で出す。判断材料が欠けたまま merge の入口を開かない。

代替案: 画面の値で判定する（押下から確認画面まで待ちが無い）。古い checks で merge を許すことになるので採らない。

### ガードの判定は `internal/action` に置き、`internal/ui` は判定を持たない
s10 が `action.BlockedByLines` / `action.HasRoutineMarker` を `ui` から呼んだのと同じ形にする。`action` は `model.HasLabel` / `model.ParseUndecided` / `classify.ChecksGreen` の既存関数を使い、判定を二重に書かない。
`Merge` は `client.MergePR` を 1 回呼ぶだけで、ラベルもコメントも書かない（不変条件 2「TUI が書くラベルは `stage:todo` と `stage:propose` に限る」）。ガードは `ui` が確認画面を出す前に呼ぶものであり、`Merge` 自身はガードを判定しない（`y` を押した人の判断が最後の関門）。

### merge の確認画面は s10 の回答の確認画面と別に持つ
s10 の確認画面は「下書きを投稿するかどうか」を聞く画面で、`y` / `e` / `Esc` の `e` は下書きの再編集である。merge には下書きが無く、`e` に相当する操作も無い。
1 つの画面状態に 2 つの意味を持たせると `y` の意味が対象によって変わるので、画面の状態を 1 つ増やす（`card-detail` の「画面の状態は 6 つ」を 7 つに変える）。CLAUDE.md「パターン競合は平均化しない」に従い、s10 の状態を流用しない。

### merge 方式は `ui.Options` でリポジトリ名から引く
`internal/ui` は `internal/config` を import しない（s03 design「`internal/gh` を `internal/config` に依存させない」と同じ方針）。`cmd/loop-cli` が `Config.Repos[].Name` → `string(MergeMethod)` の対応表を作って `Options` に渡し、`Model` は対象の `Repo` で引く。

## Risks / Trade-offs

- [`m` を押してから確認画面が出るまでに待ちが入る] → 押下直後からフッタに `<表示名> の状態を取得中` を出し、無反応に見せない。`ctx` は 30 秒（s10 / s11 / s12 と同じ）
- [警告を出しても人が読み飛ばして merge する] → 警告は確認画面の本文より上に置き、`y` を押す指が止まる位置に出す。それ以上の抑止は取らない（この change の判断そのもの）
- [merge に成功しても画面のカードは古いまま残る] → ステータスに `merge しました` を出す。カードは次の `R` か自動更新（s13）で消える。s18 が入るまでの既知の穴で、s10 / s11 と同じ扱い
- [取り直しと merge の間に状態が変わる] → 埋められない隙間である。`gh pr merge` が失敗すればフッタに赤で出るので、TUI が「merge した」と嘘をつくことは無い
- [キュー画面から PR の中身を見ずに merge できてしまう] → 確認画面にタイトル・本文・ラベル・checks・`mergeable` を出し、判断材料を画面に載せる
- [merge 済みの PR にもう一度 `m` を押せる] → カード詳細の PR 一覧は merged / closed の PR も選べるので、画面の Card が持つ `State` が `OPEN` でなければ拒否する。ただし merge に成功した直後は `Cards` が古いまま `OPEN` なので、同じ行での二重 merge は `gh pr merge` の失敗でしか止まらない（s18 が入るまでの既知の穴）
- [merge の実行中に `q` / `Ctrl+C` を押すとプログラムが終わり `gh` も `ctx` ごと止まる] → `a` / `t` と同じ既存の穴だが、merge は不可逆なので、実行中は `merge 中` のステータスを出して押させない材料にする

## 未決事項（実装者が選ぶ既定値）

| 論点 | 既定値 | 理由 |
| --- | --- | --- |
| 確認画面に出す項目 | `merge の確認: <表示名>  <Title>` / `方式: <method>` / `labels: …` / `mergeable: <Mergeable> <MergeStateStatus>` / checks の要約 / 拒否行 / 警告行 / 区切り線 / 本文 | 局面 C の判定に使う値をすべて 1 画面に載せる。docs に画面の指定は無い |
| 確認画面のスクロール | しない（残りの高さで切る） | s10 の確認画面と同じ |
| `Options` の対応表に無いリポジトリ | `squash` を使う | config は全リポジトリの方式を必ず埋めるので通常は起きない。`gh pr merge` の既定が対話式なので、方式を空で渡さない |
| 取り直しの 2 回の呼び出し | 並行に行い、両方の完了を待って 1 つのメッセージにする | s07 の `fetchDetails` と同じ形。逐次にすると待ちが 2 倍になる |
| 書き込み中の `m` | 受け付けない（`t` / `a` と同じ） | s11「書き込み中は `t` と `a` を受け付けない」の延長。merge 中の `t` / `a` も同様に止まる |
| 確認画面での取得完了メッセージ | `Cards` と最終更新時刻は更新し、確認中の対象と取り直した値は変えない | s10 の確認画面と同じ |
| merge 中に押した `o` / `?` / `u` | 受け付ける（書き込みではない） | s12 `browse-open`「書き込み中でも `o` を受け付ける」と同じ |
| 成功のステータス文言 | `<表示名> を merge しました` | s10 / s11 の文言の形に揃える |
| 確認画面の `q` / `Ctrl+C` | 終了コマンドを返す | s10 の確認画面と同じ |
| 取り直しの結果が別の画面に届いたとき | 確認画面に移らず、ステータスに `<表示名> の merge を中止しました（画面が変わりました）` を出す | 取り直し中も `?` / `u` / `Enter` は動くので、ヘルプ画面や URL 一覧画面を確認画面で踏み潰さない |
| merge の対象の保持 | 確認画面がリポジトリ名・番号・方式・表示名を保持し、`y` はそれだけを使う | 確認画面を読んでいる間に自動更新が走ると選択行が動く。s10 が `a` の押下時に `Target` を捕まえるのと同じ形 |
| PR 詳細のヒントが 82 列になること | そのまま（幅 80 では `q 終了` が切れる） | キュー画面の 80 列と同じ判断。`q` は切れても動く |
