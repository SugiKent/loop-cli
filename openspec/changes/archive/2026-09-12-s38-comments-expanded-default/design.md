## Context

詳細画面のコメントは `commentBlock`（`internal/ui/preview.go:50`）が 1 件ずつ行に直す。AI のコメントだけが
引数 `expanded` を見て、false なら見出し 1 行（`▌AI  HH:MM  <要約>  (+<n> 行)`）に畳まれる。
呼び出し側は 2 つある。キュー画面のプレビューは常に `true` を渡し（同 `:43`）、詳細画面は
`detailState.expanded` をそのまま渡す（`internal/ui/detail.go:375`）。`detailState` は `openDetail` が
ゼロ値で作る（同 `:75`）ので、詳細を開いた直後の `expanded` は false になる。動機は proposal.md の「Why」を見る。

issue #60 の title は「コメントは常に展開する」、本文は「デフォルトで全て表示するようにする」で、`x` を
残すかどうかが読み取れなかった。PR #68 で問い、折りたたみ自体を廃止する回答を得た。したがってこの change は、折りたたみという状態を
`Model` から丸ごと無くす。既定値だけを展開に変える案は、回答が廃止だったので採らない。

制約は 3 つの capability にまたがる。`card-detail` が書式と `x` の意味とフッタのヒントを、`help-screen` が
ヘルプのキーの行と行数を、`queue-screen` が「何もしないキー」の台帳を、それぞれ文面で固定している。

## Goals / Non-Goals

**Goals:**

- カード詳細画面と PR 詳細画面のコメントを、AI が書いたものも含めて常に全文で出す
- 折りたたみの状態と要約の規則を、コードと spec の両方から無くす
- `x` が何もしないキーになったことを、フッタ・ヘルプ・キュー画面の台帳の 3 か所で揃える

**Non-Goals:**

- `x` に別の意味を割り当てること（issue #60 の範囲外）
- 長いコメントを別の方法で短くすること（先頭 n 行だけ出す、セクション単位で送る、検索で飛ぶ）
- キュー画面のプレビューと review thread の見え方を変えること。どちらも元から全文である
- 人のコメントの扱いを変えること

## Decisions

### D1. 折りたたみの状態を丸ごと消す

`detailState.expanded` を消し、`case "x"` を消し、`commentBlock` から引数 `expanded` を落とす。
`commentBlock` は AI かどうかで `▌` を付けるかだけを分け、常に全行を返す。`summarize` は呼ぶ側が
無くなるので関数ごと消す。

既定値だけを `true` に変えて `x` をトグルとして残す形（PR #68 の選択肢 A）は採らない。回答が廃止だったので、
状態を持たない方が扱う分岐が少なく、`detailState` をゼロ値で作るテスト 3 か所とも食い違わない。

### D2. `x` は何もしないキーとして、3 か所の台帳をそろえる

`Update` が `x` の分岐を失うので、詳細画面でも押して何も起きない。キュー画面は元からその扱いで、
`queue-screen` の Requirement が `x` を「詳細画面のキー」として名指ししている記述だけが古くなる。
そこで台帳から `x` を詳細画面の並びの外へ出し、フッタのヒント（`card-detail`）とヘルプの一覧
（`help-screen`）からも `x` を落とす。**動かないキーを画面が案内しない**ことを 3 か所で同じにする。

### D3. フッタのヒントの列数を引き直す

`x 展開` は表示幅 6 列で、区切りの 2 列と合わせて 8 列を占める。落とすとカード詳細は 144 列から 136 列、
PR 詳細は 109 列から 101 列、`PRs` が空のカード詳細は 96 列から 88 列になる。`card-detail` の Requirement は
この 3 つの数と、切り詰めが始まる端末幅（幅 143 以下 → 幅 135 以下）、`? ヘルプ` と `u URL` が終わる列
（65 → 57、72 → 64。どちらも `x 展開` の後ろにあるので 8 列手前に来る）を文面で持っているので、すべて
引き直す。幅 80 の端末で PR 詳細のヒントが切れ始める位置も `a 回答` の後ろから `c close` の後ろへ動く
（`c close` が 73 列目で終わり、次の `n 新規` が 81 列目で終わるため）。

### D4. ヘルプの行数を 20 行に戻す

`help-screen` の Requirement はキーの行を 1 字単位で固定し、行数も文面に持つ。`x` の行を落とすと 20 行に
なり、見出しと空行を含めて 22 行、フッタと合わせて 23 行で、`Model` の既定の高さ 24 に 1 行余る。
s37 でちょうど使い切っていた余白が 1 行だけ戻る形になる。

### D5. 表示状態は `example` fixture を通したテストで再現する

この TUI は `gh` の出力を読むだけで、開発用の DB や seed を持たない。表示状態は
`internal/gh/testdata/fixtures/example/` が持つ 2 つの fixture で再現できる。issue 108 は AI コメント
1 件と人のコメント 1 件を持ち、PR 131 は AI コメント 1 件と review thread 1 本を持つ。
テストは `internal/ui/detail_test.go` が担い、`View` の文字列をそのまま検証している。したがって seed を
足さず、既存 fixture を使う Scenario で「開いた直後に全文が出る」ことを見る。

## Risks / Trade-offs

- **長い AI コメントを畳めなくなる。** grill の質問が並ぶ PR では 1 コメントが 20 行を超える。
  逃げ道はスクロール（`j` / `k` / `PgDn` / `PgUp` / `G` / `End` / `Home`）だけになる。
- **画面に最初から見えている範囲が狭くなる。** AI コメントの下にある `── review thread ` や checks を
  見るのにスクロールが要る場面が増える。
- **既存のテストが 8 本壊れる。** 6 本は詳細画面、2 本はヘルプ画面で、どれも「畳まれていること」または
  `x` の行を期待している。壊れること自体が折りたたみを消した証拠になるので、テストを消さずに書き換える。
- **`x` が空きキーになる。** mvp.md のキーバインド表に載ったまま何もしないキーが、`p` に続いて 2 つ目に
  なる。押した人には無反応に見える。

## 未決事項

- **`x` に別の意味を割り当てるか。** この change では割り当てない。空いたキーの使い道は、必要になった
  時点で issue を立てて決める。
- **コメントを畳む手立てを別の形で戻すか。** セクション単位で送るキー、検索（`/`、s19 の枠）、
  先頭 n 行だけ出す表示などが候補になる。実際に読みにくさが出てから決める。
- **`docs/mvp/mvp.md` の記述をどう扱うか。** `docs/mvp` は MVP 時点の記録として凍結する規則
  （`CLAUDE.md`）なので書き戻さない。仕様の正本は `openspec/specs/`、利用者向けの説明は `README.md` が持つ。
