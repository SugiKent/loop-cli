issue: #17

## Why

`n` で開くエディタは空のまま開く（`internal/ui/new.go:47` の `m.openEditor(routeNewIssue, "")`）。
s15 は「書式の案内を初期テキストに入れると、それがそのままタイトルになる」ことを避けるために空を選び、書式は確認画面の
`タイトル: <タイトル>` の行で見せる形にした（`openspec/changes/s15-new-issue/design.md`「下書きは 1 枚のテキストで書かせ、1 行目をタイトルにする」）。

その結果、人が Vim を開いた時点で画面には何も無く、どこに何を書けばよいかは書き終えて確認画面に着くまで分からない。
書式を間違えると（空行から書き始める・本文から書き始める）`作成を中止しました（タイトルが空）` だけが出て下書きは一時ファイルごと消える
（s15 design の Risks の 2 件目）。案内を初期テキストに入れる道が閉じていたのは、**案内の行を区切りとして使わず 1 行目をタイトルにしていた**からである。

案内の 2 行そのものを区切りに使えば、案内はタイトルにも本文にも入らない。issue #17 がこの形を求めている。

## What Changes

- `n` で開くエディタの初期テキストを、タイトルと概要のプレースホルダー行 2 本を含む下書きにする（今は空文字列）
- 下書きの分け方を「最初の改行で分ける」から「**2 本のプレースホルダー行を区切りにして分ける**」に変える。タイトルは 2 本のプレースホルダー行に挟まれた部分、本文は概要のプレースホルダー行より下すべて。前後の空白は落とす
- プレースホルダー行はタイトル・本文のどちらにも入らない。人が消した・書き換えた・複製した下書きと、案内の文言を本文に引用した下書きは**分割できないものとして作成を中止**し、フッタに `作成を中止しました（プレースホルダー行が見つかりません）` を出す
- タイトルが空 / 本文が空なら作成しないという s15 の検査はそのまま残す。プレースホルダーだけの下書き（書かずに保存した）はこの検査で止まる
- 確認画面の `e` は今と同じく編集後の下書きそのもの（プレースホルダー行を含む）をエディタに返す
- **BREAKING**（`internal/action` の関数の形）: `SplitNewIssue` は分割できたかどうかを呼び出し側へ返す形に変わる。呼び出し元は `internal/ui/new.go` の 1 か所だけで、外部に公開している API ではない
- `docs/mvp/mvp.md` キーバインド表の `n` の行（113 行目）の「1 行目がタイトル、以降が本文」を、プレースホルダー行で分ける形に書き換える

範囲外は 3 つある。本文側の複数行の扱いは変えない（概要のプレースホルダー行より下すべてが本文のまま）。GitHub 側の issue テンプレート機能を取り込まない。`a`（回答）のエディタの初期テキストは触らない（`action.AnswerTemplate` が既に事前入力している）。

## Capabilities

### New Capabilities

なし。

### Modified Capabilities

- `new-issue-action`: Requirement「下書きの 1 行目がタイトル、残りが本文になる」の分割規則が、最初の改行からプレースホルダー行の区切りに変わり、分割できなかったことを呼び出し側が判別できるようになる。エディタの初期テキストになる下書き（プレースホルダー行 2 本を含む）を提供する Requirement が 1 本増える
- `new-issue`: Requirement「n は画面の対象のリポジトリを作成先にしてエディタを開く」の `initial` が空文字列からプレースホルダー入りの下書きに変わる。Requirement「編集結果を検査して作成の確認画面に移る」の検査に「プレースホルダー行が見つからない」が加わる。Requirement「作成の確認画面は作成先と下書きを出し、y で作成して Esc で中止する」の `e` が返す下書きにプレースホルダー行が含まれる

## Impact

- コードは 2 ファイルを触る。`internal/action/newissue.go` にプレースホルダーの定数と初期下書きを足して `SplitNewIssue` を書き換え、`internal/ui/new.go` では `openEditor` に渡す初期テキストを変えて編集完了の検査を 1 件足す。`internal/gh` と `GHClient` は変わらない
- テストは `internal/action/newissue_test.go` と `internal/ui/new_test.go`。`new_test.go` のスタブ `Editor` が返す固定文字列は、今は `キュー画面の色を見直す\n\n種別の色が背景色と競合している。` のようにプレースホルダー行を持たないので、**既存のケースはすべて新しい下書きの形に書き換える**（書き換えなければ「プレースホルダー行が見つかりません」で止まり、確認画面へ進むケースが 1 本も残らない）
- `docs/mvp/mvp.md` の 1 行の書き換えと変更履歴の 1 行追加が実装 PR の diff に入る（s15 と同じ扱い。製品の目的地そのものは変えない）
- 人から見た変化: エディタが空でなくなる。s15 以前から `n` を使っている人が「プレースホルダーを消して 2 行だけ書く」やり方をすると作成できなくなり、フッタに理由が出る
- 作成される issue の中身は変わらない（プレースホルダー行は GitHub へ出ていかない）。ラベルを付けない・`Cards` を書き換えないという s15 の性質も変わらない

## 確定した判断

- **プレースホルダーの文言と下書きの形は issue #17 の指定どおりにする**。初期テキストは `タイトル（この下の行に入力してください）` / 空行 / `概要（この下に入力してください）` / 空行 の 4 行で、人はそれぞれのプレースホルダー行の下に書く
- **プレースホルダーの定数と初期下書きは `internal/action` に置く**。`a` が `action.AnswerTemplate(comments)` を `openEditor` に渡している（`internal/ui/answer.go:56`）のと同じ形で、`internal/ui` は文言を持たない。区切りに使う文字列と分割する関数が同じパッケージに並ぶので、片方だけ直して分割できなくなる事故が起きない
- **プレースホルダー行の判定は「行の前後の空白を落とした結果が文言と一致する」ことで行う**。エディタが行末に空白を残しても区切りとして働き、行の中に文字を書き足した行（`タイトル（この下の行に入力してください）キュー画面の色を見直す`）は区切りにならない。issue #17 の「人が消したり書き換えたりすると分割できない」をこの形で満たす
- **区切りは先頭から最初の 1 本ずつを採り、それ以外に案内の文言と一致する行が残っていたら分割しない**。先頭優先だけで分けると、案内の行が 3 本以上ある下書き（Vim の行複製、案内をもう 1 組貼り直した、案内の文言を本文に引用した）で案内の文字列がタイトルや本文に入って GitHub へ出ていく。たとえば `タイトル（…）` / `キュー画面の色を見直す` / `タイトル（…）` / 空行 / `概要（…）` / `本文` の下書きは、タイトルが `キュー画面の色を見直す タイトル（この下の行に入力してください）` になる。案内が issue へ出ていくより作成を止める方が良いので `ok` を偽にする（一致する行を捨てる形は、人が引用した行が黙って消える）
- **CRLF で保存された下書きは、行を分けた直後に各行の末尾の `\r` を落とす**。落とさないと本文が 2 行以上のときに行の中に `\r` が残り、そのまま issue の本文になる。行末の空白は本文では落とさない（Markdown は行末の空白 2 つを改行として読むので、落とすと人が書いた改行が消える）
- **概要のプレースホルダー行がタイトル側より前にある、またはどちらかが無い下書きは「見つからない」として扱う**。中止の文言は 1 つ（`作成を中止しました（プレースホルダー行が見つかりません）`）にし、どちらの行が壊れているかで文言を分けない（人がすることは「エディタをもう一度開いて書き直す」の 1 つで、文言を分けても行動が変わらない）
- **検査の順は エラー → プレースホルダー → タイトルが空 → 本文が空 とする**。分割できない下書きからは「タイトルが空」も導けないので、分割の可否が先に来る
- **`SplitNewIssue` は `(title, body string, ok bool)` を返す**。呼び出し元は `internal/ui/new.go` の 1 か所で、`ok` が偽のときだけ新しい中止の枝に入る。エラー値（`ErrEmptyTitle` のような）を足す形は採らない。`action.CreateIssue` の検査（空・routine マーカー）は書き込みの直前の不変条件で、こちらは下書きの形の問題なので、同じ仕組みに混ぜない
- **`action.CreateIssue` は変えない**。空・routine マーカーの検査と `gh` の呼び出しはこの change の対象外
- **確認画面の見た目と `e` の振る舞いは変えない**。`e` は編集後の下書きそのもの（プレースホルダー行を含む）を返す（issue #17 の指定）。確認画面が見せる `タイトル: <タイトル>` は分割後の値なので、プレースホルダー行は出ない
- **タイトル欄に複数行書かれたら、改行を半角空白 1 つに置き換えて 1 行にする**（人の回答 Q1: A）。各行の前後の空白を落として空行を捨て、残った行を半角空白 1 つで連結する。GitHub の issue のタイトルは 1 行なので、複数行のまま渡す道は無い。連結を選ぶと書いた文字が 1 つも消えず、連結後の姿は確認画面の `タイトル: <タイトル>` が `y` の前に見せるので、意図と違えば `e` で編集に戻って直せる。中止（選択肢 B）は改行 1 つの取りこぼしで下書きごと失い、最初の 1 行だけを採る形（選択肢 C）は消えた行に気づけないので退けた

## 延期した判断と残るリスク

- **本文側の書式の案内は入れない**。issue #17 が求めているのは概要のプレースホルダー行 1 本だけで、`## やりたいこと` のような見出しの雛形は入れない。issue の本文の書式を loop-cli が決める話になり、この change の範囲を超える。必要になったら別 issue で起票する
- **GitHub の issue テンプレート（`gh issue create --template`）は取り込まない**。s15 が Non-Goals に置いた判断をそのまま引き継ぐ
- **プレースホルダーの文言は固定で、設定で変えられない**。変えたい要望が出るまで設定項目を作らない（CLAUDE.md「投機的な機能を書かない」）
- **タイトル欄の複数行を連結すると、日本語の文の連結点に半角空白が 1 つ入る**（Q1: A の結果として受け入れる）。`キュー画面の色を見直す` と `（配色）` を 2 行で書けば `キュー画面の色を見直す （配色）` になる。確認画面で見えるので `e` で直せる
- **タイトル欄に長い行を何本も書くと、連結したタイトルが GitHub の上限を超えて作成が失敗し得る**。止まるのは `gh issue create` で、`new-issue`「作成の結果をステータスに出し、再取得しない」の失敗の経路（フッタに赤で `<作成先> の issue 作成に失敗: <エラー文字列>`）に落ちる。長さの検査を `internal/action` に足すことはしない（上限の値を loop-cli 側で持つと GitHub の変更に追従できず、失敗の経路は既にある）
- **案内の文言そのものを引用した issue は TUI から起こせない**。区切り以外に一致する行が残る下書きを分割しないので、`概要（この下に入力してください）` の文言を直したいという issue はブラウザで起票する。s15 が routine マーカーで受け入れた代償と同じ形である
- **プレースホルダー行を消した下書きは、中止のときに一時ファイルごと消えて書き直しになる**。s15 の「タイトルが空」「本文が空」と同じ既存の挙動で、この change では直さない。確認画面まで進めば `e` で下書きが戻る
- **s15 から `n` を使っている人が、プレースホルダー行を消して 2 行だけ書くやり方をすると作成できなくなる**。中止の文言が理由を名指しし、エディタを開けば毎回プレースホルダー行が入っているので 2 回目からは形に慣れる
- **`n` の下書きを画面で確かめる手立ては単体テストだけである**。TUI は本番では live の `gh` を使い、fixture で画面を開く経路が無い（`cmd/loop-cli-dev` はプレーンテキスト出力のみ）。初期の下書きはスタブ `Editor` が受け取る `initial` の検証で担保する（s15 と同じ形）
