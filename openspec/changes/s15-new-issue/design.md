## Context

キューを見ている人が「これは別 issue だ」と気づく瞬間は、カードを読んでいる最中である。そのときリポジトリは画面が既に見せているので、人に残る仕事はタイトルと本文を書くことだけである。
`gh` 側の `CreateIssue(ctx, repo, title, body)` は s03 が実装済みで、`gh issue create -R <repo> --title <title> --body-file -` を呼び、標準出力の末尾行（作成された issue の URL）を返す（`internal/gh/client.go:299`）。`--label` を渡さない実装で、human-turn-signals.md 不変条件 6「Issue 作成は承認ではない」と既に一致している。
`internal/ui` には下書きを人に書かせる道具が 1 つある。`Editor`（`func(initial string) tea.Cmd`。`internal/ui/editor.go`）で、`a` が使っている。`huh` のフォームは `cmd/loop-cli` の onboarding だけが使い、`internal/ui` の中には無い。
mvp.md キーバインド表の `n` は「フォーム: リポジトリ・タイトル・本文」と書いているが、issue #6 はリポジトリを選ばせない形を求めている。

## Goals / Non-Goals

**Goals:**
- キュー・カード詳細・PR 詳細の 3 画面から、画面が見せている対象のリポジトリに新しい issue を作れる
- タイトルと本文を `$EDITOR` の 1 枚のテキストで書き、作成前に何がどこに入るかを確認できる
- 作成した issue の URL を人に返す
- ラベルを 1 つも付けない

**Non-Goals:**
- 作成先リポジトリの選択 UI（issue #6 が明示的に外している）
- ラベル・assignee・milestone・テンプレート（issue のテンプレートは GitHub 側の機能で、`gh issue create` に `--template` を渡す道はこの change では使わない）
- 作成後に対象 1 件を再取得すること（D-002。s18 が担当する）。作成した issue の詳細画面をその場で開くこと
- mvp.md キーバインド表の `s`（即着手）。同じ s15 の枠だが、この issue の範囲外
- 作成した issue を `t` で `stage:todo` にする一連の操作の自動化（不変条件 6 は人が続けて `t` を押すと定めている）

## Decisions

### 作成先は画面の対象から決め、リポジトリを選ばせない
`a` の `answerTarget`（`internal/ui/answer.go:60`）と同じ決め方にする。キュー画面は選択行の主体、カード詳細は `Card.Issue`、PR 詳細はその PR で、そこから `Repo` だけを取り出す。
選択の UI を持たないので、複数リポジトリを横断しているときに「今どのリポジトリに作ろうとしているか」は人の頭の中にしか無い。これは確認画面の 1 行目に作成先を出すことで補い、違えば `Esc` で中止して行を選び直してもらう。
代替案として、mvp.md の記述どおりに設定のリポジトリ一覧から人へ選ばせる形も採れる。毎回その選択操作が入り、カードを見て気づいた流れが切れるので採らない。

### 下書きは 1 枚のテキストで書かせ、1 行目をタイトルにする
`internal/ui` の書き込み系の下書きはすべて `Editor` を通っており、CLAUDE.md「パターン競合は平均化しない」に従って主流に乗せる。`huh` のフォームを `internal/ui` に持ち込むと、下書きの経路が 2 つになる。
タイトルと本文の分け方は「最初の改行まで」の 1 規則だけにする（`action.SplitNewIssue`）。見出し記号（`# `）を剥がす、`---` で区切る、といった規則を足すと、人が書いた字面と作られる issue が一致しなくなる。
エディタに渡す初期テキストは空にする。書式の案内をテキストに入れると、それがそのままタイトルになる事故が起きる。書式は確認画面の `タイトル: <タイトル>` の行が見せる。

### 確認画面は必ず出し、`a` / `m` の確認画面とは別の状態にする
`a` の確認画面は「不変条件に触れる本文のときだけ」出る警告の画面で、`y` は投稿を意味する。`n` の確認画面は毎回出て、`y` は作成を意味し、見せるものはタイトルと本文の分かれ方である。
1 つの画面状態に 3 つの意味を持たせると `y` の意味が状態によって変わるので、s14 が merge の確認画面を別に持った判断と同じ理由で、画面の状態を 1 つ増やして 8 つにする。
issue の作成は取り消せない書き込み（GitHub の issue は close できても消せない）なので、警告が無くても必ず確認を挟む。

### 編集がどちらの経路で始まったかは `Model` が覚える
編集完了のメッセージは本文とエラーだけを運び、`a` と `n` のどちらで始まったかを持たない。`Editor` が返すコマンドは外部プロセスの実行を伴い、包んで別のメッセージに変える形を取れない。
そこで `Model` が「今の編集はどちらの経路か」を保持し、編集完了を受け取ったときにその値で振り分ける。**記録するのはエディタを開く 4 つの入口すべて**（`a`、`n`、回答の確認画面の `e`、作成の確認画面の `e`）で、次にエディタを開くまで消さない。
作成や中止で消す形にすると、作成の確認画面の `e` で開き直した編集の完了が回答の経路に落ち、`Model` に残った直前の回答対象（`a` を一度も押していなければゼロ値）へ下書きがコメントとして投稿される。エディタを開く操作と経路の記録を同じ場所に置いて、消す側の処理を作らない。
代替案: 編集完了のメッセージに経路を足す。`Editor` の型（`func(initial string) tea.Cmd`）を変えることになり、`a` 側と `ExternalEditor` の spec に波及するので採らない。

### 検査は `internal/action` に置き、`internal/ui` は判定を持たない
`action` は書き込みの直前の層で、不変条件の判定を 1 か所に集めるために存在する（`internal/action/action.go` のパッケージコメント）。空のタイトル・空の本文・routine マーカーの判定は `action.CreateIssue` が持ち、`internal/ui` は `action.SplitNewIssue` と `action.HasRoutineMarker` を呼ぶだけにする。
`ui` がマーカーを見るのは「確認画面に `y` を出すかどうか」を決めるためで、判定そのものは `action` の関数を借りる（s10 が `action.HasRoutineMarker` を `ui` から呼んでいるのと同じ形）。

### `blocked-by:` 行は検出せず、routine マーカーは止める
不変条件 8 は「人のコメントに `blocked-by:` で始まる行を含めない」で、dispatcher が正本にするのはコメントである。issue の本文は正本にならないので、`a` の警告をそのまま持ち込まない。
`depends on #m` を本文に書いた issue は dispatcher が依存として読むが、これは人が意図して書くものなので止めない。
マーカーの扱いが逆向きになるのは、不変条件 7 の 1 文目が「**TUI は `<!-- routine -->` を書かない**」と書き先を限定していないためである（不変条件 8 は「回答エディタは投稿前に検出して警告する」と経路を名指ししている）。dispatcher がその文字列を読むかどうかで線を引かず、docs の文面どおり、TUI から GitHub へ出ていく文字列にマーカーを 1 つも混ぜない。
この結果、マーカーそのものを引用した issue（「マーカーの判定が壊れている」類）は TUI から起こせない。loop-cli 自身の開発では起こり得るが、そのときはブラウザで起票する。docs の不変条件を TUI 側で緩める判断は、この change では採らない。

### 作成の結果はステータスに URL を出すだけにする
`Cards` を書き換えず、取得もやり直さない（s10 / s11 / s14 と同じ）。作った issue は次の `R` か自動更新で「バックログ」に現れる。
URL を出すのは、作った直後にブラウザで開いて続きを書きたい人のためである。TUI から自動でブラウザを開くところまではやらない（`o` の意味が変わる）。
文言は `issue を作成しました: <URL>` にして、`s10` / `s11` / `s14` が採った `<表示名> を…` の形を外す。フッタは省略記号を付けずに端末幅で切るので（`internal/ui/view.go`）、`SugiKent/loop-cli に issue を作成しました: https://github.com/SugiKent/loop-cli/issues/123` は 90 列になり、幅 80 の端末では URL の末尾 10 列が黙って落ちて使えない文字列が残る。作成先を落とせば 69 列に収まり、URL 自身がリポジトリ名を含むので情報も減らない。

## Risks / Trade-offs

- [人が本文から書き始めると、1 行目が本文になってタイトルが期待と違うものになる] → 確認画面が `タイトル: <1 行目>` を見せるので、`y` を押す前に気づける。`e` で編集に戻れば下書きはそのまま開く
- [空行から書き始めるとタイトルが空になり、`作成を中止しました（タイトルが空）` だけが出て下書きが消える] → 下書きは一時ファイルごと消える（`Editor` の既存の振る舞い）。書き直しになるが、確認画面まで進めば `e` で戻れる。中止のステータスに理由を書いて、何が足りなかったかは伝える
- [作成先の取り違えに気づくのが確認画面（書き終わった後）なので、間違っていたら `Esc` で下書きごと捨てて選び直すことになる] → 作成先は確認画面の 1 行目にあり、`y` を押す前に必ず目に入る。エディタを開く前に作成先を見せる案は Q3。issue #6 の「どの repo に作るのかを画面上に明示する」を、この change は確認画面で満たしている
- [本文が必須なので、タイトルだけの軽い issue を作れない] → issue #6 の決定に従う。routine が読む材料の無い issue を作らないことを優先する
- [作成した issue がキューに現れるまで最大で自動更新の 1 周期（既定 120 秒）かかる] → ステータスの URL がその間の唯一の手掛かりになる。s18 が入るまでの既知の穴で、`a` / `t` / `m` と同じ扱い
- [作成中に `q` / `Ctrl+C` を押すとプログラムが終わり `gh` も `ctx` ごと止まる] → `a` / `m` と同じ既存の穴。作成中は `<repo> に issue を作成中` を出して押させない材料にする
- [同じ下書きで `y` を 2 回押すと issue が 2 つできる] → `y` は確認画面を抜けて書き込み中フラグを立てるので、2 回目の `y` は届かない。作成が終わった後にもう一度 `n` から始めれば別の issue になるが、それは人の操作である
- [キュー画面のフッタに `n 新規` が出ないので、キューを見ているだけでは `n` の存在に気づけない（Q2 が B のとき）] → `?` のヘルプと、詳細画面のフッタが入口を見せる。キュー画面のヒントは 80 列で埋まっており、足すと幅 80 の端末で `q 終了` が常に切れる
- [mvp.md と実装が食い違ったまま残る（Q1 が B のとき）] → design.md に逸脱として残し、mvp.md を読む人が実装と読み比べる必要がある

## 未決事項（実装者が選ぶ既定値）

| 論点 | 既定値 | 理由 |
| --- | --- | --- |
| エディタに渡す初期テキスト | 空文字列 | 書式の案内を入れるとそれがタイトルになる。書式は確認画面が見せる |
| 選択行が無いときの `n` | 画面を変えず、ステータスに `新規作成の対象がありません` を出す | `a` / `m` は黙って何もしないが、`n` は「作りたい」という意思に対する応答が無いと理由が分からない。s22 の `URL がありません` と同じ形にする |
| 確認画面に出す項目 | `新規 issue の確認: <repo>` / `タイトル: <タイトル>` / マーカーの警告行 / 区切り線 / 本文 | 作成先とタイトルの分かれ方が `y` を押す前に必要な情報のすべてである |
| 確認画面のスクロール | しない（残りの高さで切る） | s10 / s14 の確認画面と同じ |
| `e` でエディタに渡す下書き | 編集後のテキストそのもの（タイトルと本文に分ける前の形） | 人が書いた字面をそのまま返す。分けて組み直すと空行の数が変わる |
| 一時ファイルの名前 | `loop-cli-draft-*.md`（`loop-cli-answer-*.md` から変える） | `Editor` を `a` と `n` で共有する。エディタは開いているファイル名を人に見せる |
| 作成の `ctx` | 30 秒 | s10 / s11 / s12 / s14 と同じ `postTimeout` |
| 成功のステータス文言 | `issue を作成しました: <URL>`（作成先を入れない） | 幅 80 の端末で URL の末尾が切れないため。Decisions「作成の結果はステータスに URL を出すだけにする」 |
| 確認画面から詳細画面へ戻るときの寸法 | 作り直さない（s10 / s14 の確認画面と同じ） | 3 つの確認画面で規則を割らない。確認中のリサイズが詳細に反映されない穴は 3 つに共通で、直すなら別 change |
| UI 側のマーカーの見方 | 下書き全体に対して `action.HasRoutineMarker` を 1 回呼ぶ | `SplitNewIssue` は空白を落として分けるだけなので、タイトルと本文を別々に見た結果と一致する |
| 作成中に押した `o` / `?` / `u` | 受け付ける（書き込みではない） | s12 `browse-open`「書き込み中でも `o` を受け付ける」と同じ |
| 確認画面での取得完了メッセージ | `Cards` と最終更新時刻は更新し、作成先と下書きは変えない | s10 / s14 の確認画面と同じ |
| 確認画面の `q` / `Ctrl+C` | 終了コマンドを返す | s10 / s14 の確認画面と同じ |
| 詳細画面のフッタでの `n 新規` の位置 | `m merge` の次、`o ブラウザ` の前 | mvp.md キーバインド表の並び。`m` を `t` の次に置いたのと同じ規則 |
| キュー画面のフッタのヒント | 80 列のまま据え置き、`n 新規` を出さない | s14 が移動系のキーを落としてまで守った 80 列の budget を保つ。詳細画面のヒントは既に 80 列を超えていて切り詰め前提なので、そちらには足す |
| ヘルプ画面の `n` の行の文言 | `選択中の repo に issue を作る（確認あり）` | 「どこに作られるか」がこのキーの唯一の疑問点なので、それを行に書く |
