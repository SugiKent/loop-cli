## Context

動機は `proposal.md` の Why にある。設計の前提になる現状は次の 4 点。

- **色の材料は既に手元にある**。`internal/fetch` は運用方式の判定のためリポジトリごとに `ListLabels` を毎回 1 回呼び（`card-fetch`「Fetch はリポジトリごとにラベル一覧を取り運用方式を判定する」）、`gh.RepoLabel` は `Name` / `Description` と並べて `Color` を持つ。ラベル一覧画面（`L`）は `[]gh.RepoLabel` をそのまま状態に持っている
- **issue / PR に付いているラベルは名前しか持たない**。`model.Issue.Labels` / `model.PR.Labels` は `[]string` で、`model.IssueFromSearch` が `gh.Label` から名前だけを写している（`gh.Label` は「id / color / description は読み捨てる」）
- **画面の幅の計算はすべて `ansi` パッケージを通っている**。`pad` は `ansi.StringWidth`、切り詰めは `ansi.Truncate`、折り返しは `wrapToWidth`。どれも ANSI エスケープを幅に数えない
- **既存の表示テストは `ansi.Strip` してから文言を照合する**（`internal/ui/view_test.go`）。`card-detail` / `merge-pr` / `close-issue-pr` / `label-picker` / `queue-screen` の Scenario はすべてこの読み方で書かれている

## Goals / Non-Goals

**Goals:**

- 任意の 16 進ラベル色に対して、背景色と文字色のコントラストを保証する規則を 1 つ決める
- 色の規則を `internal/ui` の 1 か所に集め、7 つの描画箇所が同じ関数を通る
- 表示テキスト（ANSI を除いた文字列）を変えず、幅・折り返し・切り詰めの既存の規則と Scenario をどこも直さない
- 追加の `gh` 呼び出しを 0 にする

**Non-Goals:**

- キューの表にラベル列を足すこと。表の行の色は種別で固定のまま（mvp.md）
- 色を切る設定項目を足すこと。端末側の色数への追随は Lip Gloss v2 のダウンサンプリングに委ねる（D-003）
- ラベル一覧画面と `internal/fetch` の `ListLabels` 呼び出しの重複を解消すること。どちらも既に存在し、この change は呼び出しを 1 本も増やさない
- Glamour が描く本文・コメントの配色に手を入れること

## Decisions

### D1. 文字色は背景色の相対輝度から黒か白を選ぶ

ラベル色は利用者のリポジトリごとに任意の 16 進値なので、固定の文字色ではコントラストを保証できない。sRGB の各成分を 0–1 に正規化してガンマ逆変換（`c ≤ 0.03928 ? c/12.92 : ((c+0.055)/1.055)^2.4`）を掛け、`0.2126R + 0.7152G + 0.0722B` で相対輝度 `L` を求め、`L > 0.179` なら黒、そうでなければ白を文字色にする。

`0.179` は「黒に対するコントラスト比」と「白に対するコントラスト比」が等しくなる点であり、このしきい値は**定義上、コントラスト比の高い方を選ぶ**。この規則の狙いは、「視認性を維持する」を計算だけで決まる形に落とし、実装者の好みで文字色が動く余地を残さないことにある。

代替案として、より軽い YIQ 式（`(299R + 587G + 114B)/1000 > 128` なら黒）も検討した。式は単純だが選ぶ色がコントラスト比の高い方と一致する保証が無く、「視認性を維持する」の根拠として弱い。計算量はどちらも 1 ラベルあたり数命令で、描画のたびに走っても問題にならない。

境目の近くにある色（`propose` の `0e8a16` は `L ≈ 0.183`）は、GitHub 側でわずかに色を変えると文字色が黒白で入れ替わる。これは規則が「その時点でコントラストの高い方」を選び続けている結果であり、どちらを選んでもコントラスト比は 4.5 前後を保つ。

### D2. 色は ANSI エスケープとしてだけ増やし、表示テキストを変えない

背景色を付けたラベルの左右に空白を足すと GitHub の見た目に近づくが、`labels: propose question` が `labels:  propose   question ` に変わる。すると `card-detail` / `merge-pr` / `close-issue-pr` / `queue-screen` の期待値、PR 一覧行が 1 行に収まるかの判定、ヘッダ領域の行数（`detailHeader` が高さを詰める規則）がすべて動く。色を足すだけの change が、幅に関わる仕様を横断して書き換えることになる。

そこで空白を足さず、名前の文字の範囲だけを塗る。`ansi.Strip` した結果が今と 1 文字も変わらないので、既存 Scenario はすべてそのまま通り、色が付いたことは ANSI を除く前の文字列を見る新しい Scenario で検証する。

### D3. ラベルは背景色 + 文字色、状態語は文字色だけ

`[propose] open  labels: propose question` のような行では、段階・PR の状態・ラベルが同じ 1 行に並ぶ。ラベルだけに背景色を置くと、帯になっている語がラベル、文字だけ色が付いている語が状態、と見た目で区別できる。状態語にも背景色を置くと 1 行が帯だらけになり、どれがラベルか読み直すことになって issue の目的に反する。

状態語にはプロジェクト固定の 4 色を使う。`mergeable` の値や checks の状態は GitHub のラベルではないので引ける色が無く、良し悪しの対応（緑=良い / 赤=悪い / 黄=保留 / 紫=merged）を固定すれば読み手の学習が 1 回で済む。値は mvp.md が行の色に使った出典と同じく既存のラベル色から採る: 緑 `#0E8A16`（`propose`）、赤 `#B60205`（`blocked`）、黄 `#FBCA04`（`stage:todo`）、紫 `#5319E7`（`archive`）。

色を付ける語は「値の語」だけにし、`checks ` や `mergeable ` の見出しは無色のままにする（`checks 緑` の `緑` だけを塗る）。見出しまで塗ると、行のどこを読めば状態か分からなくなる。

### D4. ラベル色は `fetch` の `Result` から `Model` へ渡し、ラベル一覧画面だけは自前の値を使う

issue / PR に付いているラベルは名前しか持たないので、名前から色を引く表が要る。`model.Issue.Labels` を構造体の列にすると `internal/classify` / `internal/action` / `internal/snapshot` とそれぞれのテストまで波及するが、色は分類にも書き込みにも一切使わない表示の都合でしかない。

そこで `Result` に「リポジトリ名 → ラベル名 → 色」の表を足し、`Model` は運用方式の表（`queue-screen`「Model はリポジトリごとの運用方式を持つ」）と同じ規則 — 取得成功で丸ごと差し替え、取得失敗では触らない（D-002） — で持つ。`ListLabels` が失敗したリポジトリはその表に入らず、そのリポジトリのラベルは色無しで描かれる。方式の表と同じ挙動なので、覚えることが増えない。

ラベル一覧画面は例外で、自分が `L` で取った `[]gh.RepoLabel` の `Color` をそのまま使う。この画面は取得したてのリポジトリのラベル定義そのものを並べており、別の表を引くと同じ画面の中で新旧 2 つの色が混ざる。

### D5. 描画はセグメントを組み立てて行う（行への後追い置換をしない）

出来上がった行に対して語を検索して色を付けると、本文やタイトルに現れた `MERGEABLE` や `propose` まで塗ってしまう。各描画箇所は今も `fmt.Sprintf` / 文字列連結で行を組んでいるので、その連結の材料を塗ってから連結する。塗る関数は `internal/ui` の新しい 1 ファイルに 2 つ（ラベル名用・状態語用）だけ置く。

## Risks / Trade-offs

- **[端末が背景色を出せない・256 色に落とす]** → Lip Gloss v2 がレンダラのプロファイルに合わせてダウンサンプリングする（D-003）。落とした先でも文字色と背景色の関係は保たれる。既存の行の色（`kindStyle` の `異常` は黄背景）が同じ仕組みで動いている実績がある
- **[`gh` が返す色が空、または 6 桁の 16 進でない]** → 色を付けずにその名前を描く。ラベルが消えたり文字が変わったりはしない。境界での検証はここ 1 か所に閉じる
- **[明るい背景の端末で、明るいラベル色に白文字が乗る]** → 起こらない。D1 のしきい値は明るい背景色に対して必ず黒文字を選ぶ。端末の背景色は関係しない（ラベルは自前の背景色を敷く）
- **[`ListLabels` が失敗したリポジトリのラベルだけ色が付かない]** → そのリポジトリは運用方式も引けず、既に `Result.Modes` から落ちている状態。色だけ別扱いにはせず、同じ落ち方に揃える
- **[状態語の色の表に無い値が今後 GitHub に増える]** → 表に無い値は無色で描く。読めなくなることはなく、表に 1 行足せば追随できる

## 未決事項

docs/mvp と docs/domain が沈黙している点と、実装者が採る既定値。

- **相対輝度のしきい値**: 既定値 `0.179`（黒と白のコントラスト比が等しくなる点）
- **`CANCELLED` / `SKIPPED` / `NEUTRAL` の checks**: 既定値は色を付けない（成功でも失敗でもなく、注意を引く必要がない）
- **`取得失敗` の色**: 既定値は赤。フッタのエラー表示が同じ赤（`errorStyle`）を使っており、取得できていないことを同じ色で示す
- **ラベル名を囲む角括弧（`[propose]` / `[question]`）**: 既定値は括弧を塗らず、中の名前だけを塗る。括弧は画面の構造を示す記号で、ラベルの一部ではない
