## Context

`n` の下書きは `Editor`（`func(initial string) tea.Cmd`。`internal/ui/editor.go`）が一時ファイル `loop-cli-draft-*.md` に `initial` を書いて `$EDITOR` を開き、終了後にファイルの中身を編集結果として返す仕組みである。`initial` に何を渡すかを決めているのは `internal/ui/new.go:47` の 1 行だけで、`a` は同じ仕組みに `action.AnswerTemplate(comments)` の結果を渡している（`internal/ui/answer.go:56`）。
`s15-new-issue` はこの `initial` を空文字列にした。理由は分割規則が「最初の改行でタイトルと本文に分ける」1 本だったためで、案内の行を入れるとその行がそのままタイトルになる（`s15-new-issue/design.md`「下書きは 1 枚のテキストで書かせ、1 行目をタイトルにする」）。
`SplitNewIssue` は `strings.Cut(text, "\n")` の 1 行の実装で（`internal/action/newissue.go:16`）、分割に失敗する入力が無い。どんな下書きでも「タイトルと本文」に分かれるので、呼び出し側は分割の可否を判定できない。
issue #17 は案内の 2 行そのものを区切りにする形を求めており、これは分割規則の置き換えである。`action.CreateIssue` の検査（空・routine マーカー・`gh` の呼び出し）は書き込みの直前の不変条件で、この change では触らない。

## Goals / Non-Goals

**Goals:**
- エディタを開いた時点で、どこにタイトルを書きどこに概要を書くのかが画面に出ている
- プレースホルダー行が issue のタイトル・本文に混ざらない
- 区切りが壊れた下書きを、理由の分かる形で作成前に止める
- 区切りに使う文字列と分割する関数が 1 つのパッケージに並び、片方だけの変更で壊れない

**Non-Goals:**
- 本文側の書式の案内（`## やりたいこと` のような見出しの雛形）。issue #17 は概要のプレースホルダー行 1 本だけを求めている
- GitHub の issue テンプレート（`gh issue create --template`）の取り込み
- 確認画面の見た目の変更。出す項目と順番は s15 のまま
- `a`（回答）の下書き。`action.AnswerTemplate` が既に事前入力しており、区切りを持つ形にする必要が無い
- プレースホルダー行を人が編集できるようにすること（設定で文言を変える等）

## Decisions

### 区切りは「行の前後の空白を落とした結果が文言と一致する」ことで判定する
行の完全一致にすると、エディタが行末に残した空白や CRLF（`\r`）で区切りが失われ、書いた下書きが丸ごと中止になる。前後の空白を落としてから比べれば、この 2 つは区切りとして働く。
部分一致（`strings.Contains`）や接頭辞一致は採らない。人が案内の行に続けて書いた行（`タイトル（この下の行に入力してください）キュー画面の色を見直す`）を区切りとみなすと、その行に書いた文字が消える。issue #17 の「人が消したり書き換えたりすると分割できない」は、書き換えを検出して止める側に寄せる。

### 区切りに使った 2 本以外に案内の行が残っていたら分割しない
先頭優先で 2 本の区切りを決めるだけでは、案内の行が 3 本以上ある下書き（Vim の行複製、確認画面の `e` で開き直した下書きに案内をもう 1 組貼り直した、案内の文言を本文に引用した）で、案内の文字列がタイトルや本文に入って GitHub へ出ていく。たとえば `タイトル（…）` / `キュー画面の色を見直す` / `タイトル（…）` / 空行 / `概要（…）` / `本文` と並んだ下書きは、挟まれた行を連結すると `キュー画面の色を見直す タイトル（この下の行に入力してください）` になる。
そこで、区切りに使った 2 本を除いてもプレースホルダーの文言と一致する行が残っていたら、分割せず `ok` を偽にする。案内が issue へ出ていくより、作成を止めて書き直させる方が良い。
落とす形（一致する行を捨ててから連結する）は採らない。人が本文に引用した行が黙って消え、確認画面でも消えたことに気づけない。
この結果、案内の文言そのものを引用した issue は TUI から起こせなくなる。s15 が routine マーカーで同じ代償を受け入れており（`internal/action` がマーカーを含む下書きの作成を止める）、そのときはブラウザで起票する。判定の形も揃う。

### CRLF は行末の `\r` だけを落とす
行を分けた直後に各行の末尾の `\r` を落とす。落とさないと、CRLF で保存した下書きの本文が 2 行以上あるときに行の中に `\r` が残り、そのまま issue の本文として GitHub へ出ていく（前後の空白を落とす処理は末尾の 1 つしか消せない）。
行末の空白そのものは本文では落とさない。Markdown は行末の空白 2 つを改行として読むので、落とすと人が書いた改行が消える。区切りの判定は前後の空白を落としてから比べるので、行末の空白があっても区切りとして働く。

### 分割できなかったことは戻り値の `ok` で返す
`SplitNewIssue` の戻り値を `(title, body string, ok bool)` にする。呼び出し元は `internal/ui/new.go` の 1 か所で、`ok` が偽のときだけ新しい中止の枝に入る。呼び出し側が見る分岐が 1 つなので、種類を持つ値にする理由が無い。`strings.Cut` と同じ comma-ok の形で、戻り値の数が変わるぶん呼び出し元の書き換えをコンパイラが強制する。
述語を別に足す形（`SplitNewIssue` を 2 値のまま残し、`HasNewIssuePlaceholders(text) bool` を並べる。`internal/ui/new.go` が `action.HasRoutineMarker` を呼んでいるのと同じ形）は採らない。区切りの探索が判定と分割の 2 か所に分かれ、片方だけを直したときに「真を返すのに分割できない」状態が作れる。マーカーの判定は下書きの中に文字列があるかを見るだけで分割と無関係なので、あちらは述語で足りている。
エラー値（`action.ErrEmptyTitle` のような `errors.Is` で判別する形）も採らない。`action.CreateIssue` のエラー値は `gh` を呼ぶ前に不変条件で止めたことを表すもので、下書きの形の問題はそこに属さない。

### プレースホルダーの文言と初期の下書きは `internal/action` の定数にする
`internal/ui` が文言を持つと、区切りの判定（`internal/action`）と初期テキスト（`internal/ui`）が別のパッケージに分かれ、片方だけを直したときに「開いた下書きが自分で分割できない」状態になる。`a` が `action.AnswerTemplate` を使っているのと同じ形で、`internal/action` が下書きを提供して `internal/ui` はそれを渡すだけにする。
初期の下書きは中身が固定なので定数にする。`AnswerTemplate` が関数なのはコメント列から中身を組み立てるからで、こちらは引数を取らない。

### タイトル欄の複数行は半角空白 1 つで連結する
人の回答（Q1: A）で確定した判断である。GitHub の issue のタイトルは 1 行なので、複数行のまま渡す道は無い。
連結を選ぶのは、書いた文字が 1 つも消えず、連結後の姿を確認画面の `タイトル: <タイトル>` が `y` の前に見せるためである。中止（選択肢 B）は改行 1 つの取りこぼしで下書きごと失われ、最初の 1 行だけを採る形（選択肢 C）は消えたことに気づけない。
実装は「区切りに挟まれた各行の前後の空白を落とし、空になった行を捨て、残りを半角空白 1 つで連結する」1 本の規則にする。1 行だけ書いた場合の結果は前後の空白を落とすだけの形と一致するので、行数で分岐しない。

### 中止の文言は区切りごとに分けない
タイトル側の区切りが無い・概要側の区切りが無い・順番が逆・余分な案内の行が残っている、のいずれでも `作成を中止しました（プレースホルダー行が見つかりません）` にする。人が次にすることは「エディタを開き直して書き直す」の 1 つで、原因を伝え分けても行動が変わらない。
この文言は表示幅 56 列で、幅 80 の端末でも切れない。`internal/ui/view.go` の `footer` は、キーヒントとステータスが並ばない幅ではステータスだけを端末幅で切って出すので、ヒント（キュー画面は 80 列）に押し出されて欠けることは無い。

### 分割の可否は空の検査より先に見る
区切りが壊れた下書きでは、タイトルも本文も空文字列になる。空の検査を先に置くと `作成を中止しました（タイトルが空）` が出て、人は「タイトルを書いたのに」と読む。区切りの有無を先に見れば、消したプレースホルダー行が原因であることが伝わる。

## Risks / Trade-offs

- [s15 から `n` を使っている人が、プレースホルダー行を消して 2 行だけ書くやり方をすると作成できなくなる] → 中止の文言が理由を名指しする。エディタを開けば毎回プレースホルダー行が入っているので、2 回目からは消さない形に慣れる
- [プレースホルダー行を消した下書きは、中止のときに一時ファイルごと消えて書き直しになる] → s15 の「タイトルが空」「本文が空」と同じ既存の挙動で、この change では変えない。確認画面まで進めば `e` で下書きが戻る
- [プレースホルダーの文言を後から変えると、変えた後に開いた下書きしか分割できない] → 下書きはエディタを閉じるまでの寿命しか無く、跨って残らない。文言と分割が同じパッケージに並ぶので、変えるときに両方が目に入る
- [人が案内の行を「消してよい」と読み、消してから書く] → 文言に「この下の行に入力してください」と書き、消せとは書かない。それでも消す人には中止の文言が伝える。案内の行に「消さないでください」を足す案は、タイトル欄の直前の行が長くなって読みにくくなるので採らない（issue #17 の文言をそのまま使う）
- [タイトル欄に複数行書くと、日本語の文の連結点に半角空白が 1 つ入る] → 確認画面の `タイトル: <タイトル>` で見えるので `e` で直せる。Q1 の回答で変わり得る
- [`n` を押すとエディタが空でなくなるので、Vim で `dd` の癖がある人がプレースホルダー行を消してしまう] → 上と同じく中止の文言で伝える
- [`SplitNewIssue` の戻り値が増えるので、呼び出し元の 1 か所を直し忘れるとコンパイルが通らない] → コンパイルエラーになるので取り逃がしが起きない（戻り値の数が変わるため、`ok` を無視した形も明示しなければ書けない）

## 未決事項（実装者が選ぶ既定値）

| 論点 | 既定値 | 理由 |
| --- | --- | --- |
| タイトル欄の複数行 | 半角空白 1 つで連結する | 人の回答（Q1: A）で確定した。正本は proposal の確定した判断で、この行はその参照である。人が書いた文字を消さず、確認画面が連結後の姿を見せる |
| プレースホルダー行が下書きに 2 度以上現れたとき | 区切りは先頭から最初の 1 本ずつを採り、それ以外に一致する行が残っていたら分割しない（`ok` を偽にする） | 先頭優先だけでは案内の文言がタイトル・本文に入って GitHub へ出ていく（Decisions の「区切りに使った 2 本以外に案内の行が残っていたら分割しない」） |
| 概要のプレースホルダー行がタイトル側より前にある下書き | 分割できないものとして扱う | タイトルの区切りより後ろで概要の区切りを探すので、追加の判定を書かずにこうなる |
| 本文の中の空行 | そのまま残す（前後の空白だけ落とす） | s15 の本文の扱いと同じ。issue の本文は複数段落を持てる |
| CRLF で保存された下書き | 行を分けた直後に各行の末尾の `\r` を落とす | 落とさないと本文の行の中に `\r` が残って GitHub へ出ていく。行末の空白は本文では落とさない（Markdown の改行が消える） |
| 分割できなかったときに保持している下書き | 変えない。中止で画面は変わらず、次の `n` が初期の下書きで作り直す | 一時ファイルは `Editor` が消しているので戻せない。確認画面へ進めて `y` を出さない形（routine マーカーと同じ）は、タイトルも本文も空の確認画面になり見せるものが無い。issue #17 も「作成しない。フッタに理由を出す」と定めている |
