## Context

s03 の `GHClient` に `Browse(ctx, repo, number)` があり、`Client` は `gh browse <n> -R <repo>` を実行する。`Fake.Browse` は `Calls` に `Method` `Browse` / `Repo` / `Number` を記録する（`internal/gh/fake.go` で確認済み。この change で `internal/gh` に足すものは無い）。
s08 の `internal/ui` は `New` で `Fetcher` を受け取り、`Init` がスピナーの tick と `fetchCmd(fetcher)` を束ねて返す。取得中は `fetching` が true で、`spinner.TickMsg` は `fetching` の間だけ次の tick を返す。取得の失敗は `errText`、部分失敗は `partial` に持ち、s08 の tasks 3.1 は「取得開始時に両方を空にする（s12 の `R` もこの経路を使う）」と書いたが、実装は `New` で `fetching` を立てるだけで、2 回目以降の取得を開始する経路はまだ無い。`WindowSizeMsg` の処理は `screen` がカード詳細 / PR 詳細のとき `refreshDetail()` を呼ぶ（ヘルプ画面を足しても現状のままで良い。tasks 4.1 で確認する）。`Update` の `KeyPressMsg` は `q` / `ctrl+c` → 確認画面 → `a`（画面判定より先。s11 の `t` も同じ位置に入る想定。tasks 1.1 で確認）→ 画面ごとの振り分けの順で処理し、`updateDetailKey` は `Model` だけを返して Cmd を返せない。
s09 が画面の状態（キュー / カード詳細 / PR 詳細）と詳細の対象、s10 が確認画面と `New(fetcher, client, editor)` の `client` とフッタ右の書き込みステータス（「次の取得が始まったとき、または次に `a` を押したときに消える」）、s11 が `t` と書き込み中フラグの共有（ステータスは「次の `t` か `a`」でも消える）を定めている。フッタのヒントは s11 でキュー画面が `j/k 移動  1-4/Tab タブ  Enter 開く  a 回答  t todo  q 終了`（58 列）、カード詳細が 95 列、PR 詳細が 66 列になっている。`footer()` はヒント単独なら端末幅で切り、ステータスがあってヒント + 1 + ステータスが幅を超えればステータスだけを出す。
mvp.md キーバインド表の `o`（ブラウザで開く。`gh browse` / `open <url>`）、`R`（全件再取得）、`?`（ヘルプ）、画面構成のフッタ例 `Enter 開く  a 回答  t todo  m merge  n 新規issue  o ブラウザ  R 更新  ? ヘルプ  q 終了`、D-002「手動 `R`、自動更新は既定 120 秒」「取得中はステータスバーにスピナー、失敗時は前回結果を維持」、human-turn-signals.md 局面 F「表示して警告、ブラウザで開く」が正本である。ヘルプ画面の構成と閉じるキー、および `o` / `R` / `?` をどの画面で受け付けるかは docs に無い。

## Goals / Non-Goals

**Goals:**
- `o` で画面の対象（キュー: 選択行の主体、カード詳細: Issue、PR 詳細: PR）をブラウザで開ける。局面 F のアクション「ブラウザで開く」が TUI から行える
- `R` で s08 の取得をもう一度発行し、`a` / `t` の書き込み結果をキューに反映できる。取得中の多重発行を防ぐ。s13 の自動更新が同じ取得開始の経路を使える
- `?` で、この時点で実装済みのキーの一覧を読める。フッタから移動系のキーを外してもキーが分かる
- `Fake.Calls`（`o`）、呼び出し回数を数える `Fetcher`（`R`）、`View` の文字列（`?`）で `gh` もブラウザも起動せずにテストできる

**Non-Goals:**
- 自動更新・スナップショットキャッシュ・通知（s13）。書き込み後の対象 1 件だけの再取得（s18）。レートリミット表示（s18）
- search 結果の `URL` を `open <url>` で開く経路。mvp.md は `gh browse` / `open <url>` の両方を挙げているが、s03 が `Browse` を `gh browse` で定義済みで、`open` は macOS 固有のコマンドである
- ヘルプ画面のスクロールと、未実装キーの表示。後続 change が自分のキーの行を MODIFIED で足す
- 局面 F の修復（human-turn-signals.md「TUI から自動修復はしない」）

## Decisions

### ファイル構成

```
internal/ui/browse.go        # o のキー処理、対象の決定、browseCmd と browsedMsg、失敗の文言
internal/ui/browse_test.go   # o → コマンド → Fake.Calls / 失敗のステータス
internal/ui/help.go          # ヘルプ画面の状態（戻り先）、キー処理、helpLines と View
internal/ui/help_test.go     # 開閉と戻り先、一覧の内容、他のキー、取得完了の反映
internal/ui/model.go         # 取得開始の共通経路（startFetch）、R、o / ? の振り分け、ヘルプ画面の状態（変更）
internal/ui/view.go          # フッタのヒント、ヘルプ画面の View への振り分け（変更）
```

### `o` は `gh browse` 1 本

s03 の `Browse` は `gh browse <n> -R <repo>` で、issue 番号でも PR 番号でも GitHub がその URL に案内する（`gh browse` は `issues/<n>` を開き、GitHub が PR なら `pull/<n>` に転送する）。search 結果の `URL` を `open <url>` に渡す案は OS ごとのコマンド差（macOS `open` / Linux `xdg-open`）を TUI が持つことになり、`gh browse` が既にブラウザの起動を OS 別に扱っている。`Browse` を使えば `Fake.Calls` で引数を検証でき、`GHClient` に足すものが無い。
対象は s10 の `a` と同じ規則（キュー = `Subject`、カード詳細 = `Card.Issue`、PR 詳細 = その PR）で、表示名も s10 と同じ。`t` と違い PR も対象にする（`gh browse` は PR も開ける）。書き込みではないので書き込み中フラグでは止めない。`o` を連打しても `gh browse` が複数回走るだけで害が無く、排他は持たない。
`Browse` はサブプロセスの起動なので `Model` から直接呼ばず、s10 / s11 と同じくコマンドで実行して `browsedMsg{label string; err error}` を返す。成功時は何も出さない（ブラウザが開くこと自体が結果。ステータスを出すと直後の `a` / `t` の結果と紛れる）。失敗だけ赤で出す。ステータスの置き場と寿命は s10 / s11 と共有する。`o` を押しただけでは前のステータスを消さない（`o` は書き込み中でも受け付けるので、押した時点で消すと進行中の `切り替え中` / `投稿中` が消える）。

### `R` は取得開始の経路を 1 つにして再利用する

`R` と s13 の自動更新が同じ「2 回目以降の取得を開始する」処理を持つ必要がある。現状は `New` が `fetching` を立て `Init` が tick と `fetchCmd` を束ねるだけで、2 回目の取得に向けた状態のリセット（`errText` / `partial` / 書き込みステータスを空にし、`fetching` を立てる）が無い。非公開の `startFetch()`（`Model` を書き換えてコマンドを返す）に集める。`Init` は現状のまま（`New` が `fetching` を立て、`Init` は tick + `fetchCmd` を返す）で `startFetch` を呼ばない。`startFetch` は `fetching` のガードを持たず、呼び手（`R` のキー処理、s13 の tick）が `fetching` を見てから呼ぶ。
スピナーの tick は `fetching` が false になった時点で止まっているので、`R` は `fetchCmd` と一緒に `spinner.Tick` を再発行する。しないとスピナーが止まったまま「取得中」だけ出る。
取得中の `R` は無視する（多重発行しない）。取得中に押した `R` を「完了後にもう一度取得」として溜める案は、完了直後に search 2 回が続けて走り 30 req/分の枠を無駄に使う。
`R` はキュー画面だけにする（既定値）。詳細画面で `R` を効かせても、s09 が詳細の対象を差し替えない規則なので画面には何も起きず、`Esc` で戻ってから `R` と結果が同じになる。確認画面とヘルプ画面でも同様。`R` で `cursor` は先頭に戻さない（s08 の丸め規則だけ。捌いている途中の位置を失わせない）。

### `?` は 5 つ目の画面の状態

s09 / s10 と同じく 1 つの `Model` の `screen` に `screenHelp` を足し、別の Bubble Tea Model を持たない。開いたときの戻り先（`?` を押した画面）を保持し、`?` / `Esc` で戻す。詳細の状態（`detail`）のスクロール位置と展開状態は変えないので、戻れば両方残る。閉じるとき戻り先がカード詳細 / PR 詳細なら `refreshDetail()` を呼んで本文領域の寸法を作り直す（ヘルプ中の `WindowSizeMsg` は `refreshDetail()` を呼ばないため）。`GotoTop` は呼ばない。確認画面から開けないのは、s10 が確認画面のキーを `y` / `e` / `Esc` / `q` に限定しており、回答の途中でヘルプに入る導線を増やさないため。
ヘルプ画面は静的な文字列（`helpLines()`）で、キーの表記を幅 16 に揃えた 15 行。内容は mvp.md キーバインド表の「動作」列の文言を、実装済みの範囲で写す（前半は表の順、後半は表に無いキー）。未実装のキーを出さないのは、押しても何も起きないキーを案内しないため。後続 change はこの Requirement を MODIFIED で写して行を足す。スクロールは持たない（15 行 + 見出し + 空行 = 17 行で、`Model` の既定の高さ 24 に収まる。低い端末では末尾から切る）。
ヘルプ画面でも `fetchedMsg` / `postedMsg` / `toggledMsg` / `browsedMsg` は各 change の規則どおり処理する。s09 の「詳細を開いている間の取得完了」と同じで、メッセージの処理は画面に依存しない。`WindowSizeMsg` の処理は現状 `screen` がカード詳細 / PR 詳細のときだけ `refreshDetail()` を呼ぶので、ヘルプ画面（キューから開くと `detail.card.Issue` が nil）で `cardHeaderLines` が落ちることは無い。現状のままで良いことを確認する。

### フッタから移動系のキーを外す

s11 のキューのヒント（58 列）に `o ブラウザ  R 更新  ? ヘルプ`（30 列）を足すと 88 列になる。`Model` の既定幅 80 で `q 終了` が切れ、初回取得中（スピナー + `取得中` = 8 列）はヒント + 1 + ステータス = 97 > 80 でヒント全体が消え、s10 の `tui-entrypoint`「初期フレームに `q 終了`」が成り立たない。
mvp.md の画面構成のフッタ例は `Enter 開く  a 回答  t todo  m merge  n 新規issue  o ブラウザ  R 更新  ? ヘルプ  q 終了` で、`j/k` と `1-4/Tab` を出していない。これに合わせて移動系のキーをヒントから外し、`?` のヘルプに委ねる。新しいヒントは `Enter 開く  a 回答  t todo  o ブラウザ  R 更新  ? ヘルプ  q 終了` で 64 列。取得中でも 64 + 1 + 8 = 73 ≤ 80 で両方出る。1 ペインの `p プレビュー`（+14）は 78 列で、取得中は 87 > 80 になりステータスだけになるが、これは s08 の 1 ペインでも同じ（72 + 9 = 81）で、この change で悪化させない。
カード詳細 / PR 詳細も同じ理由で `j/k スクロール` を外し、`o ブラウザ` と `? ヘルプ` を足す。カード詳細は 101 列、PR 詳細は 66 列。カード詳細は s11 の時点で既に 95 列と 80 を超えており、この change で組み直さないが、`? ヘルプ` を末尾に置くと幅 80 で `o ブラウザ  ? ヘルプ` が切れてヘルプの入口が見えない。`? ヘルプ` を `a 回答` の前に寄せ（`… g PR へ  ? ヘルプ  a 回答  t todo  o ブラウザ  q 終了`。`? ヘルプ` は 65 列目で終わる）、PR 詳細も同じ順にする（`Esc 戻る` が先頭にあるので狭い端末でも戻れる）。
フッタの切り詰め規則（s08 `footer()`）は変えない。

### `o` / `R` / `?` を受け付ける画面

| キー | キュー | カード詳細 | PR 詳細 | 確認 | ヘルプ |
| --- | --- | --- | --- | --- | --- |
| `o` | 選択行の主体 | Issue | PR | 何もしない | 何もしない |
| `R` | 再取得 | 何もしない | 何もしない | 何もしない | 何もしない |
| `?` | ヘルプを開く | ヘルプを開く | ヘルプを開く | 何もしない | 閉じる |

## Risks / Trade-offs

- [`gh browse` がブラウザを起動できない環境（SSH 先、ブラウザ無し）] → `gh` が非 0 で終わり、`browsedMsg.err` が赤で出る。`gh browse -n` で URL を出すだけにする案は docs に無く採らない
- [`gh browse` が issue 番号と PR 番号を区別しない] → GitHub 側の転送に頼る。s03 の `Browse` の設計をそのまま使い、この change で PR 用の引数を足さない
- [`R` の連打で search の枠を消費する] → 取得中は無視するので、1 回の取得が終わるまで次は発行されない。30 req/分に対して 1 回 2 req
- [`startFetch` がガードを持たないので、呼び手が `fetching` を見忘れると多重発行する] → 呼び手は `R` と s13 の tick の 2 つだけで、両方とも spec に「取得中は何もしない」の Scenario を持つ。`Init` は `startFetch` を呼ばず現状のまま
- [Bubble Tea の複数コマンドの束をテストで実行する方法] → s08 は `Init` の束を実行せず `fetchCmd(fetcher)()` を直接実行した。`R` のテストは束を実行し、得たメッセージが束（各コマンドの列）なら各コマンドを実行して `fetchedMsg` を拾う。spec は型名を断定せず「複数のコマンドの束ならその各コマンドも実行」と書いた
- [キューのフッタから `j/k` が消えて、初見で行移動のキーが分からない] → `? ヘルプ` がフッタにあり、ヘルプの 1 行目が `j / k / ↑ / ↓`。mvp.md のフッタ例も移動系を出していない
- [カード詳細のフッタが 101 列で、幅 100 以下では `q 終了` が切れる] → s11 の時点で 95 列と既に 80 を超えている。`q` は s09 の規則でどの画面でも終了コマンドを返す。`detail_test.go` の `TestDetailFooters` は幅 100 → 120 に直す
- [ヘルプの行を後続 change が足すたびに MODIFIED が要る] → キーの一覧はこの change の Requirement に本文として置き、後続は写して行を足す。行の書式（幅 16 の列 + 説明）を固定しているので追加は 1 行ずつで済む
- [`R` は最初の大文字のキーで、端末からは Shift 付きで届く] → Bubble Tea v2 の `Key.String()` は `Text`（端末が渡す `R`）を返すので、既存のキーと同じ `String()` の比較で足りる。`charm.land/bubbletea/v2` の `key.go` と `github.com/charmbracelet/ultraviolet` の `key.go` で確認済み
- [`WindowSizeMsg` でヘルプ画面から `refreshDetail()` が呼ばれて nil 参照] → 現状の条件（カード詳細 / PR 詳細のときだけ呼ぶ）で起きない。tasks 4.1 で現状のままで良いことを確認する。代わりにヘルプ中のサイズ変更が詳細に反映されないので、ヘルプを閉じるときに `refreshDetail()` を呼ぶ
