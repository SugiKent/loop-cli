## Context

動機は `proposal.md` の Why にある。設計の前提になる現状は 4 点。

- **テンプレートを作る場所は 1 つしかない**。`internal/action/template.go:13` の `AnswerTemplate` が最新の
  routine コメントを選び、`model.ParseQuestions` の結果から `Q<n>: <記号>` の行を組み立てて返す。
  `internal/ui/answer.go:56` がその戻り値をそのまま `openEditor` へ渡し、`ExternalEditor` は一時ファイルに
  書くだけである（`answer-question`）
- **テンプレートはそのまま投稿の本文になる**。編集後の本文は `action.HasRoutineMarker` と
  `action.BlockedByLines` の検査を通り（`answer-question`「編集結果を検査してから投稿する」）、
  引っかからなければ `action.Comment` がそのまま投稿する。テンプレートに足した文字は、
  人が消さない限り GitHub のコメントになる
- **マーカーを含む本文は投稿経路が閉じる**。`HasRoutineMarker` は本文のどこにあってもマーカーを検出し
  （`internal/action/action.go:36-40`）、`internal/ui` はその場合、投稿の選択肢が無い確認画面に移る
- **`>` を行頭に置いた行は、既存の判定のどれにも当たらない**。`BlockedByLines` は行頭の `>` を吸収せず
  （`answer-action`「`> blocked-by: human` は検出しない。dispatcher も検出しない」）、`model.IsAI` は
  本文先頭のマーカーと行頭の `## PR リスク評価` だけを見て（`internal/model/parse.go:35-46`）、
  `model.ParseQuestions` は行頭の空白とタブだけを落として `## Q<n>.` を探す（同 `:147-172`）

## Goals / Non-Goals

**Goals:**

- エディタを開いたままで質問と選択肢を読めるようにする
- 引用を足しても、投稿の経路（マーカー検査・`blocked-by` 警告・人の発言としての分類）を 1 つも壊さない
- 変更を `internal/action/template.go` の中に閉じる

**Non-Goals:**

- 画面（カード詳細・PR 詳細）の質問の見せ方を変えること。引用はエディタに入る文字だけの話である
- `n`（新しい issue）の下書きを変えること。案内 2 行を区切りに使う別の経路である
- テンプレートに人向けの案内文（「記号だけで OK です」など）を足すこと。引用そのものが案内になる
- エディタのカーソル位置を制御すること。`ExternalEditor` は一時ファイルのパスを渡すだけで、
  行番号の指定はエディタごとに違う引数になる

## Decisions

### D1. 引用は本文を写すだけにし、質問の構造から組み立て直さない

`model.ParseQuestions` が返す `Question` から `> ## Q1. <題>` の行を作り直す方式（`proposal.md` の未確定の判断
Q1 選択肢 B）は、パースできた質問しか復元できない。前置きの 1 行（「以下 2 点、回答をお願いします」）、
`- 依存: Q2 の回答が要る` の行、issue の `blocked-by: human` コメントの散文がすべて落ちる。落ちた行に
「どちらを選ぶと何が起きるか」が書かれていることがあるので、写す方式を採る。

写す方式なら、引用を作る処理は「マーカー行を落として各行に `> ` を付ける」だけになり、
質問の書式が routine 側で変わっても追随の作業が出ない。

### D2. 引用するのは「人への問い」のコメントだけに絞る

最新の routine コメントを無条件に引用すると（同 選択肢 C）、`## PR リスク評価` の評価コメントが最新である PR で
`a` を押したときに評価の全文が入る。評価は人への問いではないので、回答を書く場所が評価文に埋まる。

そこで、`model.ParseQuestions` が 1 件以上返すか `BlockedByLines` が 1 行以上返すコメントだけを引用する。
前者が grill の質問コメント（`routine-propose` が `## Q<n>.` 形式で書く）、後者が issue の `blocked-by: human`
コメントに当たり、**人への問いはこの 2 つの形でしか届かない**。判定に使うのはどちらも既存の関数で、
新しいパースは増えない。

この絞り込みの代償は、`example` の PR 131 のような素の `Q1: マイグレーションを分けますか。` が引用されないこと。
今も空のテンプレートで開くので後退ではないが、引用が入らない形が残るのは事実である。

### D3. 引用ブロックを前、回答行を後ろに置く

投稿されたコメントが GitHub 上で「引用された問い → 回答」の順に読める。確認画面が下書きをそのまま見せる形
（`answer-question`「確認画面では投稿・編集に戻る・中止を選ぶ」）とも並びが揃う。

代わりに、エディタのカーソルは 1 行目（引用の先頭）に立つので、回答行まで人が移動する。回答行を先に置けば
カーソルが最初から回答行に乗るが、読み順が逆になり、投稿したコメントも「回答 → その下に問い」の並びになる。
移動は 1 操作で済むので読み順を採る。

### D4. 空行は `>` の 1 文字で引用し、末尾の `>` だけの行は落とす

`blocked-by: human` コメントは `blocked-by:` / `unblock-when:` の行と散文の間に空行を挟む
（`routine-common`「見送りの書き戻し」）。空行を引用しないと Markdown の引用ブロックがそこで切れ、
GitHub 上で 2 つの引用に割れる。`>` の 1 文字なら 1 つの引用として続く。

本文の末尾が改行で終わっていると、写した結果の末尾に `>` だけの行が残り、回答行の前の空行が 2 行になる。
末尾に連なる `>` だけの行を落として、区切りの空行を常に 1 行にする。

### D5. 引用を投稿前に落とす処理は持たない

`n` の案内 2 行は `SplitNewIssue` が区切りとして食べるので issue に入らない（`internal/action/newissue.go:26-28`）。
同じ扱いを引用に当てると、`action.Comment` の前に「行頭が `>` の行を落とす」処理が入る。採らない理由は 2 つ。

1. 案内文（「タイトル（この下の行に入力してください）」）は GitHub に出ても意味を持たない文字列だが、
   引用された問いは意味を持つ。`Q1: B` だけのコメントより、問いを引用した回答の方が後から読める
2. 人が自分の判断を引用で補強した行（`> 選択肢 B は次の issue に回したい`）も一緒に消える。
   TUI が人の書いた行を黙って落とすのは、投稿の内容を人が決めるという不変条件に反する

この判断は `proposal.md` の未確定の判断 Q2 として人に問う。落とす側に決まった場合は、`answer-action` に
「引用行を落としてから投稿する」Requirement を足し、`internal/action/action.go` の `Comment` の手前に処理を置く
（`internal/ui` の検査の順序は変えない）。

## Risks / Trade-offs

- **[投稿するコメントが質問文のぶん長くなる]** → 引用するのは最新の routine コメント 1 件で、長さはその
  コメントと同じ。人はエディタで削れる。D5 のとおり、自動で落とす処理は入れない
- **[縦に狭い確認画面で引用が切れて見える]** → `blocked-by` の確認画面は下書きを残りの高さで切り、
  スクロールしない（`answer-question`「確認画面では投稿・編集に戻る・中止を選ぶ」）。引用が長いと
  下書きの末尾（回答行）が画面に出ないことがある。ただし引用した `blocked-by:` 行はそもそも警告に当たらない
  （行頭が `>`）ので、この確認画面に入るのは人が自分で `blocked-by:` 行を書いたときだけである
- **[引用の中にマーカーが残ると回答が投稿できなくなる]** → マーカーを含む行を落とすことを spec の
  Requirement に書き、`HasRoutineMarker(テンプレート)` が false であることを Scenario で確かめる。
  エスケープ済みのマーカー（`&lt;!-- routine --&gt;`）も同じ扱いにする
- **[引用付きの回答が、次のテンプレートの元になる]** → ならない。`AnswerTemplate` は `AI` が true の
  コメントしか選ばず、人が投稿した回答は `model.IsAI` が false と判定する（行頭が `> ` で、
  マーカーでも `## PR リスク評価` でもない）
- **[人が引用を消さずに投稿したコメントを、dispatcher が誤読する]** → 引用した `blocked-by:` 行は
  dispatcher も検出しない（`answer-action` に明記されている既存の規則）。引用した `## Q<n>.` の行も
  `model.ParseQuestions` に当たらない（行頭が `>`）

## 未決事項

`docs/mvp` はテンプレートを `Q1: A\nQ2: A` の形（`docs/mvp/mvp.md:99-101`）としか書いておらず、引用については
沈黙している。実装者が選ぶ既定値は次のとおりで、引用の範囲（Q1）と投稿時の扱い（Q2）は `proposal.md` の
「未確定の判断」として人に問う。

- **引用記号**: 既定値は `> `（半角の不等号 + 半角空白 1 つ）。Markdown の引用の標準形で、`BlockedByLines` が
  行頭の `>` を吸収しないことが既存 spec に書かれている
- **引用ブロックと回答行の区切り**: 既定値は空行 1 行。引用を閉じるために 1 行は要る
- **引用する行の行末の空白**: 既定値は落とす。Markdown の行末 2 空白（強制改行）を引用の中に残す理由が無い
- **引用の長さの上限**: 既定値は上限を設けない。切ると、切った先に判断の材料が残っていても人に届かない
