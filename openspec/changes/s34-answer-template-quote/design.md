## Context

動機は `proposal.md` の Why にある。設計の前提になる現状は 5 点。

- **実物の質問コメントは今のパーサに当たらない**。`internal/model/parse.go:28-29` の `questionRe` は
  `^##\s*Q(\d+)\.`、`optionRe` は `^[-*]\s*選択肢\s*([A-Z])\s*(（推奨）|\(推奨\))?\s*[:：]` である。
  `routine-propose` が投稿する `### Q1. …` と `- **選択肢 A（推奨）**: …` はどちらにも当たらず、
  `ParseQuestions` は質問 0 件を返す（手元で `internal/model` にテストを足して実行し確認）
- **テンプレートを作る場所は 1 つ**。`internal/action/template.go:13` の `AnswerTemplate` が最新の routine コメントを
  選び、`internal/ui/answer.go:56` がその戻り値をそのまま `openEditor` へ渡す
- **投稿前の門は 3 つだけ**。`internal/ui/answer.go:100-109` が「前後の空白を除いて空」「マーカーを含む」
  「行頭が `blocked-by:`」を見て、どれにも当たらなければ投稿のコマンドを返す。確認画面も通らない
- **`>` を行頭に置いた行は Go 側のどの判定にも当たらない**。`BlockedByLines` と `LatestBlockedBy` は
  `TrimSpace` した字面の前方一致、`IsAI` は本文先頭のマーカーと行頭の `## PR リスク評価`、`ParseQuestions` は
  行頭の空白とタブだけを落として見出しを探す
- **正本の判定は Go の外にもある**。`routine-dispatch` / `routine-common` は skill の散文で
  「`blocked-by:` 行を含む最新のコメントが正本」と定めており、判定するのは LLM である。
  行頭の `>` を除く規則は上流の散文に書かれていない

## Goals / Non-Goals

**Goals:**

- 実際に届く質問コメントから、質問文・選択肢・回答行がエディタに入る状態にする
- 引用を足しても、投稿の経路（マーカー検査・`blocked-by` 警告・人の発言としての分類・dispatcher の正本）を
  1 つも壊さない
- 引用を足したことで新しい誤爆の経路（中身の無い回答の投稿）を作らない

**Non-Goals:**

- 画面（カード詳細・PR 詳細）の質問の見せ方を変えること。パースが広がるぶん出る質問は増えるが、書式は変えない
- 回答行の選び方（最新の routine コメント）を変えること
- `n`（新しい issue）の下書きを変えること
- エディタのカーソル位置を制御すること。`ExternalEditor` は一時ファイルのパスを渡すだけである
- 質問コメントの書式を上流 skill 側に合わせさせること。loop-cli は届いた本文を読む側である

## Decisions

### D1. パーサは「`#` の数」と「Markdown 強調」だけを緩める

`questionRe` の `##` を「`#` が 1 つ以上」にし、`optionRe` に `**` を読み飛ばす位置（`選択肢` の前、`<Letter>` の直後、
`（推奨）` の直後）を足す。これで `### Q1.` と `- **選択肢 A（推奨）**: …` と `- **選択肢 A**（推奨）: …` が読める。

見出しの本文（`Q<n>.`）と選択肢の語（`選択肢 <Letter>`）の形は変えない。`Q1:`（見出しではない 1 行）の形まで
拾おうとすると、人が書いた `Q1: A` の回答コメントも質問に見えるので、見出しの記号は要求したままにする。

代替案として、行から `*` を全部落としてから当てる方式は採らない。選択肢の本文に `*` を含む質問
（`- 選択肢 A: *.md を除く`）で `Text` が変わる。

パースが広がると `internal/ui/detail.go:311-322` の blocked-by 要約にも質問と選択肢が出るようになる。これは
`card-detail` が既に定めている振る舞い（「質問が 1 件もパースできなければ本文をそのまま出す」）の範囲内で、
出る側に寄るだけなので `card-detail` の Requirement は変えない。

### D2. 引用は本文を写し、範囲の外と 3 種類の行だけを落とす

写す方式を採る理由は `proposal.md` の「確定した判断」にある。引用するのは「質問が始まった行から終わった行まで」で、
範囲の決め方は次のとおり（PR #41 のコメントで確定した方針を実装の規則に落としたもの）。

- **始まり**: 最初の質問見出しの行。見出しを持たないコメント（issue の `blocked-by: human`）では、マーカー行と
  `blocked-by:` / `unblock-when:` の行を飛ばした後の最初の非空行
- **終わり**: 本文の末尾から、空行・区切り線だけの行（`-` `*` `_` のいずれかが 3 つ以上）・`_` で始まり `_` で終わる
  1 行（`_Generated by [Claude Code](…)_` の署名）を落としていって、最初に残る行

質問の途中にある説明文・表・`- 依存:` の行は範囲の中なので引用に入る。終わりを「最後の質問ブロックの末尾」と
定義せず「末尾から定型の行を落とした位置」と定義するのは、質問の後に 1 行の結びが付く形（「回答をお待ちしています」）で
その行を落とす理由が無く、落とす条件を増やすほど取りこぼしが読めなくなるからである。

範囲の中でも、次の 3 種類の行は落とす。

| 落とす行 | 理由 |
| --- | --- |
| `TrimSpace` がマーカーと完全一致する行 | マーカーを含む本文は投稿できない。`internal/ui/preview.go:98-109` の `stripMarkers` と同じ規則 |
| `blocked-by:` で始まる行 | dispatcher の正本の宣言を引用として持ち回らない（不変条件 8） |
| `unblock-when:` で始まる行 | 同じ理由。画面側の `questionLines` もこの 2 行を落としている |

行の途中に残ったマーカーは `[routine マーカー]` に置き換える。行ごと落とすと、質問行にマーカーが含まれていたときに
質問文が消えたまま回答行が残り、人は「答えるべき問いが無いのに既定値が入った下書き」を見る。置き換えなら
内容が残り、`HasRoutineMarker(テンプレート)` が false になることも構成的に保証できる。

判定に使うマーカーの文字列は `internal/action/action.go:15-18` の定数（`HasRoutineMarker` が見ているものと同じ）に
限る。テンプレート側にリテラルを書き写すと、将来マーカーの形が増えたときに、落とす側と拒む側がずれて
**すべての回答が投稿不能**になる。

### D3. 対象のコメントは位置で選ばず、末尾から「人への問い」を探して選ぶ

`comments` を末尾から先頭へ見て、最初に見つかる次のコメントを選ぶ。引用と回答行の両方をそこから作る。

- `AI` が true である
- 質問の見出しを持つ（`ParseQuestions` が 1 件以上）か、`BlockedByLines` が 1 行以上を返す

人への問いが届く形は、grill の質問コメント（`Q<n>.` 見出し）と issue の `blocked-by: human` コメントの 2 つである。
この条件で選ぶので、人の返信・`started:` / `session:` の作業印・`## PR リスク評価` の評価コメントは自然に飛ばされ、
それらが引用されることも無い。ここが外れると引用も回答行も出ないので、spec の Scenario は実物の書式
（`### Q1.` と太字の選択肢）を入力に使い、書式の取りこぼしをテストで捕まえる。

回答行の元を同じコメントに揃えるのは、引用と回答行が別のコメントから来ると、どの問いに答えている下書きなのかが
食い違うためである。この変更で、いま「最新の `AI` コメント」を採る規則が起こしていた取りこぼし（質問の後に
routine が `started:` のコメントを足すと、回答行が 0 行になる）も同時に消える。

代償として、人が答えて worker が「確定しました」と返した後でも、さらに `a` を押すと解決済みの問い
（PR #37 の実物では表つきの約 4KB）が引用に入る。最新のコメントに限らないという方針を採った結果であり、
人はエディタで引用を削れる。「引用の鮮度を見る」案は PR #41 のコメントで退けられた。

### D4. 空行は `>` の 1 文字で引用し、末尾の `>` だけの行は落とす

`blocked-by: human` コメントは宣言行と散文の間に空行を挟む（`routine-common`「見送りの書き戻し」）。
空行を引用しないと Markdown の引用ブロックがそこで切れ、GitHub 上で 2 つの引用に割れる。
本文の末尾が改行で終わっていると写した結果の末尾に `>` だけの行が残るので、末尾に連なる分を落として、
引用ブロックと回答行の間の空行を常に 1 行に保つ。

### D5. 引用行と空行だけの本文は「空」として扱う

`internal/action` に判定を 1 つ置き、`Comment`（`ErrEmptyBody` を返す側）と `internal/ui` の編集完了の検査が
同じ関数を使う。`answer-question`「編集結果を検査してから投稿する」は既に「検査の規則は `answer-action` と同じ関数を
使い、`internal/ui` に別の判定を持たない」と定めているので、置く場所は `internal/action` になる。

これが無いと、引用だけのテンプレート（局面 B）を開いてそのまま閉じた下書きが投稿され、`unblock-when: comment` の
解除条件（正本より後に人のコメントがある）に当たって worker が推奨案で進む。いまは局面 B のテンプレートが空なので
同じ誤爆が何も起こさないので、引用を入れる代わりに安全側の既定を保つ。

代償として、引用の一部を残すだけで答えたつもりの下書き（`> 選択肢 B: 含める` の 1 行だけ）も中止になる。
フッタに理由を出して人が書き足せるようにする（`回答を中止しました（引用だけです）`）。

### D6. 引用を投稿前に落とす処理は持たない（確定）

`n` の案内 2 行は `SplitNewIssue` が区切りとして食べるので issue に入らない。同じ扱いを引用に当てると、
`Comment` の手前に「行頭が `>` の行を落とす」処理が入る。採らない理由は 2 つある。

1. 案内文は GitHub に出ても意味を持たない文字列だが、引用された問いは意味を持つ。`Q1: B` だけのコメントより、
   問いを引用した回答の方が後から読める
2. 人が自分の判断を引用で補強した行も一緒に消える。TUI が人の書いた行を黙って落とすのは、投稿の内容を人が決める
   という前提に反する

PR #41 のコメントで「最終的なコメントは、その引用もセットにして、コメントとしてサブミットする」と決まったので、
落とす側の実装は作らない。

## Risks / Trade-offs

- **[パーサを広げたぶん、質問に見える行が増える]** → 見出しの記号（`#` + `Q<n>.`）と選択肢の語（`選択肢 <Letter>`）は
  要求したままなので、人の回答（`Q1: A`）や散文が質問に化けることはない。コードブロックの中に `#### Q1.` を書いた
  コメントは質問として読まれるが、出るのは余分な回答行 1 本で、投稿前に人が消せる
- **[投稿するコメントが質問文のぶん長くなる]** → 引用するのは選んだ質問コメント 1 件の質問範囲で、PR #37 の実物は
  約 4KB。人はエディタで削れる。上限を切ると、切った先に判断の材料が残っていても人に届かない（未決事項に実寸を書く）
- **[解決済みの問いが引用に入る]** → 対象を最新のコメントに限らないので、人が答えた後に `a` を押すと同じ問いが
  もう一度引用される。PR #41 のコメントで決まった方針の帰結として受け入れ、人がエディタで削る前提にする
- **[LLM の dispatcher が引用を正本と読む]** → 正本の宣言行（`blocked-by:` / `unblock-when:`）を引用に入れない
  （D2）ので、引用に正本の形が現れない。人が自分で `blocked-by:` 行を書いた場合は、今までどおり確認画面が出る
- **[縦に狭い確認画面で引用が切れて見える]** → 確認画面は下書きを残りの高さで切り、スクロールしない。
  ただし D2 により引用は `blocked-by:` 行を含まないので、この画面に入るのは人が自分でその行を書いたときだけである
- **[引用付きの回答が、次のテンプレートの元になる]** → ならない。`AnswerTemplate` は `AI` が true のコメントしか
  選ばず、人が投稿した回答は `model.IsAI` が false と判定する（行頭が `> ` で、マーカーでも `## PR リスク評価` でもない）。
  引用した見出し（`> ### Q1.`）も `ParseQuestions` に当たらない
- **[引用だけの下書きの中止を、人が「エディタが壊れた」と読む]** → フッタに `（引用だけです）` の理由を出す。
  文言を spec の Scenario で固定する

## 未決事項

`docs/mvp` はテンプレートを `Q1: A\nQ2: A` の形（`docs/mvp/mvp.md:99-101`）としか書いておらず、引用については
沈黙している。実装者が選ぶ既定値は次のとおりで、引用の始まり（前置きを含めるか）は `proposal.md` の
「未確定の判断」として人に問う。

- **引用記号**: 既定値は `> `（半角の不等号 + 半角空白 1 つ）。Markdown の引用の標準形である
- **範囲の終わりで落とす定型の行**: 既定値は、空行・`-` `*` `_` のいずれかが 3 つ以上並んだ区切り線の行・
  `_` で始まり `_` で終わる 1 行。routine の PR コメントの署名（`_Generated by [Claude Code](…)_`）がこの形である
- **行の途中のマーカーの置き換え文字列**: 既定値は `[routine マーカー]`。マーカーの 2 つの形のどちらも含まない
- **引用ブロックと回答行の区切り**: 既定値は空行 1 行
- **引用する行の行末の空白**: 既定値は落とす。Markdown の行末 2 空白（強制改行）を引用の中に残す理由が無い
- **引用の長さの上限**: 既定値は上限を設けない。PR #37 の質問コメントの実寸は約 4KB・40 行超である
- **見出しの `#` の上限**: 既定値は上限を設けない（1 つ以上）。Markdown の見出しは 6 段までだが、
  段数で質問かどうかが変わる理由が無い
