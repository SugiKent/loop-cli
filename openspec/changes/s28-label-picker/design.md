## Context

`internal/ui` の `Model` は画面の状態を 7 つ（キュー / カード詳細 / PR 詳細 / 確認 / ヘルプ / URL 一覧 / merge 確認）持ち（`internal/ui/detail.go:22-30`）、`Update` が状態ごとにキーを振り分け、`View` が状態ごとに全画面を描く（`view.go:48-60`）。重ね合わせのオーバーレイは 1 つも無い。

ラベルを書く経路は `t` だけで、`internal/action/todo.go` の `ToggleTodo` が `ViewIssue` で現在のラベルを読み直してから `AddLabel` / `RemoveLabel` を 1 ラベルずつ呼ぶ。書き込みの直前に読み直すのは、画面の Card のラベルが最終取得時点のもので、続けて 2 回押した 2 回目が「もう一度付ける」になるのを防ぐためである。書き先の表現は `action.Target{Repo, Number, IsPR}`（`action.go:29-33`）で、`Comment` はこれ 1 つで issue / PR を書き分けている。

`GHClient`（`internal/gh/gh.go:12-31`）は 17 メソッドで、`Client` が `gh` サブプロセス、`Fake` が fixture ディレクトリを読む。後続 change がメソッドを足すときは interface・`Client`・`Fake` を同時に拡張する（`gh-client` spec「`GHClient` interface が読み取りと書き込みのメソッドを定義する」）。`Fake` は「ディレクトリ 1 つ = リポジトリ 1 件」で `repo` 引数をファイル探索に使わない（`fake.go:50-51`）。

この change は 2 つの前提を意図的に変える。**触れるラベルの範囲**（不変条件 2 と `ai-assess:requested` の一文を撤廃）と、**1 回の書き込みで変わるラベルの数**（不変条件 1 を「集合の置換をしない」に狭める）である。どちらも人の回答で決まった（proposal.md の「人の回答で決まったこと」）。

## Goals / Non-Goals

**Goals:**

- 画面を離れずに、対象（issue でも PR でも）のラベルを付け外しできる
- 複数のラベルを変えるとき、GitHub への書き込みを 1 回に収める
- 何が付いていて、送信したら何がどう変わるかが、送信前に一覧で分かる
- 送信するまで GitHub に何も起きない（`Esc` で丸ごと捨てられる）

**Non-Goals:**

- ラベルの新規作成・削除・色や説明の編集（`gh label create` / `edit` / `delete` の経路は持たない）
- ラベルで一覧を絞り込む機能（`/` の絞り込みは s19 の担当）
- 書き込み後の対象 1 件だけの再取得（P2 の別項目。反映は `R` / 自動更新に任せる）
- 100 件を超えるラベルのページング
- 危険なラベル（`stage:*` など）への警告や確認画面（人の回答 Q1 が制限を設けないと決めた）

## Decisions

### D-1: ラベル一覧は 8 つ目の画面の状態として全画面で描く

`Model` の画面の状態にラベル一覧を足し、`View` は端末の幅と高さ全体を使って描く。s22 が URL 一覧で同じ判断（design.md D-1）をしており、確認画面も merge 確認画面もヘルプ画面も全画面である。重ね合わせを入れると背面の描画結果に対する切り出しと合成の規則を新しく決めることになり、`View` の分岐が 1 つ増えるだけの全画面より複雑になる。

見出し / 空行 / ラベルの行 / 残りは空行 / フッタ の順で、スクロール位置は持たず選択位置から表示開始位置を決める（`renderURLs` と同じ）。1 行は `<選択の印><状態の印> <名前>  <説明>` で、状態の印は 4 種類ある。

| 印 | 意味 |
| --- | --- |
| `[x]` | 今付いている。送信しても変わらない |
| `[ ]` | 今付いていない。送信しても変わらない |
| `[+]` | 今付いていない。送信すると付く |
| `[-]` | 今付いている。送信すると外れる |

見出しには変更予定の件数を出す（`ラベルを付け外し（変更 2 件）`）。件数の置き場所に見出しを選んだのは、フッタの右側が取得中のスピナーやエラーと 1 つの領域を共有しており（`view.go:207-233`）、そこへ置くと取得中に消えるからである。

`gh label list` は色（`color`）も返すが、一覧では使わない。ラベル名に色を付けると、`kindStyle`（種別の色。`view.go:27-33`）と意味の違う色が同じ画面に並ぶ。色の利用は明示的に見送る。

並び順は `gh` 任せにしない。`gh label list` の既定は作成順（cli/cli `pkg/cmd/label/http.go` の `defaultSort = "created"`）で、リポジトリごとに並びが変わり fixture も画面も非決定になる。`--sort name --order asc` を渡して名前の昇順に固定する。

### D-2: 一覧の分岐は `a` / `t` / `m` / `o` / `?` より前に置く

`Update` のキー振り分けで、ラベル一覧画面の分岐を URL 一覧の直後（`a` / `t` / `m` / `o` / `?` の判定より前）に置き、`L` のハンドラをその後ろに置く。後ろに置くと、一覧を出している間の `t` が「画面はキュー」と見なして裏の対象へ書き込む。`L` のハンドラを一覧の分岐より前に置くと、一覧を出したまま `L` を押したときに戻り先が一覧自身に上書きされて `Esc` が効かなくなる（s22 design.md D-2 と同じ）。

一覧画面で扱うキーは 行の移動（`j` / `k` / `↑` / `↓`）、印の切り替え（`Space`）、送信（`Enter`）、破棄（`Esc`）、終了（`q` / `Ctrl+C`）の 5 つ。`Space` と `Enter` の割り当ては人の回答（Q6）で決まった。`Esc` は変更予定を捨てて戻り先の画面に戻り、戻り先がカード詳細 / PR 詳細のときは本文領域を作り直す（一覧を出している間の端末サイズ変更が詳細に反映されないため。s12 / s22 と同じ）。

### D-3: 対象は `L` を押した時点で `action.Target` に写し取る

`L` を押した時点で対象の `{Repo, Number, IsPR}` と戻り先の画面を状態に写し取り、送信のときはその写しを使う。`Cards` から引き直さない。

理由は自動更新である。`refresh.go:20-25` の自動更新は `fetching || writing` だけを見て画面を見ないので、一覧を出している間（`writing` は立っていない。D-6）にも走る。`fetchedMsg` は `m.cards` / `m.rows` を差し替えて `clampCursor()` する（`model.go:164-189`）ので、送信の時点で `m.rows[m.tab][m.cursor]` を読むと、選択行が別の issue に入れ替わっていてもそれに気づかずラベルを書く。s14 の `mergeState` が同じ理由で押した時点の repo / number をコピーしている（`merge.go:22-31`）。

### D-4: ラベル一覧の取得は `L` を押したときに 1 リポジトリ 1 回だけ行う

`GHClient` に `ListLabels(ctx, repo) ([]Label, error)` を足す。`Client` は `gh label list -R <repo> --json name,description,color --sort name --order asc --limit 100` を実行する。

`Model` は `map[string][]gh.Label` をリポジトリ名（D-3 で写し取った `Target.Repo`）で持つ。経路は 2 つに分かれ、仕様とテストもこの 2 つに分ける。

- **キャッシュに有る**: コマンドを返さず、その場で一覧画面に移る。`writing` は立たない
- **キャッシュに無い**: 取得のコマンドを返し、`writing` を立て、フッタに `<repo> のラベル一覧を取得中` を出す。結果が届いたら `writing` を下ろし、D-7 の判定を通してから一覧画面に移る。取得に失敗したら画面を変えず、フッタに赤で `<repo> のラベル一覧を取得できません: <エラー>` を出す

**なぜ起動時に先読みしないか。** 起動時の取得はリポジトリの数だけ `gh` を増やし、`L` を一度も押さない利用者にも払わせる。D-001 が定めた 1 更新あたりの呼び出し回数（`2 + N + 3M`）を変えないためにも、`L` を押したときの遅延取得にする。

**なぜ捨てないか。** ラベルの集合はセッション中にまず変わらない。`R` でも自動更新でも捨てず、プロセスが終わるまで保持する。ラベルを新しく作った直後に `L` を押しても出ないが、そのときは loop-cli を起動し直せばよい。この割り切りは s23 の「更新の確認は起動につき 1 度だけ。版はセッション中にまず変わらない」と同じ考え方である。同じ理由で、`--limit 100` を超えるリポジトリで一覧が 100 件に切れることも画面には出さない（切れているかを知るには 101 件目を取りに行くしかなく、`L` の反応を鈍らせる）。上限と「新しいラベルは起動し直すまで出ない」ことは `label-picker` の spec に明記する。

**`Fake` での検証。** `Fake` は `repo` 引数を無視するので「リポジトリごとに別の集合を持つ」は fixture では確かめられない。代わりに `Fake.ListLabels` の呼び出しを `Calls` に記録し、「同じリポジトリで `L` を 2 回押しても `Calls` の `ListLabels` は 1 件」で 2 回目に `gh` を呼ばないことを検証する。記録しないと D-4 の主要な主張がテスト不能なまま残る。

### D-5: 変更予定は画面の状態に持ち、送信まで GitHub に触らない

印の切り替えは `Model` の中のラベル名の集合を書き換えるだけで、コマンドを返さない。集合は「送信後にこうなっていてほしい状態」を表す。初期値は画面の Card のラベル（`Card.Issue.Labels` / `PR.Labels`。最終取得時点）で、切り替えのたびに 1 件を足し引きする。

`Esc` はこの集合を捨てる。送信するまで GitHub には何も起きないので、押し間違えても `Esc` で戻せる。**確認画面は挟まない**（issue #3 の「トグルなので確認画面は出さない」を保つ）。印の付いた一覧そのものが確認の場であり、確認画面を足すと同じ内容を 2 画面で見せることになる。

### D-6: 取得中と送信中は「書き込み中」、一覧を出している間は違う

`m.writing` を立てる場面を、ラベル一覧の取得中と送信中に広げる。s14 が「`m` が押されてから merge の判断材料を取り直している間（まだ書き込んでいない）」を書き込み中に含めたのと同じで、手続きを重ねて始めさせないためである。一覧を開いて印を切り替えている間は書き込み中ではない。したがって一覧を出している間も自動更新は走り、D-3 の写し取りが必要になる。

### D-7: 取得の間に画面が変わっていたら一覧を開かない

取得のコマンドを返した時点の画面を保持し、結果が届いたときの画面がそれと違えば、一覧画面に移らずフッタに `<repo> のラベル一覧の表示を中止しました（画面が変わりました）` を出す。

`m.writing` は書き込み系のキーだけを止め、`o` / `?` / `u` / `Esc` / `Enter` などの画面移動は通す（`openspec/specs/merge-pr/spec.md:106`）。この規則が無いと、取得中に `?` を押して開いたヘルプ画面や `u` で開いた URL 一覧を、あとから届いたラベル一覧が踏み潰す。s14 が merge の取り直しに対して同じ規則を持っており（同 spec:38、`merge.go:124-131`）、そこに揃える。

### D-8: 送信は「読み直し → 差分 → 1 回の書き込み」

`internal/action` に、`Target` と D-5 の集合（送信後にこうなっていてほしいラベル名の集合）を受け取る関数を足す。手順は 3 つ。

1. `Target.IsPR` で `ViewPR` / `ViewIssue` を選び、現在のラベルを読み直す
2. 「集合にあって現在に無い」を付ける並び、「現在にあって集合に無い」を外す並びにする。並びは名前の昇順にして、コマンドの引数を決定的にする
3. どちらも空なら書き込まずに戻る。そうでなければ `EditIssueLabels` / `EditPRLabels` を 1 回だけ呼ぶ

読み直すのは、印の元が最終取得時点の Card のラベルで、その間に他の経路でラベルが変わっていると差分がずれるためである（`action.ToggleTodo` が `ViewIssue` で読み直しているのと同じ理由）。読み直した結果、押した印がすべて実現済みだったときは書き込みが 0 件になり、その旨をフッタに出す。

**1 回の書き込みでラベル集合の置換は起きない。** `Client.EditIssueLabels` は `gh issue edit <n> -R <repo> --add-label a --add-label b --remove-label c` を実行する（ラベル名にコンマが含まれると `--add-label a,b` 形式は壊れるので、フラグを繰り返す）。`gh` の内部でも `addLabelsToLabelable` と `removeLabelsFromLabelable` の 2 つの mutation に分かれ、ラベル一覧を丸ごと置き換えることはない（cli/cli `pkg/cmd/pr/shared/editable_http.go`）。不変条件 1 が守りたかった「他の人が付けたラベルを消さない」はこれで保たれる。

**`ToggleTodo` と 1 本にまとめない。** `ToggleTodo` は `stage:todo` 固有の拒否（`ErrOtherStage` / `ErrMultipleStages` / `ErrBlocked`）を持ち、対象が issue に限られ、1 ラベルずつ書く。`t` はこれまでどおり `ToggleTodo` を呼び、`L` は新しい関数を呼ぶ。

### D-9: 送信のあとは元の画面に戻る

送信の結果が届いたら戻り先の画面に戻り、フッタに `<repo> #<n> のラベルを更新しました（+docs -wip）` を出す。失敗は `<repo> #<n> のラベルを更新できません: <エラー>` を赤で出し、同じく戻る（一覧に留まると、どの変更が通ってどれが通っていないかを印で表せない）。

一覧に残さないのは、`Cards` を書き換えないため（`t` / `m` と同じ）、送信後の一覧の印が実物と食い違うからである。

### D-10: 対象の決め方は `a` / `u` と同じにする

キュー画面は選択行の主体（`subjectOf`。`rows.go:25-37`）、カード詳細は `Card.Issue`、PR 詳細は選択中の PR。`t` の「対象は常に Issue」は `stage:todo` が issue のラベルだからで、`L` は PR にも付けたいので `a` / `u` の規則を採る。選択行が無ければ何もしない。確認画面・merge 確認画面・ヘルプ画面・URL 一覧では `L` は届かない（それぞれの分岐が先に処理する）。

リポジトリ名は `subjectOf` が返した `Issue.Repo` / `PR.Repo` を正とする（`row.repo` は表示用に `Subject` が同じ値から作っているので一致する）。

## Risks / Trade-offs

- **routine の状態機械と merge ガードを人が崩せるようになる。** 人の回答（Q1: C）で受け入れた。`stage:apply` を誤って付けると worker が 1 本起動し、`question` を外すと AI 評価前の PR を merge できる。どちらも TUI 側では取り消せず、GitHub 側で人が直すことになる
- **1 回の送信で `labeled` イベントが複数出る。** ラベルを 2 つ足せば 2 回出る。Routine のフィルターは書き込み後のラベル集合で判定されるので（`routine-common`「ラベルの書き込みが何を起動するか」）、まとめて送るほうが 1 つずつ送るより意図しない起動は起きにくい（`[stage:propose, wip]` を一度に足せば `NOT_IN [wip]` に当たって起動しない）。ただし「増えたラベルの数だけイベントが出る」ことは変わらない
- **ラベル名にコンマが含まれると壊れる可能性がある。** `gh` の `--add-label` は cobra の StringSlice で、フラグを繰り返してもコンマで分割される。issue-driven-sdd のラベルにコンマは無いので当面は当たらないが、対策は持たない
- **`gh label list` の 100 件の上限。** `--limit 100` を超えるラベルを持つリポジトリでは一覧が途切れ、切れていることを画面に出さない（D-4）
- **キャッシュが古くなる。** D-4 のとおりセッション中は捨てないので、他の経路でラベルを新しく作っても `L` には出ない。起動し直しでしか直らない
- **取得中の `R` がステータスを消す。** `R` は `m.fetching` だけを見るので取得中でも押せ、`startFetch` が `writeStatus` を消す（`model.go:140`）。`<repo> のラベル一覧を取得中` が黙って消える。`t` / `m` のステータスも同じ扱いなので、この change で変えない
- **印の初期値の古さ。** D-5 の初期値は最終取得時点の Card のラベルで、その間に他の経路で変わっていれば `[x]` / `[ ]` がずれる。とくに詳細の取得に失敗した PR の `Labels` は search 時点のもの（`model.go:230`）。送信時は D-8 で読み直すので書き込み自体は正しくなるが、利用者が見て切り替えた印と結果が食い違うことはある
- **フッタが幅 80 で切れる。** 人の回答（Q5: A）で受け入れた。キュー画面は 80 → 90 列になる
- **fixture のラベルの説明文。** s04 の伏せ字は全ファイル一括のテキスト置換で、login 表はコメントの `"login"` 値と `@mention` から作る。ラベルの `description` に表に無い人名や組織名が書かれていれば残り得る。これは既存の issue / PR 本文と同じ性質の残余リスクで、`labels.json` を足したことで新しく生まれるものではない
