## Context

進行中の規則 2 / 3 / 7（`human-turn-classify`）は、PR を「AI が次に動く」前提で進行中タブへ回す。規則 2 / 3 は auto-fix や worker が人のコメントを受け取る前提、規則 7 は assess が評価を終えて `ai-assess:requested` を外す前提である。

2026-09-12 に X-Mile/ca-ai-role-play で、この前提が崩れた状態が観測された。

- assess Routine は enabled だが、最後の run は 2026-09-06 である。`assess-pr-risk` skill にはラベルを外す手順が無く、merge 済み PR にもラベルが残っている
- worker は人の回答を反映したあと、コメントを残さずにラベルだけを書き換えた（#825 / #826）

その結果、open PR 5 件がすべて進行中に入り、「今やる」から消えた。分類は PR の今のラベルとコメントだけを見るので、上流が止まると PR は恒久的に進行中に留まる。

## Goals / Non-Goals

**Goals:**
- 規則 2 / 3 / 7 に当たる PR でも、AI が一定時間動かなければ人の目に戻す
- 追加の gh 呼び出しを増やさない（D-001 の呼び出し回数を保つ）
- 分類を入力だけから決める純粋関数のまま保つ

**Non-Goals:**
- 上流（assess Routine の起動、`assess-pr-risk` がラベルを外すこと、worker がコメントを残すこと）を直すこと
- issue 側の規則 1 / 4 / 5 / 6 を変えること。sweep / dispatch が定期実行で拾う側で、今回は崩れた例が観測されていない

## Decisions

### 「最後に動いた時刻」に `PR.UpdatedAt` を使う

search が返す `updatedAt` は、コメント・ラベルの付け外し・push で更新される。#825 / #826 では、`updatedAt` がちょうど `ai-assess:requested` を付けた時刻と一致した（2026-09-11 実測）。すでに `model.PR.UpdatedAt` に入っているので、取得を足さずに使える。

代替案:
- ラベルを付けた時刻（timeline API）: PR ごとに呼び出しが 1 回増える。D-001 の呼び出し回数を増やすほどの差は無い
- 最新コメントの `CreatedAt`: 規則 7 はラベルの付与で始まるのでコメント時刻では測れない。さらに、規則ごとに別の時刻を使うと仕組みが 2 つになる
- 規則 7 を消す: #825 / #826 は規則 2 で隠れているので、それだけでは直らない

### しきい値は 3 時間の定数 1 つ（`classify.StaleAfter`）

上流 `routine-sweep` は「最新のコメントが人のもので、そこから 3 時間を超えて routine の返信が無い PR」を止まったとみなし、引き継ぐ。loop-cli がこれより短い時間で PR を人に戻すと、sweep が引き継ぐ PR を人も同時に触ることになる。3 時間に揃えれば、loop-cli が PR を人に戻すのは sweep も止まっているときだけになる。

規則 7 には sweep の基準が無いが、同じ 1 つの定数を使う。assess は CI の完了を待ってから評価するので、3 時間あれば通常の評価は終わる。今回の障害は日単位で起きており、3 時間でも十分に拾える。

設定ファイルには出さない（値を選ぶ材料が利用者側に無く、変えたい要求も無い）。

### 規則 2 / 3 の時間切れはその他、規則 7 の時間切れは判定表へ

規則 2 / 3 の PR は、人のコメント（変更の依頼や質問への回答）がまだ AI に反映されていない状態である。判定表に流すと、checks が緑なら C（merge する）に出て、人が依頼を反映しないまま merge しかねない。`merge-action` の警告もこの状態を検出しない。そこで判定表を評価せずに、その他の局面で `PR #<n> は人のコメントに AI が応答していない` と出し、人に次の手（Routine を確かめる、PR を開いて直す）を示す。

規則 7 の PR は、AI の作業が済んで評価だけが残っている状態である。判定表に流して C に出し、人が merge しようとすると、既存の `merge-action` が `ai-assess:requested` の警告を出す。

### `ai-assess:requested` があれば規則 2 / 3 を当てない

worker は、人の回答を反映して未確定が 0 件になってから `ai-assess:requested` を付ける（`routine-common` の worker の規約）。したがって、このラベルがあれば最新コメントが人でも回答は反映済みである。#825 / #826 はこの状態にあたり、規則 7 で扱って時間切れ後に C へ出す。

### `now` を引数で渡す

`classify.PR` / `classify.Card` / `fetch.Fetch` は `now time.Time` を受け取る。`cmd/loop-cli` の fetcher は、呼ばれるたびに `time.Now()` を渡す。テストは固定の時刻を渡す。

- `internal/classify` の fixture テストは各 PR の `UpdatedAt` を `now` に渡す。採取した時点の局面で期待値を書いてあるので、実行日によって結果を変えない
- `loop-cli-dev classify` は、経過の列に使っている現在時刻を `classify.PR` にも渡す。実際の画面と同じ見え方にするためである

パッケージ変数で時計を差し替える方式は採らない。このリポジトリに前例が無く、引数の方が呼び出し側から見える。

## Risks / Trade-offs

- [`UpdatedAt` が AI 以外の出来事（CI の完了など）でも動くと、止まった AI を生きているとみなし続ける] → 動くたびに 3 時間延びるだけで、動きが止まれば人に戻る。CI の完了で `updatedAt` が動くかは実測していない
- [`ai-assess:requested` が付いた後に人がコメントすると、未反映の依頼があっても規則 7 で扱われ、時間切れ後に C に出る] → 上流の規約ではこのコメントは同じセッションの auto-fix が受け取る。merge しようとすると `merge-action` が `ai-assess:requested` の警告を出す
- [端末の時計がずれている] → `UpdatedAt` が `now` より後なら「間もない」とみなすので、時計が遅れても PR は隠れたままにならない。時計が進んでいる場合は、人に戻るのが早まるだけである
- [スナップショットから起動した直後の分類は、保存した時点の結果のまま] → 次の更新（自動更新または `R`）で `now` を渡して分類し直すので、そこで直る
