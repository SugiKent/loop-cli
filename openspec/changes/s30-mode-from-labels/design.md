# design: s30-mode-from-labels

Refs #24

## 方式の正本を移す

いまの流れは `config.yml` → `config.Repo.Mode` → `cmd/loop-cli.repoModes` → `fetch.Fetch(modes)` と `ui.Options.Modes` である。
設定が正本なので、TUI が動いている間に方式が変わることは無く、書き忘れは `view.go` の警告でしか分からない。

この change の後の流れは `gh label list` → `fetch.Fetch` の判定 → `fetch.Result.Modes` → `ui` の状態 になる。
正本は GitHub 上のラベル一覧そのもので、TUI が持つのはその写しである。写しは取得のたびに丸ごと入れ替わり、
どこにも保存しない。

3 つの経路を閉じるための形である。

1. 設定に書かない → 書き忘れが起きない
2. スナップショットに入れない → 前回の実行時の方式で書き込む経路が無い
3. 判定できないリポジトリでは書き込みを止める → 推測した方式でラベルを書く経路が無い

## 判定の置き場所

判定そのもの（ラベル名の列から方式を決める）は `internal/model` に置く。`internal/model` は既に `Mode` と
`IssueStages` / `PRStages` / `TodoLabel` という「方式ごとの語彙」を集めた場所で、判定はその語彙の逆写像だからである。
`internal/fetch` に置くと、方式の語彙が 2 パッケージに散る。

判定は「どちらとも決められない」を返せる形にする。`sdd` はゼロ値と同じ値なので、`Mode` 1 つでは
「`sdd` と判定した」と「判定できなかった」を区別できない。呼び出し側は区別できたうえで、表に入れるかどうかを決める。

## 取得と表の作り方

`Fetch` は search を 2 回実行したあと、詳細取得（`ViewIssue` / `ViewPR` / `ViewPRMergeState` / `ReviewThreads`）と
`ListLabels` を同じ並行プールに投入する。`ListLabels` はリポジトリごとに 1 本で、`repos` の要素数ぶん増える。
プールを分けないのは、`gh` の同時実行数の上限を 1 か所で持つためである。

すべて終わってから、判定できたリポジトリだけを `Result.Modes` に入れ、その表を使って `buildCards` が分類する。
表に無いリポジトリ（失敗・判定不能）は `model.Mode` のゼロ値、つまり `sdd` として分類する。分類は必ず 1 つ決まらないと
カードが並ばないので、ここは推測を許す。推測を許さないのは書き込み（`t`）だけである。

`Result.Errors` にはリポジトリ単位のエラーが加わる。いまの並びは「issue のエラー →	PR のエラー」で、どちらも
(repo, number) を持つ。`ListLabels` の失敗は番号を持たないので、リポジトリ名順にして先頭に置く。
`detailError` に「どの層の失敗か」を表す順位を持たせ、並べ替えのキーを 1 本増やす形にする。

## UI 側の持ち方

`ui.Model` は「リポジトリ名 → 方式」の表を状態として持つ。取得が成功したメッセージを受け取ったときに丸ごと差し替え、
取得が失敗したメッセージでは触らない。`Options` からは `Modes` を落とす。

表示（カード詳細の段階行・バッジ・PR 一覧の段階）は今と同じく `repoMode(repo)` を引く。表に無ければゼロ値の `sdd` で描く。
初回取得の前はスナップショットのカードを `sdd` の語彙で描くことになり、ILD のカードの段階行が `段階なし` になる。
取得は起動直後に走るので、この状態は数秒で終わる。

書き込み（`t`）だけは表に「有るかどうか」を見る。無ければコマンドを返さず、フッタの右側に理由を赤で出す。
`t` が対象を決める規則（画面に出ている Card の `Issue`）は変えない。対象が決まった後、方式を引くところで分岐が 1 本増える。

## label 方式の PR 分類

`classify.PR` の `label` の分岐は、いま「進行中の規則 2 / 3 →（規則 7 は sdd のみ）→ 行 D → 行 C → 行 F → 行 G → その他」の
順で評価される。この change で `label` は「行 A → 行 D → 行 C → その他」だけになる。

- 進行中の規則 2 / 3 を `label` で適用しない。`sdd` では auto-fix が PR を受け取って進めるので「進行中」に落とす意味があるが、
  ILD は 1 issue = 1 PR を人が捌く前提で、キューから外れると人の出番が見えなくなる
- 行 C と行 D の対象の絞り込みから `Closes #n` を外す。`Closes #n` は「routine が作った PR の印」として使っていたが、
  ILD のリポジトリの open PR を全件出すのがこの change の目的なので、印で絞る理由が無くなる
- 行 F（段階ラベルが 2 つ以上）は `PRStages(ModeLabel, …)` が常に空を返すので `label` の PR には当たらない。
  行 G（`docs`）は `label` では評価しない。どちらも今の実装のままで届かない

`sdd` の分岐は 1 行も変えない。`label` の条件だけを触るので、`sdd` の分類結果は変わらない。

## 未決事項

proposal の `## 未確定の判断` に人へ問う 4 件を書いた。ここには、その回答が決まるまで実装者が採る既定値を書く。

| 未決 | 既定値 |
| --- | --- |
| Q1 `L` の表の古さ | 取得が成功するたびに `L` の表を捨て、次に `L` を押したときに取り直す |
| Q2 どちらのラベルも無いリポジトリ | 判定できないものとして扱い、`t` を拒否する。0 件ヒントの 2 行目も「ラベルを作ってください」に直す |
| Q3 既存の `mode:` キー | 専用のエラー文で起動を止める。`config.go` に `case "mode":` を 1 本残す |
| Q4 行 D の `Closes #n` | 外す。行 C とそろえる |

既定と違う回答が来た場合に動く delta は次のとおりである。
Q1 が B なら `Result` にラベル一覧が加わり、`label-picker` の Scenario を「取得の後は取りに行かない」形に書き直す。C なら `label-picker` の delta ごと消える。
Q2 が B なら `ModeFromLabels` は常に方式を返す形になり、`t` の拒否は「取得の失敗と初回取得前」だけになる。
Q3 が B なら `config.go` の `case "mode":` が消え、`config-loading` の delta は Requirement の削除だけになる。
Q4 が B なら `human-turn-classify` の差分 4 は今のまま残る。
