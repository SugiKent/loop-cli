# sugi-loop 検証計画

最終更新: 2026-09-05-1805

現時点で決まっている検証はこの 2 点だけである。design.md には検証手段としてこれ以上の記述がなく、
不足分は推測で埋めていない。Phase 1 を実装する前に、ここへ具体的な合否条件を足す。

## V-1 分類器を fixture でテストする

分類器（`internal/classify`）がこのツールの価値の本体なので、ここだけは先にテストを書く。
`GHClient` を interface にし、稼働中リポジトリから取った JSON を個人・組織情報を伏せて fixture にして、
live データなしでテストする。検証対象は [人の出番（判定ルール）](../domain/issue-driven-sdd/human-turn-signals.md) の
局面 A–G と、「どの行にも当たらない open PR は『その他』バケットに必ず出る」こと。

## V-2 最初の動作確認は稼働中リポジトリ 1 件で行う

`routines-setup` を回していないリポジトリには `stage:*` ラベルが無く、TUI には何も出ない。
最初の live 確認は issue-driven-sdd が稼働しているリポジトリを 1 件だけ設定して行う。

## 未定

- TUI からの書き込み（`t` と `s` によるラベル付与、`a` と `A` によるコメント投稿、`m` による merge、`n` による issue 作成）を
  検証する手段は未定である。fixture では足りない。検証用リポジトリを用意するか、dry-run を実装するかは未決。
  TUI が書くラベルは `stage:todo` と `stage:propose` の 2 つに限られる（[D-004](./decisions.md)）。
- デスクトップ通知の差分比較の検証手段。
